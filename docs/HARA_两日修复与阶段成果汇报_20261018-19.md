## 二、之前为什么会“报告跑了很久，看起来却不够好”

可以把 HARA 分析理解为一项事故推演：先说清楚故障发生在哪里、车辆怎样运动、周围有什么，再计算可能发生的接触和风险。

之前的链路在几个地方衔接不够紧：

- **场景有名字，缺少画面。** 写了“驱动异常”，但没有成套的目标、距离、方向和加速度，程序拿不到可计算的工况。
- **不同工况的材料混在一起。** 旧阶段的加速度可能进入新故障模型；“车头朝上坡”和“向前溜车”没有建立明确关系。
- **题目很多，环境却很单一。** 驾驶员、参数取点一层层展开，判断数量涨了，但大量记录仍集中在同一停车场和路面条件。
- **离线样本准备充分，真实模型没有相同保证。** 模拟回答可以提供完整参数，真实模型却可能只返回符号、缺失几何或不适用方案。
- **算出来和展示出来之间还有误差。** 条件性数值被当作“没算出来”；分组统计盖住了正常场景描述；评分依据充满内部过程词。
- **运行开销不只来自模型。** 并发配置没接通、重复传上下文、反复保存大 checkpoint、响应返回后未及时持久化，都在增加时间和重发风险。

因此，这两天修复的不只是提示词，而是从“提供材料”到“计算、判断、保存、展示”的整条链路。

## 三、主要修复：之前什么样，改了什么，现在怎样

### 1. 让系统主动构建完整的物理工况

**之前：** 原文没有写故障加速度、碰撞距离，分析就容易停在符号或 Pending。某些场景只给一个加速度，却没有说明会撞到什么、距离多远。

**做了什么：** 在普通 `analyze` 中接入有界物理方案任务。已有来源或代表规则能计算的场景继续沿用原路径；不足时，让模型在一次任务中提出相互匹配的对象、位置、运动模型及参数。程序负责检查、实例化、求轨迹并评分。事实、方法、分析假设和程序推导各自保留来源。

**现在的效果：** 真实驱动样本由模型提出前方静止车辆、距离 5 m、故障加速度 1.5 m/s²，结合初速 7 km/h，程序得到碰撞速度 **15.6 km/h**、首次接触时间 **1.59 s**，并完成 **S1/E3/C3/A** 及 Excel 输出。参数是条件性假设，不是车辆实测能力。

普通全量也使用同一策略，消除了“样本有特殊提示，正式运行走另一套办法”的差异。

### 2. 防止把不同对象、阶段和来源拼成一个工况

**之前：** 新方案明确说“故障后加速度未知，用符号表示”，却可能从父场景继承旧加速度 2 m/s²，进而算出看似精确的速度和 TTC。还出现过静止 Atom 与初速 7 km/h 并存、同一移动目标被改成静止目标的反例。

**做了什么：** 建立当前模型的输入视图。新点值使用新点值，范围保留范围，显式符号保持符号；省略字段只继承对象、阶段、角色和坐标都适用的值。合法的新初态或新目标必须更新对应条件、身份及 Atom，并重验受影响因果。

同时修复了“同值覆盖来源”的问题：另一条记录即使数值相同，也不能把 LLM 假设重新标成已确认的原文事实。

**现在的效果：** 不再用旧数字把未知参数偷偷补齐；真实单场景修复前后数值保持一致，但来源恢复为正确的条件性假设。父事实和历史响应仍保留，便于回查。

### 3. 把坡向、车头朝向和溜车方向真正连起来

**之前：** 看到正坡度幅值，可能直接按“向前运动、前方目标”计算。这样虽然公式能算出数字，车辆运动方向却可能解释错。

**做了什么：** 明确坡度单位、上/下坡参考方向、车辆朝向、车体坐标和重力方向。阻力始终阻碍运动；初始静止且保持力足够时，不虚构反向启动。

**现在的效果：** 对原 12 条坡道样本逐条回查，6 条方向发生变化，2 条 S/E/C/ASIL 组合变化。没有为了保持旧数字而保留错误解释。后续真实预检和全量已包含坡道路径；最新全量 99 条坡道模型记录中，97 条得到条件性 ASIL。

### 4. 让因果判断看到程序已经算出的物理结论

**之前：** 程序已经算出“接触前停住”，模型却可能继续说“发生碰撞”；还有把“后车追尾本车”解释成“本车倒车撞后方静止车”的情况。两种场景不能因为都涉及后方目标就互相替换。

**做了什么：** 把既有的物理接触结果、符号关系及其对象/阶段引用送入固定因果视图。明确失效必须能够导致所列运动；同一对象和阶段下，无接触轨迹不能被声明为已发生接触。

**现在的效果：** 两类共 8 个已知错误身份在最终普通生产路径中被排除；正常倒车驱动正例仍能通过。修复过程也证明：只强化提示词不够，模型必须收到关键输入。

### 5. 修复模型输出契约和有限纠错

**之前：** 字段放错位置时，错误只说“参数不合法”，模型多次修正仍可能改不到点上；枚举大小写也曾被误判为实际条件冲突。早期真实样本还出现缺括号、缺身份等输出问题。

**做了什么：** 给出准确字段名、路径、单位和允许形态；按既有枚举语义比较大小写；启用当前路由支持的 JSON object 模式，并继续执行本地结构和语义校验。纠正请求携带原始错误响应，不手工补成“模型成功”。

**现在的效果：** 三组坡向结构/截断问题经过有界恢复成功，已有成功方案继续复用。最新全量仍保留 2 个最终 INVALID 方案，未把局部失败伪装为全部成功。

### 6. 补来源范围，让场景覆盖不再只停留在标签上

**之前：** 原始 Item 的上下坡 15% 范围未完整提取；室内、室外与车位条件没有充分进入代表选择；天气还曾替代道路条件。较早全量 3,500 条判断全部选择多层停车场，约 97% 采用低附着条件。

**做了什么：** 将室内/室外、坡度允许范围及车位属性接入来源规范化和代表生成；按实际维度选择 WHERE/ROAD；保留有工程意义的代表，避免简单地把所有标签互相相乘。15% 被当作允许范围和适用边界，不硬填成每条场景的实际坡度。

**现在的效果：** 最新物理展开前的 816 个来源候选包含 3 类 WHERE、4 类 ROAD，其中 194 条选择较大坡度 Atom、20 条选择左右附着差 Atom。已明显改善单一环境集中问题。

**尚未完成：** 多层停车场 Atom 仍占 674/816。通用停车场 Atom 本身也不能证明室外覆盖；仍须结合来源上下文逐项核对关键 ODD 与危险机制的对应关系。

### 7. 减少没有新增信息的参数展开与重复推理

**之前：** 一个物理方案生成多个参数点，再乘驾驶员分支，数量迅速放大。即使因果链已经明确中断，后续空占位字段仍可能触发一次付费纠正。

**做了什么：**

- 保留范围端点、实际方法边界和必要代表点，减少同一区间内没有新增信息的取点。
- 符号几何场景优先保留参数关系，避免生成一批仍然不能数值求解的近似任务。
- 精确复用以未舍入输入、对象、阶段、来源和模型为依据，不按相同文字、等级或 Pending 合并。
- 修复驾驶员合批绕过复用证明的路径；能证明共享的部分共享，其余独立判断。
- 仅省略因果断点之后没有主张、没有证据的空占位，保留真实后续主张和错误引用检查。

**现在的效果：** 同一批冻结真实方案重放中，自主物理实例由 30 个收敛到 22 个，共同点的计算结果和可计算等级集合保持一致。旧全量中识别出 579 次只由空占位触发的纠正，冻结响应回放证明可以避免；这些已经发生的历史调用没有被倒算成节省。

最新全量实际为 385 次物理方案共享、768 个共同证据批次、1,470 条局部上游因果共享。**精确因果任务复用和完整因果结论复用均为 0**，这一点如实保留，不能用合批数替代。

### 8. 让运行更快，也让中断后更少“交第二遍作业”

**之前：** `max_workers=4` 没有传到物理任务阶段，实际串行；大量重复上下文被反复发送；每完成一个小任务就复制、编码和保存越来越大的状态。还发现一次模型已返回、整批尚未保存，恢复后又请求了一遍。

**做了什么：** 接通现有并行调度；用可还原的引用压缩重复上下文；改为合并变化部分、紧凑编码 checkpoint、跳过未变化缓存的重复保存；风险事实响应也复用已有逐响应缓存，先保存返回，再提交整批状态。预算仍由同一本持久账本约束。

**现在的效果：**

- 15 份冻结请求压缩前后可无损还原，字符量下降约 78.7%；这不是全量 Token 节省率。
- 同一实际 checkpoint 的编码耗时从 3.17 s 降至 0.71 s，解析后的内容相同。
- 32 组冻结并发实验中，快照次数从 68 次降至 32 次，保存相关耗时由约 2.09 s 降至 0.96 s。
- 最终真实全量的请求、Token 和总时间确实下降，见第一节；各项局部收益不能直接相加当作整体加速比例。

### 9. 修复已有 C 方法的接线，保留真正的方法缺口

**之前：** 已有优先规则适用的 C，可能被后续 TTC 检查无条件清空；另一侧又存在把故障执行器的正常能力继续当作可用避险能力的风险。

**做了什么：** 命中活动方法的适用路径时沿用现有规则；制动能力已失效时，不把“有遥控按钮”等同于“有有效制动能力”。侧向首次接触时间不改名为纵向 TTC，也没有新增未经确认的 C 阈值。

**现在的效果：** 最新全量 C 数值可用率由 6.4% 提升至 49.0%。仍缺方法或控制能力证据的场景保留具体原因，没有统一填 C3 来提高完成率。

### 10. 让 Excel 重新讲清“发生了什么、为什么这样评”

**之前：** 审核组数量、内部 ID 和分支统计占据场景描述；评分理由主要是执行步骤；明细塞入过多原始结构；同一个“待审”标签既表示有条件性数值，也表示根本没有数值。

**做了什么：**

- 单成员保留正常场景文字，多成员显示真实共同条件，差异放到独立说明和明细。
- 按同一分支显示完整 S/E/C/ASIL，不拼接不同分支的各列最大值。
- 无唯一完整组结论时显示共同值或未决，成员等级分布仍保留。
- 评分理由优先写碰撞对象、速度、接触时间和实际参与的 E 条件；规则与完整来源留在追溯中。
- 功能、失效清单从上游完整投影，不因没有风险行而消失。
- 区分“已有来源/方法数值”“已有条件性数值”“尚无数值”，修复摘要与跨表统计。
- 速度最多 1 位小数，距离、加速度、时间最多 2 位；显示舍入不改变计算精度，小非零值不显示成零。
- 等级格保持 S1、E3、C3、A 等纯等级，审核状态另列；条件性初速和碰撞速度都能正常展示。

**现在的效果：** 最新报告 9 个功能、61 个失效、1,000 个风险明细身份及等级已逐项对账。主表、明细、SG 页面已渲染检查。SG 文案曾做过来源匹配和行为短句压缩，但最近全量复核又发现不足，不能将 SG 通用表达标为完成，见第五节。

### 11. 收敛代码，同时保留历史和有效实现

**之前：** 多轮修复容易堆出同职责包装、重复初始化或样本专用逻辑，后续维护难以判断哪个入口是权威。

**做了什么：** 更新仓库约定，功能修复和纯清理分开提交。清理了已证明无额外职责的报告包装、重复初始化、无用转换及临时列表；保留方法编译、来源检查、历史兼容和离线/真实客户端各自职责。

**现在的效果：** 同一冻结输入下，清理前后的请求、状态、身份、来源、评级和报告保持一致；历史报告 123,444 个单元格及样式核对一致。没有新增平行评分器或报告器，没有清空历史运行、修改个人配置或以删行数作为交差指标。

## 四、验证是怎样一步步走到真实全量的

这两天不是一次改完就直接跑全量，而是经历了几个有明确边界的阶段。

| 阶段 | 证明了什么 | 不能证明什么 |
|---|---|---|
| 离线反例、点值/范围/符号回放 | 输入隔离、方向、计算、缓存及报告接线 | 不能证明真实模型会提出同样好的条件 |
| 早期有界真实样本 | 暴露格式、契约反馈、符号输入和持久化问题 | 有些轮次预算耗尽，未形成完整数值报告，未计作验收成功 |
| 单一驱动真实端到端 | 4 次请求完成真实方案、因果、事实、评分和 Excel，来源修复后数值不变 | 不是全功能或全 ODD 验证 |
| 五族真实预检 | 18 次请求，14 条保留风险；全部有 S/E，8 条有 ASIL，6 条侧向 C/ASIL 未决 | 不是要求所有方法缺口清零 |
| 最新真实全量 | 9 功能、61 失效，实际产出 1,000 条风险及报告 | 不是正式工程审批，也不是所有场景已独立复核 |

最新代码完整回归为 **1,038 passed、1 skipped**；编译、差异检查和活动方法/模板诊断通过。唯一跳过是原有需显式启用的历史运行保护测试。真实 Provider 结果另有账本和原始响应，未混入离线测试通过数。

全量运行中修复所需的重新判断、重试和暂停，都保留在总耗时与账本中。没有为了显示优化收益而删除失败请求，也没有将旧响应改成新的模型成功返回。

## 五、最新评审指出：哪些还没有做好

### 1. Safety Goal 仍有具体错误和缺失

参考 IAV 样表有 8 条较集中的安全目标，当前报告有 29 条草稿。数量不同本身不构成错误，但当前划分更多跟随功能、引导词和故障原文，同一安全意图仍有重复和碎片化。

最明确的反例是：目标写成 **“防止需解除驻车时无法释放”**，关联的 4 条事件却全部描述 **“驻车请求卡死在释放状态，无法施加驻车制动”**。也就是目标写“松不开”，实际分析“拉不起”。这是短句选取与成员分支错配，需要优先修正。

另有目标重复拼接“防止功能关闭失效”，并把 7 km/h 倒车速度带进正文；部分文字过泛或仍在复述故障过程。转向类因为 ASIL 未完成，没有进入当前 SG 汇总页，不能让读者误以为没有相应安全意图。

**这些是刚完成的只读复核发现，尚未在本报告截止版本中修复。** 当前 330 条 A/B 风险均关联 SG，29 条 SG 的最高已计算 ASIL 与其关联成员一致；关联和汇总正确，不代表目标语义已经正确。

### 2. FTTI 和 Safe State 还缺正式的方法链

当前报告能计算不少场景的接触时间，但没有完成 FTTI 推导。TTC 描述给定轨迹多久接触；FTTI 需要结合故障起点、危险事件判据及相关工况确定容错时间，不能直接把 TTC 换个列名。

参考表中的响应时间和安全状态也不能照搬。后续需要把安全目标、危险形成的时间边界、安全处置及其所需时间连起来。当前“待确定”反映的是实际方法缺口。

### 3. S/E/C 的数值完成率，不等于全面工程合理性

- **S：** 当前 997 条可计算，但依赖所选对象、轨迹和参数假设；尚未证明覆盖最危险的合理工况。
- **E：** 当前全部能计算，但 Atom 的语义适用和环境覆盖仍须核对，不能只验公式能否执行。
- **C：** 510 条没有数值，其中 429 条侧向方法缺口、78 条失效控制能力依赖未明确、3 条缺 TTC。
- **ASIL：** 507 条有数值，493 条未决。其中部分 S0 按活动方法得到 QM，即使 C 仍未决，所以 C 与 ASIL 的未决数不相同。

本次核对 997 个分支记录，未发现汇总漏掉更高的已计算 ASIL；Excel 与 checkpoint 的身份和等级一致。这证明了数据一致性，不能代替对全部工况和因果关系的工程验收。

### 4. HARA 条目和 ODD 覆盖还没有完全闭合

最新全量中，驱动扭矩保留 203 条、全部有 ASIL；转向扭矩保留 382 条、暂无完整 ASIL；驻车制动保留 117 条、107 条有 ASIL；报警提示保留 3 条、暂无完整 ASIL。

“开启功能”做了 48 条判断后全部排除。这不自动等于漏分析，但需要检查排除理由是否成立。后续应形成“来源 ODD 条件 → 相关失效 → 危险机制 → 场景分支 → 结果/排除理由”的覆盖对应，不能把功能名称都出现过等同于覆盖完成。

### 5. 报告的运行性质标签仍需修正

最新全量确实使用真实 Provider，但 SG 页仍写“离线/条件性草稿”。这里混淆了两件事：**是否真实调用模型**，以及**结果是否仍待工程确认**。应分别表达，不能让真实运行成果看起来像模拟结果。

## 六、下一步往哪里完善

建议按下面的顺序推进，优先消除已有结果中的明确问题，再补方法能力，避免又花几个小时跑出同样的缺口。

| 优先级 | 工作方向 | 具体完成标准 |
|---|---|---|
| P0 | 修正 SG 分支意图、冗余表达和运行性质标签 | “松不开/拉不起”等反例正确；参数不混入共同目标；未决目标可见；ID、关联和审批可追溯；从现有 checkpoint 重导验收 |
| P1 | 核对关键 ODD 与危险机制覆盖 | 原文室内/室外、坡道、车位和交通对象等条件有明确去向；排除有依据；不靠增加候选数量宣称覆盖 |
| P1 | 复核有数值结果的适用性 | 对制动、驱动、坡道、侧向、功能启停选代表分支，核对假设、轨迹、因果、E 条件及 C 能力依赖，不只看等级是否非空 |
| P2 | 补侧向 C、移动目标及间接行为的方法能力 | 明确可用方法、适用条件和能力依赖；通过活动 MethodContract 接入，不借用纵向 TTC 或统一填 C3 |
| P2 | 建立 Safe State / FTTI 分析方法 | 安全目标、危险时间边界、处置过程及时间预算能够相互追溯；无依据的不填固定毫秒数 |
| P3 | 继续减少重复工作 | 分开记录精确任务、方案、共同证据、局部因果、完整因果复用；以真实请求和 Token 验收，不以缩表数验收 |
| 持续 | 维护回归与代码收敛 | 保留历史反例；修复与清理分开；对实际触及职责检查重复实现，已证明关闭的问题不反复扩大审查 |

SG 展示和现有数据核查可以先零 Provider 完成。确需新模型验证时，用固定代表场景和有效预算测试；有必要再做同提示、同输入的 Turbo/Pro 对照。现有证据已经表明，同一个 Turbo 在任务与输入修正后能显著改善，尚不能将问题简单归因于模型能力，也不能承诺换模型会解决方法缺口。
