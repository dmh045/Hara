# wf-05～wf-08：场景组合、驾驶员配置与物理世界

本文展开当前工作流的 **wf-05—wf-08**，生产逻辑以 `d6a400e` 源码为基准；交接文档更新不改变这里的生产职责。场景数量与覆盖采用五份输入各自的最新修订结果，不能把一个项目的数量当成其他输入的固定产出。下面标为“伪结构”的内容仅解释字段和关系，示意数字不是项目事实；“实现例”的代码则连续摘自指定生产提交，并标注函数、行号、调用方与对应测试。普通主入口是 [assess_scenarios](../../../src/hara_agent/workflow/nodes/scenarios.py)，四步在该节点内部连续发生，并非四套独立运行时。

## wf-05 将失效与基础场景配对，选择适用的方法选项

### 从功能失效到运行场景

到这一步，程序已经知道项目有哪些功能，以及某个功能可能怎样偏离预期。例如，“控制驱动扭矩”是功能，“输出的驱动扭矩大于当前需求”是一种失效。可是，这句话没有说明车在哪里、朝哪个方向运动、附近有什么对象。车辆在空旷位置轻微前移，与车位开口处朝横穿行人加速，不能仅因为失效名称相同就得到同一个风险结论。

wf-05 的工作，是把“功能出了什么问题”放进“问题发生在什么运行条件下”。它先使用原文已经支持的地点、模式和范围，再查看当前方法是否为这类失效提供了适用的分析选项。这些选项可能把“车辆附近有障碍物”进一步细化成对象的类别、方位或交互关系。此时得到的仍是**需要继续验证的候选**：程序尚未认定故障一定造成碰撞，更没有决定 S、E、C 或 ASIL。

“场景”在不同阶段对应不同的数据对象。它们保存的信息和已经证明的结论不同，具体区别如下。

| 名称 | 用通俗话理解 | 它已经确定了什么 | 它还没有证明什么 |
|---|---|---|---|
| 来源父场景 | 从资料中整理出的运行背景 | 有来源的模式、位置、环境或允许范围 | 某个故障会造成什么后果 |
| 方法分析候选 | 把某个失效放进某组适用条件 | 本次要检查的失效与运行条件组合 | 因果成立、数值风险或工程批准 |
| 物理方案 | 对“故障后怎么动、与谁交互”的结构化解释 | 选用模型、对象、参数假设和控制依赖 | 模型提出的假设就是真实产品能力 |
| 参数取点 | 为一个范围选取有限个可计算例子 | 某一次计算使用的具体参数 | 整个连续范围都得到相同结论 |
| 驾驶员分支 | 在同一相关工况下检查不同人员条件 | 人在哪里、对应哪些来源和限制 | 人一定能接管，或能使用某个控制 |
| 碰撞成员 | 在一个具体物理世界中求出的接触关系 | 当前对象、轨迹、接触阶段及计算结果 | 可以与另一个成员混拼 S/E/C |

**本章贯穿例子是流程示意，不是新增项目事实。** 假设输入资料明确支持“车辆在停车区域执行泊入”，功能为驱动控制，失效为驱动输出偏大。下面沿用这条线索说明程序如何补齐世界；假设中的距离、加速度和人员条件只用于解释计算过程，不会写入生产方法，也不能拿来替代五份输入各自的原始证据。

### 贯穿示例一：驱动异常的运行范围与对象

对这个驱动异常，程序可以检查“车辆朝前方静止对象运动”，也可以在输入允许且方法适用时检查“车辆与移动道路使用者发生交互”。这两个候选的意义不同，因为接触对象和轨迹不同。程序不应把“停车”理解成必然只有多层停车场，也不应为了提高严重度而擅自选高速道路。

在这一阶段，核对重点有三项：原文是否允许该运行条件；当前方法选项是否适用于该失效；原对象、模式或方向是否得到保留。下面的调用说明和筛选记录，分别提供对应证据。若方法没有足够证据作强匹配，程序会保留已有来源条件供后续检查；“没有选上某个模板”与“这个场景没有危险”是两件事。

### 调用入口、输入和这一步的权限

`assess_scenarios` 对每个 `MalfunctionCandidate` 调用 `MethodScenarioCandidateService.generate_for_malfunction(malfunction, parents, project_facts, function)`。这里的 `parents` 是此前由项目模式与 ODD 建立的来源父场景；不是等待 LLM 自由补全的风险表行。服务先调用 `ItemDefinitionFacts.for_scope(function_id, operating_mode)` 收窄项目范围，再进入 `ScenarioMethodService.instantiate_analytical_candidates`。无 Atom 目录或项目事实时保留现有模板候选路径；正常 Atom 路径先不展开驾驶员，留到 wf-07。来源见 [method_scenario_service.py](../../../src/hara_agent/services/analysis/method_scenario_service.py)：`generate_for_malfunction`。

输入中承担不同职责的字段必须分开：故障的 `function_id/component_category/failure_type/functional_effect` 支持方法选择，父场景的 `operating_mode/facts/fact_provenance/semantic_fingerprint` 定义已有条件，方法的 `scenario_model.scenario_method.fm_template_catalog` 提供可执行模板选项。项目原文没有给出的能力不能从模板示例推断。这一步只生成方法来源的分析候选，不授予因果通过、评级或工程批准。权威实现见 [ScenarioMethodService](../../../src/hara_agent/services/analysis/scenario_method_service.py)，字段契约见 [MethodContract](../../../src/hara_agent/contracts/method_contract.py)。

### 筛选顺序与保守放行的准确含义

第一层是 `MalfunctionSituationSelectionService.select`。它由有来源的功能输出、功能运行作用域和规范化故障类型匹配情境规则，对每个父场景产生 `INCLUDE/EXCLUDE/UNRESOLVED`。没有正向规则不等于排除：缺输出证据、没有目录或竞争规则时，记录 `UNRESOLVED` 并继续后续因果判断。真正 `EXCLUDE` 要有可执行排除权限、批准项目约束、当前项目／功能／MF／场景范围精确匹配的直接证据；不能因“没命中参考场景”删除父场景。入口见 [malfunction_situation_selection.py](../../../src/hara_agent/services/analysis/malfunction_situation_selection.py)：`select`，审计保留 `records/exclusion_evidence/unresolved_passthrough_count`。

第二层才是 `match_fm_template`。一般路径按关键词／治理别名、组件类别、失效类型发现候选，再由 `_qualify_matches` 判断强、弱或歧义；原始首项优先序只记录，不作为歧义时偷选第一条的依据。另有已绑定项目且字段精确匹配的治理工程决定路径，也要核对批准模板及完整 option 身份。只有 `FMTemplateMatchResult.injectable`，即 `STRONG_MATCH` 且存在模板时，才执行父场景×模板选项；否则 `selection_mode=BASE_CANDIDATES_ONLY`，保留来源父场景。入口见 [scenario_method_service.py](../../../src/hara_agent/services/analysis/scenario_method_service.py)：`match_fm_template/_qualify_matches/instantiate_analytical_candidates`。

一般资格判断的真实先后是：唯一“组件＋失效”交集先得强匹配，多个交集为歧义；无此唯一交集时，结构化组件／失效支持相互冲突则拒绝挑选；没有组件命中而有唯一“失效＋来源机制关键词”时可强匹配；唯一被规范目录支持的组件模板也可强匹配。只有失效类型或只有关键词通常仍是弱匹配，不据此注入。这样既不会让一个碰巧出现的词覆盖结构化冲突，也不会因多一个关键词别名降掉本已唯一的结构证据。具体层次及审计 `qualification_tier` 仍以 [_qualify_matches](../../../src/hara_agent/services/analysis/scenario_method_service.py) 为准。

第三层逐 option 检查对象／方位、数值类型与非负范围、方法词汇映射，以及与父事实是否相容。`INVALID_TEMPLATE_OPTION` 或明确冲突的 option 不注入，并保留 `validation_status=INVALID/CONFLICT`；未映射词汇记 `UNMAPPED_METHOD_VALUE`，不伪造规范对象类型。合法 option 的距离、目标速度等写作 `SCENARIO_DEFINED`、`approval=PENDING` 的分析条件，原父对象不原地改写。一个父场景可以产生多个相互隔离候选。**强匹配后若全部 option 无效／冲突，该方法返回空实例列表，不再悄悄退回父场景；这与未强匹配时保留父候选不同。** 要查 `options/conflict_count/instance_count` 解释数量变化，不能自行补一个“最危险”对象或把未生成当成因果已否定。实现见 [instantiate_analytical_candidates](../../../src/hara_agent/services/analysis/scenario_method_service.py)。

### 输出身份与故障差异如何保留

新候选指纹由场景契约版本、方法哈希、MF ID、父 ID、父指纹、模板 ID、`source_option_id`、源资产哈希及实际 option facts 一起计算，生成 `SCN-ANALYTICAL-…`。不是按“描述文字一样”合并，也不是按最后评级相同合并。`analysis_instance` 与逐字段来源保存 `source_template_id/source_option_id/source_option_values/source_hash/applicable_scope/assumptions`；MF 或物理选项不同，不能只保留一段共用文案冒充已经分析。入口见 [scenario_method_service.py](../../../src/hara_agent/services/analysis/scenario_method_service.py)。

```text
# 字段示意，非实际对象／数值
ScenarioCandidate:
  scenario_id: SCN-ANALYTICAL-示例
  source_scenario_id: 来源父场景示例
  facts: {object_position: FRONT, object_speed_kph: 示例值}
  fact_provenance.object_speed_kph:
    provenance: SCENARIO_DEFINED
    approval: PENDING
    source_option_id: 模板示例:OPTION:1
    applicable_scope: {malfunction_id: MF-示例, scenario_id: SCN-ANALYTICAL-示例}
  analysis_instance: {malfunction_id: MF-示例, source_template_id: 模板示例, assumptions: […]}
```

wf-05 的计数至少分清 `base_candidate_count/scenarios_after_selection/instance_count/options`；这些是具体阶段口径，不是请求次数，也不是风险数。查证入口是 `situation_selection` 与 `analytical_scenario_instantiation` 审计；回归可从 [失效与工况选择回归](../../../tests/unit/test_malfunction_situation_selection.py)、[来源场景实例化回归](../../../tests/unit/test_analytical_scenario_instantiation.py) 和 [运行范围与限定条件回归](../../../tests/unit/test_qualified_odd_scope.py) 开始。

## wf-06 在 ODD 约束内组合场景 Atom，并合并精确重复

### ODD、场景 Atom 与代表覆盖

ODD 是运行设计域，表示功能允许工作的范围；例如允许的地点、路面、天气或速度范围。Atom 在本项目中指方法目录里的一个结构化场景条件。它不只是报告中的一个词，还带着稳定身份、适用范围和方法含义，供后续暴露度 E 等计算使用。可以把 Atom 理解为“程序和方法双方都认识的一块条件”，例如一个场所条件或一种道路条件。

wf-06 把适用的条件组合成有代表性的分析候选。它不是把目录中所有条件排列组合，也不是让模型先猜一个 E 再反向挑选 Atom。组合必须先满足项目范围与条件相容性：如果原文只支持泊车运行，不能为了填满维度选入高速公路交通行为；如果某个维度对当前世界不适用，也不必随便填一项。

这一层同时回答两个不同问题。第一个是**覆盖**：是否保留了足以改变危险机制的不同条件。第二个是**精确重复**：两个来源记录是否事实上描述了完全相同的分析输入。覆盖需要保留差异，精确去重则可以减少重复计算；两者不能通过“最后评级一样”来混为一谈。

### 贯穿示例二：独立工况与重复记录的区别

沿用驱动异常的例子，假设资料中有两段文字都支持同一个前方静止对象工况。如果实际对象、方向、速度、来源权威和方法绑定都相同，只是显示文字不同，可以保留一个代表，同时记录它对应原来的两条身份。工程师仍能追查这两条来源，只是不必把同一个任务发给模型两次。

如果另一条是在坡道上、目标在车后，或者一种人员条件会影响功能使能，那么它改变了工程条件，不能按文字相近合并。还有第三种情况：两条条件不同，但有界覆盖选择只保留了其中一条。未选择的那条必须记为“本轮未评估”，不能把它记为“与保留者风险相同”。

| 观察到的情况 | 当前层应怎样解释 | 对数量统计的影响 |
|---|---|---|
| 条件及有效来源完全相同，原始 ID 不同 | 精确重复，可建立代表与别名映射 | 减少代表任务，原始身份不丢失 |
| 目标、坡向、附着或相关控制条件不同 | 保留不同世界 | 增加的记录有明确工程差异 |
| 条件不同，但本轮未选为覆盖代表 | 有界选择留下的未评估组合 | 不计为已验证覆盖或复用收益 |
| 文字不同，结构字段是否相同还不清楚 | 尚不能证明精确重复 | 不能仅凭相似描述合并 |

因此，数量统计至少区分“生成了多少原始身份”“保留了多少代表条件”“哪些组合暂未评估”。主表行数是更下游的展示口径，不能用来代替这三个数。

### 组合不是七维全集，也不是按评级选工况

wf-05 产生的每个物理 option 进入 `ConstrainedScenarioSynthesisService.generate_candidates`。实际调用为 `generate_for_malfunction → generate_candidates → _generate_context_candidates → build_input → logical_selection_assignments → validate_provider_payload → materialize`；验证方法名称虽然带 provider，普通确定性组合仍复用它来校验本地产生的选择，不表示这一层必须联网。当前基线的七维是 `WHERE/ROAD/EGO_ACTION/EGO_X_ROAD/TRAFFIC_PATTERN/EGO_DYNAMICS/OBJECT`，维度定义和适用性由已编译 `scenario_model` 提供。入口见 [scenario_synthesis_service.py](../../../src/hara_agent/services/analysis/scenario_synthesis_service.py)。

`build_input` 从 MF、功能输出、父条件、FM 模板证据与已按函数／模式收窄的项目上下文构建语义查询，再由 `candidate_sets` 分别形成候选池。硬约束包括速度交集、坡度、天气、来源地点、全局复合 Atom 相容性和可执行方法约束；排序使用机制与条件语义，不把 E 等级作为选取“更危险场景”的依据。已确认、不可修改的父绑定不能被覆盖；可细化的分析选择则保留父 Atom、子 Atom、来源与细化理由。必需、可选、不适用三类维度分别处理，不能为了凑齐七格把不适用项硬填成任意 Atom。入口见 [candidate_sets/hard_filter_decision/global_compound_legality](../../../src/hara_agent/services/analysis/scenario_synthesis_service.py)、[ScenarioConstraintExecutor](../../../src/hara_agent/services/analysis/scenario_constraint_service.py)。

### 覆盖选择、来源边界与失败去向

逻辑组合先满足 `coverage_plan` 中的主要变化维度及复合填充关系。一个复合 Atom 可填多个维度，但不能被再次选择、与另一个 Atom 冲突占用同一维度。来源坡度边界通过独立 context 表达，而非把所有坡度、车位、天气与对象求笛卡尔积；`include_source_boundaries` 控制每个物理 option 的来源锚点，明确边界优先解析，再让普通来源场景代表其他环境。没有合法 assignment 返回 `NO_VALID_COVERAGE_ASSIGNMENT`；多来源边界 context 无解时可保留 `SCN-SOURCE-…` 的 PENDING 缺口候选，上层某 option 未产生组合时保留该 option 供后续审查，而不是扩回整个目录。入口见 [generate_candidates/_generate_context_candidates](../../../src/hara_agent/services/analysis/scenario_synthesis_service.py)、[generate_for_malfunction](../../../src/hara_agent/services/analysis/method_scenario_service.py)。

跨来源 context 的 `_select_context_representatives` 按四类特征选择：主要 Atom 组合、原来源条件、WHERE、ROAD。已覆盖特征的其他**不同条件组合**进入 `deferred_context_variants`，明确 `status=COMBINATION_NOT_EVALUATED`、`risk_equivalence_proven=False`。它们不是“已经证明风险相同的重复”；其中真正精确相同的别名仍交给后面的 coalescing 建立映射，不能在覆盖裁剪时丢掉。数量审计包括各维 `catalog_size/hard_filtered_pool_size/candidate_atom_ids/generation_status` 与 `coverage_plan`。实现见 [MethodScenarioCandidateService._select_context_representatives](../../../src/hara_agent/services/analysis/method_scenario_service.py)。

### 精确去重比较哪些字段

`coalesce_candidates` 对有 `scenario_atom_ids` 的候选按 `signature(scenario_conditions(candidate))` 分组；没有 Atom 身份时以原 `scenario_id` 保持独立。规范化视图含 `operating_mode`、实际 `facts` 和 `fact_authority`。已解析维度仅保留 `atom_id/canonical_atom_id/filled_dimensions/method_semantics/applicability_status/speed_intersection_kph`；未解析绑定完整保留，避免把两个不同的未知误并。速度数值约束仍在 facts 中，只有重复的 `speed_context_resolution` 提取历史不参与身份。代码见 [scenario_equivalence.py](../../../src/hara_agent/services/analysis/scenario_equivalence.py)：`scenario_conditions/coalesce_candidates`。

来源权威也参与比较，字段包括 `provenance/approval/method_source_hash/method_contract_hash/analysis_value_semantic/time_role/unit/source_refs/applicable_scope/validation_status/input_fact_metadata/object_id/coordinate_frame/fault_motion_model`。规范化只对当前／父生成 ID、生成的目标别名、接触／轨迹局部 ID 做一致重命名，并忽略 `branch_id/semantic_fingerprint/display_label` 等身份标签；实际目标身份和实际语义不同仍保留。`source_refs` 与 `scenario_atom_ids` 排序消除无意义顺序差异，不把不同来源、作用域或批准当成等价。不要另写一个“只比 Atom ID”的去重器。权威实现见 [scenario_conditions](../../../src/hara_agent/services/analysis/scenario_equivalence.py)。

### 输出、映射与下一步

代表候选保留 `equivalent_candidate_ids/equivalent_parent_ids/condition_signature`；若最初来源父层级与即时父层级不同，还记录 `source_parent_ids`。去重前身份由 `record_generated` 写入 append-only 审计，不是删历史。随后 `_allocate_source_focus` 按非驾驶员规范世界稳定分配来源条件，记 `source_condition_focus`，不新增世界；wf-07 才展开人员。`atom_generation` 审计给出 `raw_candidate_count/unique_condition_count/coalesced_candidate_count/equivalence_mapping/source_focus_allocation`，未选条件只能声明未评估。入口见 [method_scenario_service.py](../../../src/hara_agent/services/analysis/method_scenario_service.py)，回归见 [场景合成回归](../../../tests/unit/test_scenario_synthesis.py)、[场景覆盖治理回归](../../../tests/unit/test_scenario_coverage_governance.py)、[场景生成生产链回归](../../../tests/unit/test_p6_scenario_pipeline.py)。

## wf-07 按来源与项目策略展开驾驶员配置

### 人员位置对功能与控制能力的影响

驾驶员分支不是为了让每个场景自动多出两行。它是把人员条件明确放进分析：驾驶员坐在驾驶位、在车内但不在驾驶位、在车外，这些情况对应的可用控制可能不同，也可能影响功能是否允许启用。程序只能展开当前输入和适用策略支持的配置，不能假设所有泊车项目都同时允许车内和车外操作。

沿用驱动异常例子，车辆不受干预时的运动轨迹可能相同；但坐在驾驶位的人是否能通过独立踏板制动，与站在车外的人能否发送远程停车命令，是两个不同问题。即使制动执行器没有故障，也不等于任何位置的人都能控制它。需要继续检查控制入口是否存在、是否在当前故障下仍可用、响应是否来得及。

### 贯穿示例三：共有运动与不同人员控制

如果本项目确实支持两种人员条件，程序可在物理方案中共用“车辆向前加速接近对象”这部分，并分别记录两种人员配置的控制条件。这样有机会减少重复方案请求，同时仍保留两种情况下各自的因果判断、可控性和响应结果。

但共享有边界。例如，某个故障只有在远程操作模式才会触发，或者驾驶员在座时系统根本不会使能，那么人员变化已经影响危险形成。此时不能复制另一分支的完整因果结论。后续会根据依赖证明判断能复用哪一段；证明不足就分别判断，仍可共享已有证据，避免重复读取同一批资料。

本步先明确：**来源允许哪些位置 → 当前父场景是否已固定位置 → 位置能推出哪些事实。** 随后在 wf-08 的物理与控制分析、wf-09 的具体因果调度中，继续核对当前故障下有哪些控制路径，以及哪些结论有充分依据复用。报告中一句“驾驶员在车外”必须来自前面的来源和推导，不能只是为了把英文标签翻译得简短。

### 人员配置从哪里来，什么时候不展开

`generate_for_malfunction` 在条件去重和来源焦点分配后，调用 `ScenarioMethodService._with_driver_configurations`，内部由 `DriverConfigurationBrancher.expand` 展开。输入是 wf-06 的候选、项目 `risk_facts` 和经 `effective_project_policy` 处理的活动政策，不是把驾驶员有／无当成无条件二选一。无项目事实、无有效 policy ID，或没有来源有效且 FINALIZED 的 `DRIVER_IN_VEHICLE` 允许配置时，保留原候选，不造默认驾驶员。入口见 [scenario_method_service.py](../../../src/hara_agent/services/analysis/scenario_method_service.py)、[driver_configuration_service.py](../../../src/hara_agent/services/analysis/driver_configuration_service.py)。

`allowed_position` 从 `context.allowed_driver_position` 或有原文支撑的“在驾驶位／不在驾驶位”解析位置；布尔／数值编码表达成员状态，不另造地理位置。`_scope_matches` 将除允许位置标签外的 context 约束，与当前 `facts/operating_mode/scenario_id/parent_scenario_id/malfunction_id` 逐项比较。不属于当前模式、MF 或条件的允许集合不参与该世界。父场景若已经固定位置，只核对该位置，不重复展开；固定位置不在项目允许集合时保留原身份，记录 `SOURCE_CONFLICT`、`driver_configuration_source_conflict` 并清除不可靠的位置布尔推导，不能偷换为另一个配置。代码见 [DriverConfigurationBrancher.allowed_position/_scope_matches/expand](../../../src/hara_agent/services/analysis/driver_configuration_service.py)。

### “不在驾驶位”与“车外”不是同一事实

在驾驶位可推出人在车内；不在驾驶位可能在副驾、后排或车外。没有独立车内／车外来源时，`outside_driver_seat` 不直接推出 `driver_in_vehicle=False`。只有明确绑定当前项目、模式和来源的 `driver_location_convention` 才能补该约定，不能因产品叫泊车系统便套用。独立“人在车外”事实还会阻止拼接矛盾的驾驶位分支。该差异直接影响人工 C、远程干预和下游可用操作，因此不能在报告层把两者统一翻译后丢掉结构字段。权威入口为 [location_convention/apply_location_convention/_independent_vehicle_location](../../../src/hara_agent/services/analysis/driver_configuration_service.py)。

### 同一运动如何带着不同控制继续走

wf-08 可将非驾驶员条件完全相同的成员组成物理家族，共享未缓解轨迹方案，并把实际 `driver_configurations` 传给物理 Agent。方案中的 `driver_control_assessments[position]` 由 `controls_for_driver` 选择：通用 `braking/drive/steering/parking_hold/speed_limiter` 执行能力可在无局部冲突时共享，但 `driver_braking`、`remote_control`、`automatic_*_command` 不靠执行器完整自动补出；显式局部失败和未知优先。相同模型／对象的共有故障时钟可以按既有严格规则保留，但不能借另一个人的响应或覆盖局部 timing gap。代码见 [physical_scenario_plan.controls_for_driver](../../../src/hara_agent/contracts/physical_scenario_plan.py)、[workflow.physical_analysis](../../../src/hara_agent/workflow/physical_analysis.py)。

历史响应若遗漏 `driver_positions`，只允许从**签名验证通过的唯一请求配置**恢复同一人员范围：`plan_key` 匹配、去掉 plan_key 后的 context 签名匹配、MF 相同、`conditions` 与 producer 的规范输入全等；多配置、未知或明确冲突均不能默认车内。实例化 `request_driver_scope` 记录该证据，不篡改 LLM 原回复。入口见 [PhysicalHypothesisInstantiationService.instantiate](../../../src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py)，真实冻结回归见 [请求人员范围回归](../../../tests/unit/test_request_driver_scope.py)、[保存响应的人员范围回归](../../../tests/unit/test_saved_personnel_response_scope.py)。

### 共享物理方案不等于共享因果批准

驾驶员变化可能改变启用、触发、交互和危险。后续 `_assess_instantiated_scenarios` 用 `driver_families` 组织成员；只有 `driver_reuse_proof` 证明非驾驶员事实及来源权威一致、变化字段不被依赖、且存在完整或四方面局部 noninterference 证据，才尝试重绑并由正常 parser 重验。失败原因如 `NON_DRIVER_CONDITIONS_CHANGED/DRIVER_NONINTERFERENCE_NOT_PROVEN/DRIVER_FACT_USED_BY_CAUSAL_CHAIN` 会转为独立因果判断；至多复用已证明相同的 MF→B 前缀，不能复制整条通过结论。共同请求中分别判断的成员也不是复用成功。入口见 [scenario_equivalence.driver_reuse_proof](../../../src/hara_agent/services/analysis/scenario_equivalence.py)、[nodes/scenarios._assess_instantiated_scenarios](../../../src/hara_agent/workflow/nodes/scenarios.py)。

### 实现例 P02｜人员分支只采用当前范围内有来源的位置事实

`ScenarioMethodService._with_driver_configurations` 调用 `DriverConfigurationBrancher.expand`。下面是展开之前的准入部分：输入是一个场景及项目中性的 `risk_facts`；输出在没有适用人员事实时仍是原场景的单元素元组，不是默认增加车内／车外两条。

[实际源码：DriverConfigurationBrancher.expand，第177—200行](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/src/hara_agent/services/analysis/driver_configuration_service.py#L177-L200)

<!-- source-example: src/hara_agent/services/analysis/driver_configuration_service.py:L177-L200 -->
```python
def expand(
    self, scenario: ScenarioCandidate, risk_facts: Iterable[dict[str, Any]],
) -> tuple[ScenarioCandidate, ...]:
    if not self.policy_id:
        return (scenario,)
    if scenario.analysis_instance.get("driver_configuration_branch"):
        return (scenario,)
    by_position: dict[str, list[tuple[str, SourceRef]]] = {}
    for fact in risk_facts:
        if not isinstance(fact, dict):
            continue
        if str(fact.get("parameter", "")).upper() != "DRIVER_IN_VEHICLE":
            continue
        if str(fact.get("approval", "")).upper() != "FINALIZED":
            continue
        position, context = self.allowed_position(fact)
        if not position or not self._scope_matches(context, scenario):
            continue
        for source in self._source_refs(fact):
            by_position.setdefault(position, []).append((
                str(fact.get("fact_id", "")), source,
            ))
    if not by_position:
        return (scenario,)
```

`FINALIZED` 在这里修饰来源位置事实，不是把后续整个场景批准。`_scope_matches` 继续匹配当前模式和条件，`_source_refs` 保留来源。通过这段后，后续代码才核对父位置、建立新身份并应用有项目绑定的约定；“不在驾驶位”仍不能据此推出“人在车外”。

更不能从“人在车内”直接推断脚能够踩到制动踏板：位置证据与 `driver_braking` 能力由后续控制路径分别处理。这段仅证明分支准入，不证明人工制动可用，也不证明两个人员分支的因果相同。生产展开回归为 [普通生产链只展开适用人员分支](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/tests/unit/test_sec_scenario_semantics.py#L494-L529)；位置与车辆内外区别见 [驾驶位事实与车辆内外位置的区别](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/tests/unit/test_sec_scenario_semantics.py#L172-L194)；人工通道反例见 [人在车内不等于能够操作踏板](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/tests/unit/test_physical_input_scope.py#L60-L73)。

## wf-08 形成可计算工况，实例化物理分支并求轨迹

### 从危险描述到可计算物理工况

“驱动异常可能撞上前方对象”描述了危险主张，却还不能计算。程序至少需要知道起始运动状态、目标相对位置、故障后如何运动，以及相应模型需要的几何条件。wf-08 的目的，就是在已有事实和方法范围内，把这些信息整理成同一对象、同一阶段、同一坐标下的可计算工况。

这里有两类工作。模型负责提出并解释分析假设，例如采用哪个已有运动模型、选择什么代表距离、剩余哪些控制；Python 负责检查这些内容是否相容，再按方程计算。模型不得直接给最终风险等级，也不能通过写一句“已经批准”让假设变成项目事实。已有来源或规则足够时，程序直接用现有输入，不需要重新请模型编一遍。

本章中的“世界”是对一个完整工况的简称：同一时刻的车辆和对象、相对位置、运行条件，以及接下来假设的运动。这样称呼，是为了强调不能把甲世界的距离、乙世界的速度和丙世界的控制能力拼成一条看似完整的计算输入。

### 贯穿示例四：条件性假设与确定性求解

下面仍讲驱动异常，但**另用一组教学参数展示求解过程**，与前文“2秒接触”的例子分开：初速为 1 m/s、故障后恒定净加速度为 1 m/s²、到前方静止对象首次接触还有 5 m，目标确实位于该运动路径上。这是一组完整但条件性的输入，不是车辆实测能力，也不是生产默认值。

Python 使用 `5 = 1 × t + 1 × t² / 2` 求首次正时间根，得到约 2.32 s；接触速度约为 3.32 m/s，即 11.94 km/h。此处展示值经过舍入，实际程序保留计算精度。接下来还要验证“该失效确实会导致这里假设的车辆行为和接触”，并由活动方法决定相应的 S/E/C；不能只看到一个碰撞速度，就直接宣告某个 ASIL。

如果加速度只知道范围，程序可以在有限的代表点和边界点上计算，保存每次计算的参数。如果加速度只能保留符号 `a`，那么可保存 `v_contact² = v0² + 2ad` 这样的关系及适用条件，而不能把上一步故障前的某个加速度偷偷补回来。两种输出都可提供分析价值，但含义不同：一个是“在这些数值假设下的结果”，另一个是“结果如何随未确定参数变化”。

### 物理阶段的输出及下游用途

| 产物 | 它回答的问题 | 后续怎样使用 |
|---|---|---|
| 原始方案与假设依据 | 为什么选择这个对象、模型和参数 | 审核假设合理性，复查来源限制 |
| 当前模型输入视图 | 本次究竟使用哪些父事实、哪些新假设，排除了什么旧值 | 防止对象、阶段、单位和坐标串用 |
| 轨迹与接触结果 | 是否接触，何时接触，以什么速度接触 | 给具体场景因果检查和风险计算提供输入 |
| 参数敏感性与未取点说明 | 哪些取值已算，哪些范围还未证明 | 避免把少量计算点说成连续范围保证 |
| 控制与响应诊断 | 当前响应是否有适用控制，能否达到所提状态 | 支持后续 C、Safe State 和 FTTI 的各自检查 |
| 子身份及父身份映射 | 这条具体工况从哪条来源、哪个方案形成 | 恢复运行、关联明细和定位报告问题 |

这些产物出现于风险评分之前，但其中关于响应的计算也会被后续评分与报告链复用。**物理可计算、因果成立、评级有值、工程批准是四个不同层次。** 例如，几何有效但响应无法避碰，是一个有意义的工程结果；不能为了让它显示成功而把距离加大，或把没有依据的制动能力调高。

### 入口：先使用已有权威，再选择三条任务路线

人员条件展开完成后，程序先检查已有输入能否直接使用：绑定当前项目和方法中的物理事实，区分正常运行速度与故障后运动速度，并在适用时使用受治理的代表运动规则。**已经建立的自主物理假设，不会再被模板默认值覆盖。**

随后才决定是否需要调用模型：缺运动条件时补完整方案，运动已知时只补控制和响应，所需内容已评估时直接继续。这三条路线最后都进入同一个物理计算服务；调用路线不同，不代表使用了不同的风险计算器。

| 执行位置 | 实际职责 | 代码索引 |
|---|---|---|
| 先整理可直接使用的输入 | 绑定已有事实、检查速度含义，按适用的代表规则补成物理输入；保留已有自主假设 | [AnalyticalPhysicsInstantiationService.produce_inputs](../../../src/hara_agent/services/analysis/analytical_physics_instantiation_service.py) |
| 调度物理阶段 | 从场景分析节点进入物理构建，组织候选、复用和请求 | [assess_scenarios](../../../src/hara_agent/workflow/nodes/scenarios.py) → [construct_physical_scenarios](../../../src/hara_agent/workflow/physical_analysis.py) |
| 选择任务范围 | 判断需要完整运动方案、只补控制，还是无需新请求 | [PhysicalHypothesisInstantiationService.task_scope](../../../src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py) |

| `task_scope` | 触发与输入 | 应改变／应保留什么 |
|---|---|---|
| `MOTION_AND_CONTROLS` | 现有碰撞／运动输入不能建立来源有效的当前轨迹 | 提出模型、几何、点／范围／符号参数及剩余控制；有依据的初态、目标和来源约束继续保留 |
| `CONTROL_INPUTS_ONLY` | 已有运动可复用，但活动方法所需控制／人员声明未评，或时序要求需补同一运动的响应 | 原轨迹、对象、速度和坐标不变，只评当前范围的控制与响应；生成受父身份绑定的控制实例 |
| 空字符串 | 已有作用域有效的完整评估，或现有规则已足以回答所需输入 | 不再发物理／控制请求，沿用该世界进入后续因果；明确 failed/unknown 也是完成的评估 |

三路规则在 [PhysicalHypothesisInstantiationService.task_scope/manual_path_gap](../../../src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py)。不能把“C仍无值”直接等同还需 Provider：合法无接触、符号关系、已明确未知及方法不适用可保持 Pending 而不反复请求。反过来，旧方案只说通用 `braking` 执行器保留，未评 `driver_braking`，也不能因此跳过所需人工路径补评；此时只补控制，不重跑运动。

### 哪些工况可以共用方案，程序怎样识别同一请求

程序先按**相同任务范围、相同规范化物理条件**分组。这种组在代码中称为“物理家族”。它共享的是尚未施加避险响应时的故障运动提案，不是所有成员的最终风险结论。目标、坐标、速度、模型、来源权威或有效期不同，就不能因为描述相似而直接并为同一任务。

人员条件也不能一概删除。共同运动条件可以与完整驾驶员配置分开传递；但如果驾驶员具体位置未知，输入又明确说明人在车内或车外，这个存在条件仍保留在共同物理输入中。否则，分组时就可能把不同的运行条件错误合并。

| 用途 | 对应字段或实现 | 阅读时应注意什么 |
|---|---|---|
| 识别可以共用提案的组 | `_physical_families` 使用 `task_scope` 与 `physical_conditions(candidate)` 的签名 | 相同失效编号本身不足以证明输入相同 |
| 提取共同物理条件 | `physical_conditions` 调用 `scenario_conditions(..., without_driver=True)` | 特定的 `driver_in_vehicle` 存在条件仍会保留，并非删除全部人员信息 |
| 保留各人员分支 | `driver_configurations` | 共用运动提案后，各成员仍须使用自己的控制条件 |

分组以后，实际请求还需要带上功能、来源、方法和版本等信息。这些内容一起决定 `plan_key`，即完整请求输入的签名。它不是仅对失效编号或父场景编号做哈希。这样，相同编号下的来源、方法或提示语义发生变化时，就不会误读成旧任务。

| 请求内容 | 对应字段 | 为什么需要它 |
|---|---|---|
| 当前分析对象及项目依据 | `malfunction`、`function`、`project_context`、`project_physical_facts` | 区分分析哪个功能失效，以及采用哪些项目条件 |
| 方法、控制输入和分析用语 | `method_identity`、`method_version`、`intervention_inputs`、`risk_vocabulary` | 区分适用方法和本次可判断的控制条件 |
| 执行策略、输入状态及版本 | `analysis_strategy`、`model_input_status`、`producer_version`、`model_catalog_identity`、`prompt_version`、`route` | 防止不同策略、模型目录或提示版本错误共用结果 |
| 完整运动任务的候选范围 | `source_condition_focus`、`operating_atom_options`、`object_focus_options` | 限定来源条件和可选对象；控制任务则使用对应的控制请求版本 |
| 可追溯来源片段 | `_source_evidence` 选择的原文块 | 按任务选取踏板、退出、自动停车、故障处理和接口等证据，缩小请求但不改写原文 |

生成签名后，程序把 `plan_key` 写入保存的 `context`，供实例化时核对请求身份。分组入口见 [workflow.physical_analysis._physical_families](../../../src/hara_agent/workflow/physical_analysis.py) 和 [PhysicalHypothesisInstantiationService.physical_conditions](../../../src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py)；请求组织与签名生成见 [construct_physical_scenarios](../../../src/hara_agent/workflow/physical_analysis.py)。

### 结构校验、继承与真实实例身份

模型交回方案后，程序先检查“写法是否符合契约”，再检查“这些输入是否属于当前工况”。两层检查不能互相替代：JSON及字段正确，不代表某个旧值就可以用于新对象、新阶段。方案状态为 `VALIDATED` 只表示通过相应契约校验，**不表示其中的车辆能力或分析假设已经获得工程批准**。

继承父场景输入时，程序同时核对当前失效与场景来源、单位、坐标、模型、对象和时间含义。例如，接触时的速度不能直接成为新轨迹的初速；前一个目标的距离不能成为新目标间距；故障前加速度也不能成为故障后净加速度。真正适用的父值可以继续使用，不适用的值保留排除原因，而不是删除历史资料或补一个默认值。

| 检查内容 | 字段或代码 | 失败或保留结果 |
|---|---|---|
| 方案是否符合约定结构 | 模型枚举、精确字段、单位、证据 ID、条件和控制依赖 | 先通过结构检查，才能进入后续实例化；结构合法不等于工程批准 |
| 运动假设数量及任务范围 | `hypotheses` 为0～3项；`uncovered_conditions` | 控制补评不得同时带运动假设；空方案必须说明具体未覆盖条件 |
| 控制、目标状态和时间放在哪一层 | 运动 `hypothesis` 内的控制、Safe State 和时钟；`control_assessment` | 运动假设直接携带这些内容，不再嵌套另一份控制评估 |
| 父值能否用于当前模型 | `_model_inputs`、`_inheritance_reason`；故障前阶段 `PRE_FAULT` | 不适用的继承值记录 `EXCLUDED_FROM_ACTIVE_MODEL` 及原因；不将故障前加速度当作故障后净加速度 |
| 必需输入是否齐全 | 当前模型必需字段；`REQUIRED_MODEL_INPUT_OMITTED` | 既未合法继承、又未声明的必需输入进入已有有限纠正，不制造默认值 |
| 参数是否被所选模型使用 | `MODEL_CATALOG`、`PARAMETER_UNITS` | 模型目录决定必需参数；单位表列有该字段不代表所有模型都使用它，误带参数可触发 `PARAMETER_NOT_USED_BY_MODEL` |
| 符号输入是否保持符号 | `SYMBOLIC` | 主动移除对应旧数值，避免声明符号后仍从父数据算出伪数值 |
| 新初态或新目标是否形成了新工况 | `condition_changes.initial_state`、`condition_changes.target` | 相应替换目标身份，核对条件单元（Atom）及来源约束；不能在同一身份上静默覆盖事实 |
| 对象、初速或人员范围变化后，方法条件是否同步 | `_object_binding`；`OBJECT`、`EGO_DYNAMICS`、`EGO_ACTION`；`operating_atoms`、`driver_operating_atoms` | 重新核对适用条件并更新 `method_scenario_dimensions`、`scenario_atom_ids`、`dimension_bindings`，而不是只改中文描述 |
| 新对象的暴露条件是否有对应依据 | `physical_object_exposure_conditional`、`physical_object_exposure_unresolved` | 新对象与原对象绑定不同时保留条件性标记；无法建立绑定时保留未解决标记，不借旧对象的 E 补空 |

检查通过后，程序为实际运动取点或控制补评建立子身份，同时保留父对象。新实例状态仍为 `PENDING`。下面的身份和证据字段，使报告中的结果能够追溯到具体方案、参数点和来源：

| 记录 | 身份或保存字段 | 用途 |
|---|---|---|
| 运动子实例 | PH 哈希使用 `parent`、`plan`、`hypothesis`、`point`；必要时加入严格验证的 `request_driver_scope`，形成父 ID 后缀 `-PH-…` | 区分不同方案、假设、取点及必要的人员范围 |
| 控制补评子实例 | CTRL 哈希使用 `plan`、`assessment`；必要时加入唯一请求驾驶位，形成父 ID 后缀 `-CTRL-…` | 保留原有运动，区分本次控制评估及其人员条件 |
| 两类实例的共同证据 | `physical_analysis` 或 `control_analysis` 中的 `plan_key`、`hypothesis_id`、`parent_scenario_id`，以及原假设、输入来源和条件性说明 | 将子实例连回请求、方案和父场景 |
| 运动实例的额外证据 | `sample_parameters`、`sensitivity`、`model_input_view` | 保存实际取值、敏感性信息和本次真正使用的模型输入 |

对象、速度和控制条件会影响风险，但这里的工作是形成一致的计算输入，**不是先选定 S/E/C，再倒推一组能得到它的参数**。评级由后续评分步骤执行。

### 模型方程、坐标与适用条件

当前自主模型分别描述直线加速、溜坡、横移、圆弧转向，以及与移动对象接触。每个模型由运动关系和适用条件共同定义。**模型的适用条件与公式同样重要**：公式算得出数字，不代表可以把它用到任意场景。

例如，圆弧转向描述车辆沿曲线行驶；横向恒加速度描述独立的横移或侧滑。两者都可能出现侧面接触，但不是同一运动。把普通转弯的法向加速度直接代入侧滑模型，会把物理含义改掉。另一个例子是坡道：坡度大小只决定重力分量的幅值，还必须知道车头与下坡方向的关系，才能判断车辆向前溜还是向后溜，以及前后哪个目标可能被接近。

所有方程先把 km/h 除以3.6转为 m/s；距离 m、时间 s、加速度 m/s²。`BODY_FORWARD_POSITIVE` 为初始车体 x前、y左，目标中心偏移带符号；方向角从+x朝+y计，是固定**速度方向**，不是车轮角。有限接触 `contact_half_length_m/contact_half_width_m` 是双方投影半尺寸之和，不能替换成缺乏来源的默认车长／车宽。静止沿程模型的 `relative_distance_m` 是至首次表面接触的剩余行程，不是中心距。权威单位与模型范围见 [MODEL_CATALOG/PARAMETER_UNITS](../../../src/hara_agent/contracts/physical_scenario_plan.py)。

| 模型 | 程序关系 | 使用前提与拒绝边界 |
|---|---|---|
| `CONSTANT_ACCELERATION_TO_IMPACT_DISTANCE` | `d=v0*t+a*t²/2`、`v_contact²=v0²+2*a*d`，稳定根求首次接触 | 静止目标在运动路径上；停止后不隐式反向。显式剩余独立限速可形成加速／限速分段，正常运行上限不是故障限速 |
| `GRADE_ROLLAWAY_TO_IMPACT_DISTANCE` | `a=max(0,g*sin(atan(p/100))-r)` 后使用沿程方程 | 从静止开始，坡度p为百分比，r为残余阻力；须明确重力与车头／下坡坐标。阻力足够时不启动，目标不在下坡路径不能强行接触 |
| `CONSTANT_LATERAL_ACCELERATION_TO_CONTACT` | `w=vy0*t+ay*t²/2`，x恒速，接触合速度按 x/y 分量求范数 | 明确独立惯性横移／侧滑与延展静止侧边界；不是恒速转弯，不能把正常转弯法向加速度当漂移；不派生纵向TTC |
| `CONSTANT_SPEED_CURVATURE_TO_CONTACT` | `theta=v*t/R`、`y=R*(1-cos(theta))`，`a_normal=v²/R` | 恒速无侧滑圆弧，只到显式时域或首个四分之一圆；方向、半径、目标侧须相容。半径为假设不等于车辆能力上界 |
| `RECTILINEAR_MOVING_TARGET_CONTACT` | `r(t)=offset+u_hat*s_target(t)-v_hat*s_ego(t)`；分段 `s=v0*dt+a*dt²/2`；首次同时 `abs(x)<=hx`、`abs(y)<=hy` | 固定方向／固定投影有限包络，自车恒加速度；目标恒速或显式反应后制动至停，停止保持不反向。不模拟时变转向或旋转包络 |

求解权威集中在 [scenario_physics.py](../../../src/hara_agent/services/analysis/scenario_physics.py)：`constant_acceleration_contact/constant_speed_curved_contact/rectilinear_moving_contact/derive_scenario_physics`。圆弧还可成对提供 `object_offset_x_m/contact_half_length_m`，只核对固定有效纵向区间是否覆盖计算接触点；缺区间时只能依赖延展边界假设，区间外返回几何不适用，不能说别处也不会撞。直线移动模型可用 `grade_frame` 从静止推导坡度运动，并用 `post_stop_motion=HOLD_POSITION` 检查本车停住后目标是否继续进入包络。治理规则生成的 `CONSTANT_SPEED_REPRESENTATIVE` 则是已有确定性输入路径，不是 Agent 可任选的第六模型。相关入口为 [AnalyticalPhysicsInstantiationService.produce_inputs](../../../src/hara_agent/services/analysis/analytical_physics_instantiation_service.py)。

RECTILINEAR在求根前先检查有限正包络与时域、速度非负、位置标签与偏移符号一致：例如 LEFT要求目标初始y为正。初态已重合返回 `INITIAL_CONTACT_REQUIRES_SEPARATE_PHASE`，不能伪装成稍后首次接触；位置符号矛盾返回 `TARGET_OFFSET_POSITION_CONFLICT`。目标的 `object_reaction_time_s/object_braking_deceleration_mps2` 必须成对、满足有效反应／制动条件；本模型不会把一个缺字段自动补成普通人反应能力。对应校验在 [scenario_physics._straight_world](../../../src/hara_agent/services/analysis/scenario_physics.py)，不满足时保留输入／几何诊断而不是返回安全等级。

### 点／范围／符号如何展开，哪些“最大值”不能宣称

`POINT` 是一个代表值；`RANGE` 同时保存 `lower/value/upper`；`SYMBOLIC` 保留符号、条件和理由，不调用猜测值填空。`_samples` 先用代表点，按单因素范围端点、活动方法边界与邻接区域取点，机制与参数点共享 `MAX_INSTANCES_PER_PLAN=3` 槽位，不做多参数笛卡尔积。未实际取的点列入 `deferred_points`；`parameter_relations` 仍保存可解释的符号关系与已知输入。`boundaries` 是从活动方法表读取边界再反解物理参数，不是新增一个评级器。权威实现见 [PhysicalHypothesisInstantiationService._samples/boundaries/parameter_relations](../../../src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py)。

```text
# 非JSON、非真实取值，仅展示三种参数字段；模型还须携带其余必需参数
parameters:
  - {field: ego_speed_kph, kind: POINT, unit: km/h, value: <代表初速>, rationale: <来源或条件依据>}
  - {field: longitudinal_acceleration_mps2, kind: RANGE, unit: m/s2,
     lower: <下界>, value: <代表值>, upper: <上界>, rationale: <故障阶段范围依据>}
  - {field: relative_distance_m, kind: SYMBOLIC, unit: m,
     symbol: d, rationale: <当前目标初始行程未能量化及适用条件>}
# 不把<代表初速>等占位符发送给Provider；这里仅解释契约形状。
```

例如某同一世界的可用距离仍为符号，已知净加速度范围也不能自动生成接触速度；参数关系可留待工程分析。样本中最大 S 或最高 ASIL只表明已算样本，`range_invariance_proven=False/vehicle_upper_bound_proven=False/deferred_points_evaluated=False` 必须保留。未知、零速度、停止前无接触和模型不适用是不同状态；有独立环境输入时 E可继续可算，不应因无S/C而全部清空。入口见 [physical_hypothesis_instantiation_service.py](../../../src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py)、[StructuredRiskScoringService](../../../src/hara_agent/services/analysis/structured_risk_scoring_service.py)。

### 当前世界、接触分支与反事实检查

`derive_scenario_physics(child)` 产生 `DERIVED.motion_model_outcome/ego_impact_speed_kph/object_impact_speed_kph/relative_speed_kph/first_contact_time_s` 等；只有实际位移轴满足纵向条件时才派生 `ttc_s`。`SIDE` 表面标签本身不等于横向运动；完整目标轨迹速度恒零时，`0×RIGHT` 仍为零向量，原方向标签保留，只在合法计算副本中使用静止方向。真正横移、初始零后运动、不同对象或阶段不满足该证明。接触后才生成含 `branch_id/mechanism_id/impact_time_id/physically_possible` 的有限碰撞成员，不从全对象目录补“最大危险”。入口见 [scenario_physics.py](../../../src/hara_agent/services/analysis/scenario_physics.py)、[_instantiate](../../../src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py)。

当前实现还有一个明确而窄的反事实：RECTILINEAR且自车初速为0时，复制同一facts，将 `longitudinal_acceleration_mps2` 改为0，再求 `stationary_ego_counterfactual`。如果同一目标也接触静止自车，调度加入 `CONTACT_WITH_STATIONARY_EGO`，要求说明故障增量危险或提出有依据的不同目标路径。它不是“正常请求世界”的通用仿真，也不自动否定故障；不能用原接触结果反向证明 MF必然引起运动。原世界和反事实分别保存，后续因果节点仍逐跳核验 M→B→I→H。权威实现见 [PhysicalHypothesisInstantiationService._instantiate](../../../src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py)、[instantiate_family内诊断](../../../src/hara_agent/workflow/physical_analysis.py)。

避让提案也只作用于计算副本：`moving_target_avoidance` 要有识别延迟、速度、净空以及有参数的有限过渡；反向不能瞬时发生，跨轴转向无模型就拒绝收益。它验证本对象能否避开该包络，不授予C等级。Safe-State提案同理：先检查当前剩余控制、实际响应轨迹和故障时钟，保存正窗口、即时不安全或缺控制诊断；可算响应不表示已经检测／触发，不能减去当前未缓解世界的危险。入口见 [scenario_physics.moving_target_avoidance](../../../src/hara_agent/services/analysis/scenario_physics.py)、[RiskCalculationInputService](../../../src/hara_agent/services/analysis/risk_calculation_input_service.py)、[FTTIMethodExecutor](../../../src/hara_agent/services/analysis/deterministic_risk_executor.py)。

### 一次有限纠正与失败后的原样保留

纠正的目的，是修复本次任务中有证据指向的问题，不是让模型一直重答到出现满意的评级。比如同一个方案对三个参数点都给出了相同的方向冲突，工作流会汇总这个共同问题，让原有方案作一次受限语义纠正；不会因为多了三个参数点就启动三个新的完整方案任务。纠正必须保留已经有效的世界条件，不能把“补控制路径”变成“换一个更容易避碰的目标”。

一个家族先实例化所有成员，再汇总几何／相位冲突、未评人工或自动命令、不可达响应、缺故障时钟及反事实等诊断，共用**一次**语义纠正；不是为每条分支再开一个 Agent。纠正前保存 `initial_plan/correction_diagnostics/instantiations` 并设 `CORRECTION_REQUESTED`，请求带 `previous_plan` 与中性差异反馈。Schema修复与这次语义纠正是不同计数；预算或网络请求也不能用“纠正”名义不记账。实现见 [construct_physical_scenarios](../../../src/hara_agent/workflow/physical_analysis.py)、[PhysicalScenarioAgent.propose](../../../src/hara_agent/services/semantic/physical_scenario_agent.py)。

纠正必须通过 `PhysicalScenarioPlan.validate_correction_scope`，不能以修控制理由改变已有效轨迹或世界。返回无效时保留原有效运动及局部缺口，记 `PHYSICAL_CORRECTION_INVALID_ORIGINAL_RETAINED`；合法返回再用同一个 producer 重实例化。仍无生成结果或方案不适用时，物理层保留原候选并挂 `physical_plan_diagnostics`，不为让流程继续而制造评级；解析／实例化失败保存 `INVALID`、原响应和错误。已撤回响应由 `_retain_rejected_response` 保留历史，并按当前严格作用域重验，不把旧负面文字冒充当前计算成功。入口见 [physical_scenario_plan.py](../../../src/hara_agent/contracts/physical_scenario_plan.py)、[workflow/physical_analysis.py](../../../src/hara_agent/workflow/physical_analysis.py)。

### 未完成结果的原因分类与处理责任

“未完成”可能来自资料、输入传递、模型范围或返回结构等不同环节，处理责任如下。它们不能都翻译成“输入信息不足”，也不能都用重发模型请求来处理。

| 实际状态 | 例子 | 应保留的结论与下一步 |
|---|---|---|
| 产品事实缺项 | 原文没有说明故障后某个命令通道是否仍独立可用 | 标明能力未获来源确认；可按合法条件性假设分析，不能冒充已知能力 |
| 动态参数尚为符号 | 模型给出了加速度 `a` 的关系，未形成可信数值范围 | 保存参数化关系和影响条件，不从旧阶段补回一个数值 |
| 新旧输入冲突 | 初始静止的有效条件与新方案初速不一致 | 指出冲突对象和阶段；合法新条件要重新实例化身份与绑定 |
| 物理模型不支持 | 当前任务要求模型目录以外的时变转向轨迹 | 记录具体模型范围缺口，不把目标改成静止来迁就计算器 |
| 合法无接触 | 在给定时域和轨迹内，两个包络没有相交 | 保留适用时域及条件；不伪造碰撞速度，也不据此推断所有工况安全 |
| 响应确实不能避碰 | 已有控制按给定延迟执行，仍与同一对象接触 | 保存失败轨迹与诊断；不能靠改距离、换目标或放大能力制造成功 |
| 返回结构错误 | 缺必需字段、单位不合法或引用了不存在的证据 | 保存原始响应，按现有有限结构修复处理，并统计请求成本 |

### 缓存恢复、当前派生视图与因果失效

缓存可以理解为“保存过、并且能够证明仍适用于本次输入的工作结果”。它不是看到相同失效编号就直接取旧答案。方案输入、方法版本、提示契约或人员条件变化后，旧结果可能只剩部分可复用；程序需要检查任务身份与作用域。反过来，输入没有变、模型已经明确给出局部不适用，也不应在每次恢复时重新花钱问同一个问题。

物理缓存保存完整 `context/plan/responses/instantiations/response_validation_version`。同校验版本已失败记录不会在每次resume无限重发；校验版本变化可先用已保存raw响应重验，合法旧计划应零新请求恢复。新提示、目录或真实输入语义变化必须改变正确身份，不能伪造旧key。`VALIDATED` 计划在每个家族成员上实例化，不表示所有驾驶员共享一次通过判断。权威入口为 [workflow.physical_analysis](../../../src/hara_agent/workflow/physical_analysis.py) 与 [PhysicalScenarioAgent的版本／响应checkpoint逻辑](../../../src/hara_agent/services/semantic/physical_scenario_agent.py)。

派生缓存纠正后的事实必须一致进入后续请求和任务身份。`scenario_with_current_physics` 仅对保存的直线移动接触结果采用同一个来源校验 materializer；无变化返回原candidate，有变化则用计算副本，不改原来源事实。直接PROJECT事实冲突报错，同值直接事实保留原来源；不能把所有DERIVED都当成随意可覆盖。后续 `exact_task_key`、`_scenario_json` 和 parser共同读取当前视图，所以旧“longitudinal_contact=false”结论不能用旧key冒充新true世界。输入／对象／条件／来源真的变化时，必须重验受影响因果；相同接触数值本身不是免费继承批准的理由。入口见 [scenario_equivalence.py](../../../src/hara_agent/services/analysis/scenario_equivalence.py)、[HazardousEventRiskContextService._scenario_with_derived_physics](../../../src/hara_agent/services/analysis/hazardous_event_risk_context_service.py)、[scenario_batching.py](../../../src/hara_agent/services/semantic/scenario_batching.py)。

本步输出为带来源与条件性的具体子场景、碰撞成员和完整诊断，交给 wf-09 的因果资格检查，尚不是最终 S/E/C。检查数量时同时看 `plan_requests/plan_cache_hits/generated_instances/physical_solve_points/physical_plan_reuse/control_plan_reuse/semantic_corrections`；缓存命中、确定性求解点、子身份和HTTP尝试不是同一数字。关键回归导航：[自主物理方案回归](../../../tests/unit/test_autonomous_physics.py)、[有界交互覆盖回归](../../../tests/unit/test_bounded_interaction_coverage.py)、[圆弧转向物理回归](../../../tests/unit/test_curved_steering_physics.py)、[零速度目标方向回归](../../../tests/unit/test_zero_target_velocity_direction.py)、[纵向接触表面与缓存回归](../../../tests/unit/test_longitudinal_surface_cache.py)、[已撤回方向的缓存重验](../../../tests/unit/test_withdrawn_axis_cache_revalidation.py)。

### 实现例 P03｜已求出的运动为什么只补控制，而不重新请求整个物理方案

程序先把任务范围和规范物理条件相同的候选放在一组，再检查这一组缺什么。已有完整评估时不增加请求；运动已知但缺控制或响应时，只补缺失部分；只有运动本身尚未建立时，才请求完整方案。下面展示任务范围判断的前半段。

| 返回值 | 对应的处理 |
|---|---|
| 空字符串 | 无需新增方案任务 |
| `CONTROL_INPUTS_ONLY` | 只补控制与响应 |
| `MOTION_AND_CONTROLS` | 建立完整运动方案及控制条件 |

**调用定位：** 物理调度入口 `construct_physical_scenarios` 先通过 `_physical_families` 分组，再由 `producer.task_scope` 判断任务范围。

[实际源码：PhysicalHypothesisInstantiationService.task_scope，第135—160行](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py#L135-L160)

<!-- source-example: src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py:L135-L160 -->
```python
def task_scope(self, candidate, malfunction_id):
    """Retain solved motion; assess its controls and response once."""
    scope = dict(malfunction_id=malfunction_id, scenario_id=candidate.scenario_id)
    for key in ("control_analysis", "physical_analysis"):
        if candidate.facts.get(key) and source_is_accepted_for(candidate.fact_provenance.get(key, {}), **scope):
            h = candidate.facts[key].get("hypothesis", {})
            if ("driver_in_vehicle" in self.intervention_inputs
                    and candidate.facts.get("driver_in_vehicle") is None
                    and not self.driver_position(candidate) and len(h.get("driver_positions", [])) != 1
                    and "driver_in_vehicle" not in h.get("unresolved_controls", {})):
                return "CONTROL_INPUTS_ONLY"  # Legacy omission; retain motion, assess the missing condition once.
            contact = candidate.facts.get("motion_model_outcome", {}).get("status") == "CONTACT" or bool(candidate.facts.get("collision_branches"))
            if contact and self.manual_path_gap(candidate, h, malfunction_id):
                return "CONTROL_INPUTS_ONLY"
            return ""  # An assessed limitation is not another request on resume.
    # A validated symbolic/no-contact world may intentionally have no
    # collision branches. Reuse its assessment rather than proposing the
    # same world again just to manufacture a numeric contact.
    if not (candidate.facts.get("collision_branches") and
            source_is_accepted_for(candidate.fact_provenance.get("collision_branches", {}), **scope)):
        return "MOTION_AND_CONTROLS"
    if self.method.metadata.get("project_analysis_policy", {}).get("timing_analysis"):
        # C readiness does not establish a reachable safe state or a timed
        # response. Existing source/method motion needs the same assessment
        # already requested by the autonomous motion path.
        return "CONTROL_INPUTS_ONLY"
```

可以直接看到两种节流：已有有效评估的限制不会因为恢复就再请求；已有合法碰撞分支且需要响应分析时，只走控制补全。调用前仍核对场景及 MF 来源作用域，不能把另一个世界的旧结果拿来省请求。方法未配置时间分析时，函数后半段还会按 C 的实际输入就绪情况判断，不能将这里的截取误读为所有路径只有这三个条件。

用于核查“真实少请求”的冻结回归是 [已有运动只补控制，恢复后不新增请求](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/tests/unit/test_c_response_applicability.py#L283-L338)：已有运动进入控制任务，补完后恢复不增加请求；[无接触或符号工况不重复提案](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/tests/unit/test_autonomous_physics.py#L606-L615) 则验证合法无接触／符号世界可以保留，而另一 MF 不得借用。样例证明的是这些给定输入的调度行为，不是承诺所有任务都不需纠正。

### 实现例 P04｜新方案的符号输入如何阻止旧数值被补回

`instantiate` 与 `input_status` 都调用 `_model_inputs`，所以提示中的缺口视图与真正实例化共用同一输入规则。下面截取遍历参数的主体；`explicit` 已由当前方案参数构造，`allowed` 已由当前模型的必需／可选输入构造，二者不是任意用户字典。

[实际源码：PhysicalHypothesisInstantiationService._model_inputs，第417—437行](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py#L417-L437)

<!-- source-example: src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py:L417-L437 -->
```python
values, audit = {}, {}
for field in PARAMETER_UNITS:
    if field in explicit:
        parameter = explicit[field]
        if field not in allowed:
            raise PhysicalInputConflict("PARAMETER_NOT_USED_BY_MODEL", field, None, parameter)
        audit[field] = {"action": parameter["kind"], "parameter": parameter}
        if parameter["kind"] != "SYMBOLIC":
            values[field] = parameter["value"]
    elif field in parent.facts:
        accepted, reason = self._inheritance_reason(parent, h, field, malfunction_id)
        value = parent.facts[field]
        if not isinstance(value, (int, float)) or isinstance(value, bool) or not math.isfinite(value):
            accepted, reason = False, "PARENT_INPUT_NOT_FINITE_NUMBER"
        if field not in allowed:
            accepted, reason = False, "PARAMETER_NOT_USED_BY_MODEL"
        audit[field] = {"action": "INHERITED" if accepted else "EXCLUDED_FROM_ACTIVE_MODEL", "reason": reason,
            "parent_value": parent.facts[field], "parent_metadata": deepcopy(parent.fact_provenance.get(field, {}))}
        if accepted:
            values[field] = parent.facts[field]
return values, audit
```

关键是 `if field in explicit` 与 `elif field in parent.facts` 互斥。模型明确提出 `SYMBOLIC` 时，会写入审计但不写数值，也不会落到父值继承分支。只有没有显式新参数，才检查父值的对象、阶段、角色、坐标、模型范围及数值有效性。返回的 `values` 供同一物理计算链使用；`audit` 保留继承或排除理由，不删除父事实。

反例是父场景保存故障前加速度 2 m/s²，新方案声明故障后 `a_fault` 为符号：子场景不得再产生唯一碰撞速度和 TTC。正例是新方案未填写加速度，而父值确属本车、故障后阶段、当前模型：允许继承并计算。两者分别由 [显式符号不得继承旧点值](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/tests/unit/test_physical_input_scope.py#L155-L167) 和 [未填写参数仅继承适用对象和阶段的值](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/tests/unit/test_physical_input_scope.py#L170-L186) 覆盖。范围取点与敏感性仍在 `_samples` 后续处理；这里没有把 RANGE 证明为连续范围不变，也没有把 LLM 假设变成来源事实。
