## wf-05 将失效与基础场景配对，选择适用的方法选项

### 从功能失效到运行场景

到这一步，程序已经知道项目有哪些功能，以及某个功能可能怎样偏离预期。例如，“控制驱动扭矩”是功能，“输出的驱动扭矩大于当前需求”是一种失效。可是，这句话没有说明车在哪里、朝哪个方向运动、附近有什么对象。车辆在空旷位置轻微前移，与车位开口处朝横穿行人加速，需要按各自条件分别形成风险结论。

wf-05 的工作，是把“功能出了什么问题”放进“问题发生在什么运行条件下”。它先使用原文已经支持的地点、模式和范围，再查看当前方法是否为这类失效提供了适用的分析选项。这些选项可能把“车辆附近有障碍物”进一步细化成对象的类别、方位或交互关系。此时得到的仍是**需要继续验证的候选**：程序尚未认定故障一定造成碰撞，更没有决定 S、E、C 或 ASIL。

“场景”在不同阶段对应不同的数据对象。它们保存的信息和已经证明的结论不同，具体区别如下。

| 名称 | 用通俗话理解 | 它已经确定了什么 | 它还没有证明什么 |
|---|---|---|---|
| 来源父场景 | 从资料中整理出的运行背景 | 有来源的模式、位置、环境或允许范围 | 某个故障会造成什么后果 |
| 方法分析候选 | 把某个失效放进某组适用条件 | 本次要检查的失效与运行条件组合 | 因果成立、数值风险或工程批准 |
| 物理方案 | 对“故障后怎么动、与谁交互”的结构化解释 | 选用模型、对象、参数假设和控制依赖 | 模型提出的假设就是真实产品能力 |
| 参数取点 | 为一个范围选取有限个可计算例子 | 某一次计算使用的具体参数 | 整个连续范围都得到相同结论 |
| 驾驶员分支 | 在同一相关工况下检查不同人员条件 | 人在哪里、对应哪些来源和限制 | 人一定能接管，或能使用某个控制 |
| 碰撞成员 | 在一个具体物理世界中求出的接触关系 | 当前对象、轨迹、接触阶段及计算结果 | 可以与另一个成员混拼 S/E/C |

**本章贯穿例子是流程示意，不是新增项目事实。** 假设输入资料明确支持“车辆在停车区域执行泊入”，功能为驱动控制，失效为驱动输出偏大。下面沿用这条线索说明程序如何补齐世界；假设中的距离、加速度和人员条件只用于解释计算过程，不会写入生产方法，也不能拿来替代五份输入各自的原始证据。

### 贯穿示例一：驱动异常的运行范围与对象

对这个驱动异常，程序可以检查“车辆朝前方静止对象运动”，也可以在输入允许且方法适用时检查“车辆与移动道路使用者发生交互”。这两个候选的意义不同，因为接触对象和轨迹不同。地点选择以实际允许范围为依据：通用“停车”不直接限定为多层停车场，高速道路也需有相应来源与适用条件。

在这一阶段，核对重点有三项：原文是否允许该运行条件；当前方法选项是否适用于该失效；原对象、模式或方向是否得到保留。下面的调用说明和筛选记录，分别提供对应证据。若方法没有足够证据作强匹配，程序会保留已有来源条件供后续检查；“没有选上某个模板”与“这个场景没有危险”是两件事。

### 调用入口、输入和这一步的权限

这一阶段逐个处理失效，把它与当前项目允许的来源父场景配对。父场景来自前一步整理的运行模式和 ODD，已经带有来源条件；这里是在该范围内选择方法选项。

**先收窄范围，再生成候选。** 程序逐个处理失效，取得当前功能与模式的项目范围，再生成方法分析候选。输入中的 `parents` 是有来源的父场景集合。

有 Atom 目录和项目事实时，程序进入正常的条件组合路径，人员展开留到 wf-07。缺少这两类材料时，沿用已有模板候选路径。

**各类输入各司其职。** 失效记录中的 `function_id/component_category/failure_type/functional_effect` 用于方法选择。父场景的 `operating_mode/facts/fact_provenance/semantic_fingerprint` 保存已有条件及其来源身份。方法目录 `scenario_model.scenario_method.fm_template_catalog` 提供可执行选项。

这一步的输出是带方法依据的分析候选。项目能力仍须来自有效项目证据，模板示例仅在其明确权限内使用；因果判断、风险评分和工程审核在后续各自完成。

### 筛选顺序与保守放行的准确含义

筛选分为三层：先判断失效与运行情境是否相关，再选择适用模板，最后检查模板中的每个物理选项。三个层次分别留下记录，数量变化可以回到具体决定。

**第一层：运行情境是否适用。** 情境选择服务根据有来源的功能输出、功能运行范围和规范故障类型，对每个父场景给出 `INCLUDE/EXCLUDE/UNRESOLVED`。

缺少输出证据、没有目录或存在竞争规则时，结果为 `UNRESOLVED`：保留来源场景，交由后续因果判断继续检查。明确排除则需要可执行的排除权限、获批项目约束，以及与当前项目、功能、失效和场景范围精确对应的直接证据。因此，未命中参考场景本身不会删掉父场景。

实现入口为 `MalfunctionSituationSelectionService.select`。审计保留 `records/exclusion_evidence/unresolved_passthrough_count`，分别对应逐项决定、排除依据和未决放行数量。

**第二层：是否有足够依据注入模板。** `match_fm_template` 先按关键词或受治理别名、组件类别、失效类型发现候选，再由 `_qualify_matches` 区分强匹配、弱匹配和歧义。原始首项优先序只作记录，歧义仍按歧义处理。

一般资格判断依次检查：

1. 唯一的“组件＋失效”交集形成强匹配；多个交集形成歧义。
2. 没有唯一交集时，若结构化组件与失效支持相互冲突，停止挑选模板。
3. 没有组件命中、但存在唯一“失效＋来源机制关键词”匹配时，可形成强匹配。
4. 唯一且获规范目录支持的组件模板也可形成强匹配；只有失效类型或只有关键词通常仍属弱匹配。

这个顺序优先保留明确的结构证据，并把真正的冲突留在审计中。匹配层次记为 `qualification_tier`。

另有一条受治理的工程决定路径：决定必须已经绑定当前项目，字段精确匹配，并核对获批模板及完整 option 身份。两条路径最终都要求 `FMTemplateMatchResult.injectable`，即 `STRONG_MATCH` 且模板存在，才展开“父场景×模板选项”。其余情况记录 `selection_mode=BASE_CANDIDATES_ONLY`，继续使用来源父场景。

**第三层：逐个物理选项核对相容性。** 程序检查对象与方位、数值类型和非负范围、方法词汇映射，以及选项与父事实是否一致。无效或明确冲突的选项不注入，分别保留 `INVALID_TEMPLATE_OPTION`、`validation_status=INVALID/CONFLICT` 等诊断。未映射词汇记为 `UNMAPPED_METHOD_VALUE`，保留缺口供定位。

合法选项中的距离、目标速度等按 `SCENARIO_DEFINED`、`approval=PENDING` 保存为分析条件。父对象保持原样，不同选项形成相互隔离的候选。

**两种“没有新候选”的含义不同。** 尚未强匹配时，程序保留父候选；已经强匹配、但全部 option 均无效或冲突时，方法返回空实例列表。后一种情况应从 `options/conflict_count/instance_count` 解释，不另选一个“最危险”对象填补，也不视为因果已经被否定。

### 输出身份与故障差异如何保留

每个新候选都有稳定的分析身份。指纹共同使用场景契约版本、方法哈希、MF ID、父 ID、父指纹、模板 ID、`source_option_id`、源资产哈希和实际 option facts，生成 `SCN-ANALYTICAL-…`。因此，文字相同或最终评级相同，本身都不足以合并身份。

`analysis_instance` 与逐字段来源保存模板和选项身份、原选项值、源资产哈希、适用范围及假设。这组记录把候选连回具体失效、模板选项和适用条件；不同失效或物理选项分别保留分析记录。

```text
# 字段示意，非实际对象／数值
ScenarioCandidate:
  scenario_id: SCN-ANALYTICAL-示例
  source_scenario_id: 来源父场景示例
  facts: {object_position: FRONT, object_speed_kph: 示例值}
  fact_provenance.object_speed_kph:
    provenance: SCENARIO_DEFINED
    approval: PENDING
    source_option_id: 模板示例:OPTION:1
    applicable_scope: {malfunction_id: MF-示例, scenario_id: SCN-ANALYTICAL-示例}
  analysis_instance: {malfunction_id: MF-示例, source_template_id: 模板示例, assumptions: […]}
```

本步统计分别记录基础候选数、筛选后候选数、实例数和选项数。这些是生成阶段的口径，模型请求数和最终风险数在各自阶段统计。

查证时使用 `situation_selection` 与 `analytical_scenario_instantiation` 两类审计，可以看到某个来源父场景如何进入、保留或退出。

## wf-06 在 ODD 约束内组合场景 Atom，并合并精确重复

### ODD、场景 Atom 与代表覆盖

ODD 是运行设计域，表示功能允许工作的范围；例如允许的地点、路面、天气或速度范围。Atom 在本项目中指方法目录里的一个结构化场景条件。它不只是报告中的一个词，还带着稳定身份、适用范围和方法含义，供后续暴露度 E 等计算使用。可以把 Atom 理解为“程序和方法双方都认识的一块条件”，例如一个场所条件或一种道路条件。

wf-06 把适用的条件组合成有代表性的分析候选。它不是把目录中所有条件排列组合，也不是让模型先猜一个 E 再反向挑选 Atom。组合必须先满足项目范围与条件相容性：如果原文只支持泊车运行，不能为了填满维度选入高速公路交通行为；如果某个维度对当前世界不适用，也不必随便填一项。

这一层同时回答两个不同问题。第一个是**覆盖**：是否保留了足以改变危险机制的不同条件。第二个是**精确重复**：两个来源记录是否事实上描述了完全相同的分析输入。覆盖需要保留差异，精确去重则可以减少重复计算；两者不能通过“最后评级一样”来混为一谈。

### 贯穿示例二：独立工况与重复记录的区别

沿用驱动异常的例子，假设资料中有两段文字都支持同一个前方静止对象工况。如果实际对象、方向、速度、来源权威和方法绑定都相同，只是显示文字不同，可以保留一个代表，同时记录它对应原来的两条身份。工程师仍能追查这两条来源，只是不必把同一个任务发给模型两次。

如果另一条是在坡道上、目标在车后，或者一种人员条件会影响功能使能，那么它改变了工程条件，仍按不同工况保留。还有第三种情况：两条条件不同，但有界覆盖选择只保留了其中一条。未选择的那条记录为“本轮未评估”，与已证明的精确重复分开统计。

| 观察到的情况 | 当前层应怎样解释 | 对数量统计的影响 |
|---|---|---|
| 条件及有效来源完全相同，原始 ID 不同 | 精确重复，可建立代表与别名映射 | 减少代表任务，原始身份不丢失 |
| 目标、坡向、附着或相关控制条件不同 | 保留不同世界 | 增加的记录有明确工程差异 |
| 条件不同，但本轮未选为覆盖代表 | 有界选择留下的未评估组合 | 不计为已验证覆盖或复用收益 |
| 文字不同，结构字段是否相同还不清楚 | 尚不能证明精确重复 | 不能仅凭相似描述合并 |

因此，数量统计至少区分“生成了多少原始身份”“保留了多少代表条件”“哪些组合暂未评估”。主表行数属于更下游的展示口径，应与这三个数量分别统计。

### 七维条件的有界组合与选择依据

每个已经通过检查的物理选项，进入约束场景合成服务。程序先建立当前失效的查询，再准备各维候选池、选择合法组合，最后生成具体候选。

当前基线使用七个维度：`WHERE/ROAD/EGO_ACTION/EGO_X_ROAD/TRAFFIC_PATTERN/EGO_DYNAMICS/OBJECT`。维度定义与适用性由已编译的 `scenario_model` 提供；必需、可选和不适用维度分别处理。

**候选池怎样形成。** `build_input` 使用失效、功能输出、父条件、FM 模板证据，以及已经按功能和模式收窄的项目上下文，构建语义查询。`candidate_sets` 据此形成各维候选池。

速度交集、坡度、天气、来源地点、全局复合 Atom 相容性和可执行方法约束构成硬条件。候选排序看机制及条件语义，E 等级留给后续计算，不用于倒推“更危险”的组合。

**父条件怎样保留。** 已确认且不可修改的父绑定保持原值；可细化的分析选择记录父 Atom、子 Atom、来源和细化理由。不适用维度保持不适用，七维目录不要求每条场景都填满七格。

这里的 `validate_provider_payload` 也用于验证本地生成的选择。虽然函数名带有 provider，普通确定性组合仍可在本地完成。

### 覆盖选择、来源边界与失败去向

**先满足覆盖计划，再分配来源边界。** 逻辑组合按 `coverage_plan` 保留主要变化维度及复合填充关系。一个复合 Atom 可以填多个维度，但同一 Atom 只选择一次，其他 Atom 也须避开已占用的冲突维度。

来源坡度边界通过独立 context 表达。`include_source_boundaries` 控制各物理 option 的来源锚点：先解析明确边界，再让普通来源场景代表其他环境。这样保留关键边界，同时避免将全部坡度、车位、天气和对象直接相乘。

没有合法组合时，记录 `NO_VALID_COVERAGE_ASSIGNMENT`。多来源边界 context 无解时，可以保留 `SCN-SOURCE-…` 的 `PENDING` 缺口候选；某个物理 option 未产生组合时，上层保留该 option 供后续审查，而不重新展开整个目录。

**跨来源怎样选代表。** `_select_context_representatives` 使用四类特征：主要 Atom 组合、原来源条件、WHERE、ROAD。其他不同条件组合若未被本轮选为代表，进入 `deferred_context_variants`，记录 `status=COMBINATION_NOT_EVALUATED` 和 `risk_equivalence_proven=False`。

### 精确去重比较哪些字段

精确去重比较完整的规范输入。已有 `scenario_atom_ids` 的候选，按 `signature(scenario_conditions(candidate))` 分组；尚无 Atom 身份的候选则以原 `scenario_id` 保持独立。

**实际条件与方法绑定。** 规范视图包含 `operating_mode`、实际 `facts` 和 `fact_authority`。已解析维度保留Atom身份及规范身份、填充维度、方法含义、适用状态和速度交集；未解析绑定完整保存，使不同未知条件仍可区分。

速度数值约束继续保留在 facts 中。重复的速度提取历史 `speed_context_resolution` 不参与身份，因为它不增加当前工况的实际约束。

**来源及审核性质。** 程序比较来源类别、审核状态、方法资产与契约身份，也核对分析值的含义、时间角色、单位、来源引用、适用范围、校验状态和输入事实元数据。对象身份、坐标系及故障运动模型同样参与比较。相同数值若来自不同来源范围、对象、阶段或审核状态，仍然是不同输入。

**哪些标签可以规范化。** 当前与父生成 ID、生成的目标别名、接触及轨迹局部 ID 可以一致重命名；`branch_id/semantic_fingerprint/display_label` 等身份标签可忽略。实际目标身份与实际语义仍参与比较。

```python
groups = defaultdict(list)
for candidate in candidates:
    if not candidate.facts.get("scenario_atom_ids"):
        key = candidate.scenario_id
    else:
        key = signature(scenario_conditions(candidate))
    groups[key].append(candidate)
retained, mappings = [], []
for key, members in groups.items():
    first = members[0]
    ids = [member.scenario_id for member in members]
    retained.append(replace(first, analysis_instance={
        **first.analysis_instance,
        "p6_generation": True,
        "equivalent_candidate_ids": ids,
        "equivalent_parent_ids": sorted({m.source_scenario_id for m in members}),
        "condition_signature": key,
    }))
    mappings.append({"representative_scenario_id": first.scenario_id,
                     "scenario_ids": ids, "condition_signature": key,

## wf-07 按来源与项目策略展开驾驶员配置

### 人员位置对功能与控制能力的影响

驾驶员分支不是为了让每个场景自动多出两行。它是把人员条件明确放进分析：驾驶员坐在驾驶位、在车内但不在驾驶位、在车外，这些情况对应的可用控制可能不同，也可能影响功能是否允许启用。程序按当前输入和适用策略展开配置；具体允许车内还是车外操作，由各项目来源确定。

沿用驱动异常例子，车辆不受干预时的运动轨迹可能相同；但坐在驾驶位的人是否能通过独立踏板制动，与站在车外的人能否发送远程停车命令，是两个不同问题。即使制动执行器没有故障，也不等于任何位置的人都能控制它。需要继续检查控制入口是否存在、是否在当前故障下仍可用、响应是否来得及。

### 贯穿示例三：共有运动与不同人员控制

如果本项目确实支持两种人员条件，程序可在物理方案中共用“车辆向前加速接近对象”这部分，并分别记录两种人员配置的控制条件。这样有机会减少重复方案请求，同时仍保留两种情况下各自的因果判断、可控性和响应结果。

但共享有边界。例如，某个故障只有在远程操作模式才会触发，或者驾驶员在座时系统根本不会使能，那么人员变化已经影响危险形成。此时完整因果结论需要按新人员条件独立核对。后续会根据依赖证明判断能复用哪一段；证明不足就分别判断，仍可共享已有证据，避免重复读取同一批资料。

本步先明确：**来源允许哪些位置 → 当前父场景是否已固定位置 → 位置能推出哪些事实。** 随后在 wf-08 的物理与控制分析、wf-09 的具体因果调度中，继续核对当前故障下有哪些控制路径，以及哪些结论有充分依据复用。报告中“驾驶员在车外”的表述，沿用前面已经建立的来源和推导。

### 人员配置从哪里来，什么时候不展开

完成条件去重和来源焦点分配后，程序读取候选、项目中性的 `risk_facts` 和有效项目政策，决定允许展开哪些人员配置。

**展开的前提。** 政策先经过 `effective_project_policy` 筛选。项目事实、有效 policy ID，以及来源有效且已 `FINALIZED` 的 `DRIVER_IN_VEHICLE` 允许配置都具备时，才形成相应分支；缺少其中的必要条件时，保留原候选。

位置由 `allowed_position` 从 `context.allowed_driver_position` 或原文支持的“在驾驶位／不在驾驶位”解析。布尔或数值编码表达成员状态，不额外代表一个地理位置。

**范围如何匹配。** `_scope_matches` 将允许位置标签以外的 context 约束，与当前 `facts/operating_mode/scenario_id/parent_scenario_id/malfunction_id` 逐项比较。只有适用于当前模式、失效及条件的允许集合参与展开。

父场景已经固定位置时，只核对该位置。固定位置若不在项目允许集合内，程序保留原身份，记录 `SOURCE_CONFLICT`、`driver_configuration_source_conflict`，并清除不可靠的位置布尔推导；不会改换成另一个人员配置。

    by_position: dict[str, list[tuple[str, SourceRef]]] = {}
    for fact in risk_facts:
        if not isinstance(fact, dict):
            continue
        if str(fact.get("parameter", "")).upper() != "DRIVER_IN_VEHICLE":
            continue
        if str(fact.get("approval", "")).upper() != "FINALIZED":
            continue
        position, context = self.allowed_position(fact)
        if not position or not self._scope_matches(context, scenario):
            continue
        for source in self._source_refs(fact):
            by_position.setdefault(position, []).append((
                str(fact.get("fact_id", "")), source,
            ))
    if not by_position:
        return (scenario,)
```

代码中的 `FINALIZED` 修饰来源位置事实。`_scope_matches` 继续匹配当前模式与条件，`_source_refs` 保留原来源。通过准入后，后续代码才核对父位置、建立新身份并应用已经绑定项目的位置约定。

这一步确定允许的人员分支。人工制动能力 `driver_braking` 在后续控制分析中单独核对：人在车内，仍需证明能够操作踏板；不在驾驶位，仍需独立证据区分在车内或车外。

生产回归分别检查适用人员集合的展开、驾驶位与车辆内外位置的区别，以及位置证据不足以证明踏板可用的反例。

## wf-08 形成可计算工况，实例化物理分支并求轨迹

### 从危险描述到可计算物理工况

“驱动异常可能撞上前方对象”描述了危险主张，却还不能计算。程序至少需要知道起始运动状态、目标相对位置、故障后如何运动，以及相应模型需要的几何条件。wf-08 的目的，就是在已有事实和方法范围内，把这些信息整理成同一对象、同一阶段、同一坐标下的可计算工况。

这里有两类工作。模型负责提出并解释分析假设，例如采用哪个已有运动模型、选择什么代表距离、剩余哪些控制；Python 负责检查这些内容是否相容，再按方程计算。最终风险等级由程序依据活动方法计算，工程批准沿用独立的审核记录。已有来源或规则足够时，程序直接用现有输入，不需要重新请模型编一遍。

本章中的“世界”是对一个完整工况的简称：同一时刻的车辆和对象、相对位置、运行条件，以及接下来假设的运动。计算输入因此应始终对应同一工况中的距离、速度和控制能力。

### 贯穿示例四：条件性假设与确定性求解

下面仍讲驱动异常，但**另用一组教学参数展示求解过程**，与前文“2秒接触”的例子分开：初速为 1 m/s、故障后恒定净加速度为 1 m/s²、到前方静止对象首次接触还有 5 m，目标确实位于该运动路径上。这是一组完整但条件性的输入，不是车辆实测能力，也不是生产默认值。

Python 使用 `5 = 1 × t + 1 × t² / 2` 求首次正时间根，得到约 2.32 s；接触速度约为 3.32 m/s，即 11.94 km/h。此处展示值经过舍入，实际程序保留计算精度。接下来验证该失效是否确实导致所假设的车辆行为和接触，再由活动方法计算S/E/C及ASIL。

如果加速度只知道范围，程序可以在有限的代表点和边界点上计算，保存每次计算的参数。如果加速度只能保留符号 `a`，那么可保存 `v_contact² = v0² + 2ad` 这样的关系及适用条件，原先故障前的加速度则保持其原阶段含义。两种输出都可提供分析价值，但含义不同：一个是“在这些数值假设下的结果”，另一个是“结果如何随未确定参数变化”。

### 物理阶段的输出及下游用途

| 产物 | 它回答的问题 | 后续怎样使用 |
|---|---|---|
| 原始方案与假设依据 | 为什么选择这个对象、模型和参数 | 审核假设合理性，复查来源限制 |
| 当前模型输入视图 | 本次究竟使用哪些父事实、哪些新假设，排除了什么旧值 | 防止对象、阶段、单位和坐标串用 |
| 轨迹与接触结果 | 是否接触，何时接触，以什么速度接触 | 给具体场景因果检查和风险计算提供输入 |
| 参数敏感性与未取点说明 | 哪些取值已算，哪些范围还未证明 | 避免把少量计算点说成连续范围保证 |
| 控制与响应诊断 | 当前响应是否有适用控制，能否达到所提状态 | 支持后续 C、Safe State 和 FTTI 的各自检查 |
| 子身份及父身份映射 | 这条具体工况从哪条来源、哪个方案形成 | 恢复运行、关联明细和定位报告问题 |

这些产物出现于风险评分之前，但其中关于响应的计算也会被后续评分与报告链复用。**物理可计算、因果成立、评级有值、工程批准是四个不同层次。** 例如，几何有效但响应无法避碰，是一个有意义的工程结果；结论始终基于原距离及有依据的制动能力，失败轨迹本身也是审核材料。

### 入口：先使用已有权威，再选择三条任务路线

人员条件展开完成后，程序先检查已有输入能否直接使用：绑定当前项目和方法中的物理事实，区分正常运行速度与故障后运动速度，并在适用时使用受治理的代表运动规则。已经建立的自主物理假设继续保留，不再被模板默认值覆盖。

随后选择本次任务范围。缺运动条件时补完整方案，运动已知时只补控制和响应，所需内容已评估时直接继续。三条路线最终都进入同一个物理计算服务。

| `task_scope` | 触发与输入 | 本次处理 |
|---|---|---|
| `MOTION_AND_CONTROLS` | 现有碰撞／运动输入尚不能建立来源有效的当前轨迹 | 提出模型、几何、点／范围／符号参数和剩余控制；保留有依据的初态、目标及来源约束 |
| `CONTROL_INPUTS_ONLY` | 已有运动可复用，活动方法所需控制／人员声明未评，或需要补同一运动的响应 | 保持轨迹、对象、速度和坐标，只评当前范围的控制与响应；生成受父身份绑定的控制实例 |
| 空字符串 | 已有作用域有效的完整评估，或现有规则足以回答所需输入 | 沿用当前工况进入因果阶段，无新增物理／控制请求；明确 failed/unknown 也属于已完成的评估 |

C 尚无数值时，要先看缺口性质。合法无接触、符号关系、已明确未知和方法不适用，可以保留 Pending，并复用已经完成的分析。若旧方案只评了通用 `braking` 执行器，却未评所需 `driver_braking` 人工入口，则只补控制部分，已有运动继续使用。

### 哪些工况可以共用方案，程序怎样识别同一请求

程序先按**相同任务范围、相同规范化物理条件**分组。这种组在代码中称为“物理家族”。它共享的是尚未施加避险响应时的故障运动提案，不是所有成员的最终风险结论。目标、坐标、速度、模型、来源权威或有效期不同，就不能因为描述相似而直接并为同一任务。

人员条件也不能一概删除。共同运动条件可以与完整驾驶员配置分开传递；但如果驾驶员具体位置未知，输入又明确说明人在车内或车外，这个存在条件仍保留在共同物理输入中。否则，分组时就可能把不同的运行条件错误合并。

| 用途 | 对应字段或实现 | 阅读时应注意什么 |
|---|---|---|
| 识别可以共用提案的组 | `_physical_families` 使用 `task_scope` 与 `physical_conditions(candidate)` 的签名 | 相同失效编号本身不足以证明输入相同 |
| 提取共同物理条件 | `physical_conditions` 调用 `scenario_conditions(..., without_driver=True)` | 特定的 `driver_in_vehicle` 存在条件仍会保留，并非删除全部人员信息 |
| 保留各人员分支 | `driver_configurations` | 共用运动提案后，各成员仍须使用自己的控制条件 |

分组以后，实际请求还需要带上功能、来源、方法和版本等信息。这些内容一起决定 `plan_key`，即完整请求输入的签名。它不是仅对失效编号或父场景编号做哈希。这样，相同编号下的来源、方法或提示语义发生变化时，就不会误读成旧任务。

| 请求内容 | 对应字段 | 为什么需要它 |
|---|---|---|
| 当前分析对象及项目依据 | `malfunction`、`function`、`project_context`、`project_physical_facts` | 区分分析哪个功能失效，以及采用哪些项目条件 |
| 方法、控制输入和分析用语 | `method_identity`、`method_version`、`intervention_inputs`、`risk_vocabulary` | 区分适用方法和本次可判断的控制条件 |
| 执行策略、输入状态及版本 | `analysis_strategy`、`model_input_status`、`producer_version`、`model_catalog_identity`、`prompt_version`、`route` | 防止不同策略、模型目录或提示版本错误共用结果 |
| 完整运动任务的候选范围 | `source_condition_focus`、`operating_atom_options`、`object_focus_options` | 限定来源条件和可选对象；控制任务则使用对应的控制请求版本 |
| 可追溯来源片段 | `_source_evidence` 选择的原文块 | 按任务选取踏板、退出、自动停车、故障处理和接口等证据，缩小请求但不改写原文 |

生成签名后，程序把 `plan_key` 写入保存的 `context`，供实例化时核对请求身份。

### 结构校验、继承与真实实例身份

模型交回方案后，程序先检查“写法是否符合契约”，再检查“这些输入是否属于当前工况”。两层检查不能互相替代：JSON及字段正确，不代表某个旧值就可以用于新对象、新阶段。方案状态为 `VALIDATED` 只表示通过相应契约校验，**不表示其中的车辆能力或分析假设已经获得工程批准**。

继承父场景输入时，程序同时核对当前失效与场景来源、单位、坐标、模型、对象和时间含义。例如，接触时的速度不能直接成为新轨迹的初速；前一个目标的距离不能成为新目标间距；故障前加速度也不能成为故障后净加速度。真正适用的父值可以继续使用，不适用的值保留排除原因，而不是删除历史资料或补一个默认值。

| 检查内容 | 字段或代码 | 失败或保留结果 |
|---|---|---|
| 方案是否符合约定结构 | 模型枚举、精确字段、单位、证据 ID、条件和控制依赖 | 先通过结构检查，才能进入后续实例化；结构合法不等于工程批准 |
| 运动假设数量及任务范围 | `hypotheses` 为0～3项；`uncovered_conditions` | 控制补评不得同时带运动假设；空方案必须说明具体未覆盖条件 |
| 控制、目标状态和时间放在哪一层 | 运动 `hypothesis` 内的控制、Safe State 和时钟；`control_assessment` | 运动假设直接携带这些内容，不再嵌套另一份控制评估 |
| 父值能否用于当前模型 | `_model_inputs`、`_inheritance_reason`；故障前阶段 `PRE_FAULT` | 不适用的继承值记录 `EXCLUDED_FROM_ACTIVE_MODEL` 及原因；不将故障前加速度当作故障后净加速度 |
| 必需输入是否齐全 | 当前模型必需字段；`REQUIRED_MODEL_INPUT_OMITTED` | 既未合法继承、又未声明的必需输入进入已有有限纠正，不制造默认值 |
| 参数是否被所选模型使用 | `MODEL_CATALOG`、`PARAMETER_UNITS` | 模型目录决定必需参数；单位表列有该字段不代表所有模型都使用它，误带参数可触发 `PARAMETER_NOT_USED_BY_MODEL` |
| 符号输入是否保持符号 | `SYMBOLIC` | 主动移除对应旧数值，避免声明符号后仍从父数据算出伪数值 |
| 新初态或新目标是否形成了新工况 | `condition_changes.initial_state`、`condition_changes.target` | 相应替换目标身份，核对条件单元（Atom）及来源约束；不能在同一身份上静默覆盖事实 |
| 对象、初速或人员范围变化后，方法条件是否同步 | `_object_binding`；`OBJECT`、`EGO_DYNAMICS`、`EGO_ACTION`；`operating_atoms`、`driver_operating_atoms` | 重新核对适用条件并更新 `method_scenario_dimensions`、`scenario_atom_ids`、`dimension_bindings`，而不是只改中文描述 |
| 新对象的暴露条件是否有对应依据 | `physical_object_exposure_conditional`、`physical_object_exposure_unresolved` | 新对象与原对象绑定不同时保留条件性标记；无法建立绑定时保留未解决标记，不借旧对象的 E 补空 |

检查通过后，程序为实际运动取点或控制补评建立子身份，同时保留父对象。新实例状态仍为 `PENDING`。下面的身份和证据字段，使报告中的结果能够追溯到具体方案、参数点和来源：

| 记录 | 身份或保存字段 | 用途 |
|---|---|---|
| 运动子实例 | PH 哈希使用 `parent`、`plan`、`hypothesis`、`point`；必要时加入严格验证的 `request_driver_scope`，形成父 ID 后缀 `-PH-…` | 区分不同方案、假设、取点及必要的人员范围 |
| 控制补评子实例 | CTRL 哈希使用 `plan`、`assessment`；必要时加入唯一请求驾驶位，形成父 ID 后缀 `-CTRL-…` | 保留原有运动，区分本次控制评估及其人员条件 |
| 两类实例的共同证据 | `physical_analysis` 或 `control_analysis` 中的 `plan_key`、`hypothesis_id`、`parent_scenario_id`，以及原假设、输入来源和条件性说明 | 将子实例连回请求、方案和父场景 |
| 运动实例的额外证据 | `sample_parameters`、`sensitivity`、`model_input_view` | 保存实际取值、敏感性信息和本次真正使用的模型输入 |

对象、速度和控制条件会影响风险，但这里的工作是形成一致的计算输入，**不是先选定 S/E/C，再倒推一组能得到它的参数**。评级由后续评分步骤执行。

### 模型方程、坐标与适用条件

当前自主模型分别处理直线加速、溜坡、横移、圆弧转向，以及与移动对象接触。选择模型时，运动关系与适用条件一起核对。

圆弧转向描述车辆沿曲线行驶；横向恒加速度描述独立横移或侧滑。二者都可能发生侧面接触，但正常转弯的法向加速度不代表侧滑加速度。坡道则还需车头和下坡方向，才能把坡度幅值转换成前溜或后溜，并判断哪一侧目标会被接近。

**单位与坐标。** 计算将 km/h 除以3.6换为 m/s，统一使用距离 m、时间 s、加速度 m/s²。`BODY_FORWARD_POSITIVE` 规定初始车体 x轴向前、y轴向左；目标中心偏移带符号。方向角从+x朝+y计，表示固定速度方向，车轮转角是另一物理量。

有限接触中的 `contact_half_length_m/contact_half_width_m` 是双方投影半尺寸之和，需要对应输入依据。静止沿程模型的 `relative_distance_m` 则表示到首次表面接触的剩余行程，区别于两个对象的中心距。

| 模型 | 程序关系 | 使用前提与适用边界 |
|---|---|---|
| `CONSTANT_ACCELERATION_TO_IMPACT_DISTANCE` | `d=v0*t+a*t²/2`、`v_contact²=v0²+2*a*d`，稳定根求首次接触 | 静止目标在运动路径上，停止后保持不反向。显式剩余独立限速可形成加速／限速分段；正常运行上限与故障限速分别处理 |
| `GRADE_ROLLAWAY_TO_IMPACT_DISTANCE` | `a=max(0,g*sin(atan(p/100))-r)` 后使用沿程方程 | 从静止开始，坡度p为百分比，r为残余阻力；须明确重力与车头／下坡坐标。阻力足够时不启动，目标须在下坡路径上才可能接触 |
| `CONSTANT_LATERAL_ACCELERATION_TO_CONTACT` | `w=vy0*t+ay*t²/2`，x恒速，接触合速度按 x/y 分量求范数 | 适用于独立惯性横移／侧滑与延展静止侧边界；正常转弯法向加速度不在此范围，本模型不派生纵向TTC |
| `CONSTANT_SPEED_CURVATURE_TO_CONTACT` | `theta=v*t/R`、`y=R*(1-cos(theta))`，`a_normal=v²/R` | 恒速无侧滑圆弧，求解限于显式时域或首个四分之一圆；方向、半径和目标侧相容。假设半径保留其条件性，不作为车辆能力上界 |
| `RECTILINEAR_MOVING_TARGET_CONTACT` | `r(t)=offset+u_hat*s_target(t)-v_hat*s_ego(t)`；分段 `s=v0*dt+a*dt²/2`；首次同时 `abs(x)<=hx`、`abs(y)<=hy` | 固定方向和固定投影有限包络，自车恒加速度；目标恒速或在明确反应后制动至停，随后保持静止。时变转向和旋转包络超出该模型范围 |

**各模型的补充几何条件。** 圆弧可成对提供 `object_offset_x_m/contact_half_length_m`，核对固定有效纵向区间是否覆盖接触点。没有该区间时，结论依赖延展边界假设；接触点落在区间外时，返回几何不适用，结论范围限于当前几何。

直线移动模型可以用 `grade_frame` 从静止推导坡度运动，并用 `post_stop_motion=HOLD_POSITION` 检查自车停住后，目标是否继续进入包络。受治理规则产生的 `CONSTANT_SPEED_REPRESENTATIVE` 属于已有确定性输入路径，不在 Agent 可选的上述五模型目录中。

**求根前检查。** RECTILINEAR要求有限正包络、有效时域、非负速度，以及位置标签与偏移符号一致。例如 LEFT对应目标初始y为正。初始包络已重合时返回 `INITIAL_CONTACT_REQUIRES_SEPARATE_PHASE`；位置符号矛盾时返回 `TARGET_OFFSET_POSITION_CONFLICT`。

目标的 `object_reaction_time_s/object_braking_deceleration_mps2` 成对提供，并满足有效反应及制动条件。缺少其中字段时，保留输入／几何诊断，由后续定位补全；计算器不将其自动解释成普通人的反应能力。

### 点值、范围与符号参数的展开及结果范围

同一个参数可以有三种表达方式：`POINT` 给出代表值，`RANGE` 同时保存 `lower/value/upper`，`SYMBOLIC` 保存符号、条件和理由。三者分别表示当前知道的内容，符号参数继续保留符号形式。

**怎样选择有限计算点。** `_samples` 先使用代表点，再按单因素范围端点、活动方法分档边界及邻接区域取点。机制与参数点共同使用 `MAX_INSTANCES_PER_PLAN=3` 个槽位，保持有限展开，不做多参数笛卡尔积。

没有实际取到的点列入 `deferred_points`。`parameter_relations` 保存可解释的符号关系与已知输入；`boundaries` 则从活动方法表读取边界，再反解相应物理参数，继续使用同一评分方法。

```text
# 非JSON、非真实取值，仅展示三种参数字段；模型还须携带其余必需参数
parameters:
  - {field: ego_speed_kph, kind: POINT, unit: km/h, value: <代表初速>, rationale: <来源或条件依据>}
  - {field: longitudinal_acceleration_mps2, kind: RANGE, unit: m/s2,
     lower: <下界>, value: <代表值>, upper: <上界>, rationale: <故障阶段范围依据>}
  - {field: relative_distance_m, kind: SYMBOLIC, unit: m,
     symbol: d, rationale: <当前目标初始行程未能量化及适用条件>}
# 不把<代表初速>等占位符发送给Provider；这里仅解释契约形状。
```

**结果能说明到什么范围。** 同一工况的距离若仍为符号，仅知道净加速度范围，仍不足以形成数值接触速度；此时保存参数关系和适用条件。

样本内最大S或最高ASIL只描述已计算的样本。记录继续保留 `range_invariance_proven=False/vehicle_upper_bound_proven=False/deferred_points_evaluated=False`，分别说明尚未证明连续范围不变性、车辆真实上界和未取点结果。

未知、零速度、停止前无接触及模型不适用各有自己的结果状态。存在独立环境输入时，E仍可计算；S或C尚无值不会自动清空有效的E结果。

### 当前世界、接触分支与反事实检查

**先计算当前轨迹。** 程序保存运动结果、自车与目标的接触速度、相对速度，以及首次接触时间。实际位移轴满足纵向条件时，再派生 `ttc_s`。

接触表面的 `SIDE` 标签和运动方向分别处理。目标整条轨迹速度恒零时，即使方向标签为 RIGHT，`0×RIGHT` 仍是零向量；原标签保留，合法计算副本使用静止方向。真实横移、初始静止后开始运动，以及其他对象或阶段，不满足这项等价证明。

实际接触形成后，程序生成有限碰撞成员，保存分支、危险机制和接触阶段的身份，以及物理可行性。成员来自当前计算交互，不从全对象目录额外补一个“最大危险”。

**再检查一个明确范围的反事实。** 当前实现对 RECTILINEAR且自车初速为0的工况，复制同一 facts，把 `longitudinal_acceleration_mps2` 改为0，计算 `stationary_ego_counterfactual`。

如果同一目标仍会接触静止自车，加入 `CONTACT_WITH_STATIONARY_EGO` 诊断。后续需说明故障带来的增量危险，或提出有依据的不同目标路径。这个结果用于提示因果问题，不自动否定故障，也不代表已经模拟全部正常运行。

原工况与反事实分别保存；后续因果节点继续逐跳检查 M→B→I→H。

**避让响应使用独立计算副本。** `moving_target_avoidance` 要求识别延迟、速度、净空和带参数的有限过渡。反向需要实际过渡时间；跨轴转向仅在已有模型支持时评价收益。该计算回答当前对象能否离开接触包络，C等级由后续活动方法决定。

Safe State提案同样核对剩余控制、实际响应轨迹和故障时钟，保存有效时间窗口、即时响应不安全或缺少控制的诊断。响应可算说明存在可分析的提案；其检测和触发是否已经实现仍需相应依据。原始未干预故障风险继续保留。

### 一次有限纠正与失败后的原样保留

纠正用于处理本次任务中可明确指出的问题。一个方案若在三个参数点上都出现同样的方向冲突，工作流汇总共同原因，让原方案接受一次受限语义纠正，保留三个参数点的身份映射。

**纠正前先保存现场。** 家族中的所有成员完成实例化后，共同汇总几何或相位冲突、未评人工或自动命令、不可达响应、缺故障时钟及反事实诊断。各成员共用**一次**语义纠正机会。

程序保存 `initial_plan/correction_diagnostics/instantiations`，设置 `CORRECTION_REQUESTED`。纠正请求带上 `previous_plan` 和程序计算出的中性差异反馈。Schema结构修复与这次语义纠正分别计数，所有网络请求仍计入同一预算。

**纠正范围由当前任务决定。** `PhysicalScenarioPlan.validate_correction_scope` 核对返回是否保持已经有效的轨迹和工况。例如只补控制路径时，目标和距离继续固定。

返回无效时，保留原有有效运动和局部缺口，记录 `PHYSICAL_CORRECTION_INVALID_ORIGINAL_RETAINED`。合法返回则由同一个 producer重新实例化。

仍未生成结果或模型不适用时，保留原候选并附上 `physical_plan_diagnostics`。解析或实例化失败记录 `INVALID`、原响应和错误，后续按实际缺口处理。

已撤回响应由 `_retain_rejected_response` 保留历史，并按当前严格范围重验。历史负面结果、当前有效提案和当前计算状态分别保存，报告据此说明发生了什么。

### 未完成结果的原因分类与处理责任

“未完成”可能来自资料、输入传递、模型范围或返回结构等不同环节，处理责任如下。逐类定位后，再选择补查来源、修正传递、调整适用模型或有限修复返回等处理。

| 实际状态 | 例子 | 应保留的结论与下一步 |
|---|---|---|
| 产品事实缺项 | 原文没有说明故障后某个命令通道是否仍独立可用 | 标明能力未获来源确认；可按合法条件性假设分析，结论保留未确认能力的范围 |
| 动态参数尚为符号 | 模型给出了加速度 `a` 的关系，未形成可信数值范围 | 保存参数化关系和影响条件，不从旧阶段补回一个数值 |
| 新旧输入冲突 | 初始静止的有效条件与新方案初速不一致 | 指出冲突对象和阶段；合法新条件要重新实例化身份与绑定 |
| 物理模型不支持 | 当前任务要求模型目录以外的时变转向轨迹 | 记录具体模型范围缺口，保留原目标运动条件 |
| 合法无接触 | 在给定时域和轨迹内，两个包络没有相交 | 保留适用时域、条件及无接触结果，结论限于当前计算范围 |
| 响应确实不能避碰 | 已有控制按给定延迟执行，仍与同一对象接触 | 保存原距离、目标和控制能力下的失败轨迹与诊断 |
| 返回结构错误 | 缺必需字段、单位不合法或引用了不存在的证据 | 保存原始响应，按现有有限结构修复处理，并统计请求成本 |

### 缓存恢复、当前派生视图与因果失效

缓存保存已经完成、且仍适用于当前输入的工作。是否可以复用，要比较方案输入、方法版本、提示契约和人员条件；同一失效编号下也可能存在不同任务。

**方案缓存怎样恢复。** 缓存保存请求上下文、方案、原始响应、实例化结果和响应校验版本。同校验版本下已经失败的记录保留结果，不在每次resume重复请求。校验版本变化时，先使用已保存的原始raw响应重验，合法旧方案可以零新请求恢复。

新提示、目录或真实输入语义发生变化时，任务身份随之更新。`VALIDATED` 方案仍要在家族的每个成员上实例化；共有方案与各驾驶员的具体判断分别处理。

**当前物理视图怎样传到下游。** `scenario_with_current_physics` 对已保存的直线移动接触结果使用同一个来源校验 materializer。内容无变化时返回原candidate；有变化时使用计算副本，原来源事实保留。

直接PROJECT事实与派生值冲突时报告错误；同值直接事实继续保留其原来源。这使派生视图的修订与项目事实的权威保持一致。

后续 `exact_task_key`、`_scenario_json` 和 parser读取相同的当前视图。例如 `longitudinal_contact` 从false修订为true时，请求及身份都反映新条件。输入、对象、条件或来源确实变化的，重验受影响因果；仅数值相同不足以继承已有批准。

**输出和计数。** 本步把带来源与条件说明的子场景、碰撞成员及完整诊断交给 wf-09。最终S/E/C随后计算。

检查效率时，分别统计方案请求、缓存命中、生成实例、确定性求解点、运动方案复用、控制方案复用和语义纠正。各项计数保留自己的口径。

### 实现例 P03｜已求出的运动为什么只补控制，而不重新请求整个物理方案

程序先把任务范围和规范物理条件相同的候选放在一组，再检查该组缺什么。已有完整评估时不增加请求；运动已知时只补缺失控制或响应；运动尚未建立时再请求完整方案。

| 返回值 | 对应处理 |
|---|---|
| 空字符串 | 无需新增方案任务 |
| `CONTROL_INPUTS_ONLY` | 只补控制与响应 |
| `MOTION_AND_CONTROLS` | 建立完整运动方案及控制条件 |

调用中，`construct_physical_scenarios` 通过 `_physical_families` 分组，再由 `producer.task_scope` 判定范围。下面是判定函数的前半段。

<!-- source-example: src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py:L135-L160 -->
```python
def task_scope(self, candidate, malfunction_id):
    """Retain solved motion; assess its controls and response once."""
    scope = dict(malfunction_id=malfunction_id, scenario_id=candidate.scenario_id)
    for key in ("control_analysis", "physical_analysis"):
        if candidate.facts.get(key) and source_is_accepted_for(candidate.fact_provenance.get(key, {}), **scope):
            h = candidate.facts[key].get("hypothesis", {})
            if ("driver_in_vehicle" in self.intervention_inputs
                    and candidate.facts.get("driver_in_vehicle") is None
                    and not self.driver_position(candidate) and len(h.get("driver_positions", [])) != 1
                    and "driver_in_vehicle" not in h.get("unresolved_controls", {})):
                return "CONTROL_INPUTS_ONLY"  # Legacy omission; retain motion, assess the missing condition once.
            contact = candidate.facts.get("motion_model_outcome", {}).get("status") == "CONTACT" or bool(candidate.facts.get("collision_branches"))
            if contact and self.manual_path_gap(candidate, h, malfunction_id):
                return "CONTROL_INPUTS_ONLY"
            return ""  # An assessed limitation is not another request on resume.
    # A validated symbolic/no-contact world may intentionally have no
    # collision branches. Reuse its assessment rather than proposing the
    # same world again just to manufacture a numeric contact.
    if not (candidate.facts.get("collision_branches") and
            source_is_accepted_for(candidate.fact_provenance.get("collision_branches", {}), **scope)):
        return "MOTION_AND_CONTROLS"
    if self.method.metadata.get("project_analysis_policy", {}).get("timing_analysis"):
        # C readiness does not establish a reachable safe state or a timed
        # response. Existing source/method motion needs the same assessment
        # already requested by the autonomous motion path.
        return "CONTROL_INPUTS_ONLY"
```

这段代码体现两种请求节省：已经评估出的限制在恢复时继续使用；已有合法碰撞分支而需要响应分析时，只进入控制补全。

调用前仍核对当前场景和MF的来源范围。方法没有配置时间分析时，函数后半段还会根据C的实际输入就绪情况继续判断，因此完整入口需结合后续代码阅读。

冻结回归验证已有运动补完控制后，恢复不增加请求；合法无接触或符号工况也可保留已有评估，其他MF则保持独立。测试证明的是这些固定输入的调度行为，其他任务仍按自身诊断使用必要的纠正机会。

### 实现例 P04｜新方案的符号输入如何阻止旧数值被补回

缺口展示和真正实例化使用同一套输入规则。`instantiate` 与 `input_status` 都调用 `_model_inputs`，所以模型看到的缺口与计算器最终使用的输入能够对应。

下面截取参数遍历主体。`explicit` 来自当前方案明确给出的参数，`allowed` 来自当前模型的必需与可选字段。

<!-- source-example: src/hara_agent/services/analysis/physical_hypothesis_instantiation_service.py:L417-L437 -->
```python
values, audit = {}, {}
for field in PARAMETER_UNITS:
    if field in explicit:
        parameter = explicit[field]
        if field not in allowed:
            raise PhysicalInputConflict("PARAMETER_NOT_USED_BY_MODEL", field, None, parameter)
        audit[field] = {"action": parameter["kind"], "parameter": parameter}
        if parameter["kind"] != "SYMBOLIC":
            values[field] = parameter["value"]
    elif field in parent.facts:
        accepted, reason = self._inheritance_reason(parent, h, field, malfunction_id)
        value = parent.facts[field]
        if not isinstance(value, (int, float)) or isinstance(value, bool) or not math.isfinite(value):
            accepted, reason = False, "PARENT_INPUT_NOT_FINITE_NUMBER"
        if field not in allowed:
            accepted, reason = False, "PARAMETER_NOT_USED_BY_MODEL"
        audit[field] = {"action": "INHERITED" if accepted else "EXCLUDED_FROM_ACTIVE_MODEL", "reason": reason,
            "parent_value": parent.facts[field], "parent_metadata": deepcopy(parent.fact_provenance.get(field, {}))}
        if accepted:
            values[field] = parent.facts[field]
return values, audit
```

**先处理新方案，再判断继承。** `if field in explicit` 与 `elif field in parent.facts` 互斥。新方案明确声明 `SYMBOLIC` 时，程序写入审计并保留符号，不再走父值继承分支。

没有显式新参数时，才核对父值的对象、阶段、角色、坐标、模型范围及数值有效性。返回的 `values` 进入同一物理计算链；`audit` 保存继承或排除理由，父事实仍保留。

反例的父场景保存故障前加速度2 m/s²，新方案将故障后 `a_fault` 声明为符号。预期结果是保持符号关系，不生成唯一碰撞速度和TTC。

正例的新方案未填写加速度，而父值确属本车、故障后阶段和当前模型。此时允许继承并计算。

范围取点和敏感性由 `_samples` 后续处理。当前输入继承检查只说明哪些值适用；连续范围不变性与假设的工程审核仍分别保留状态。
