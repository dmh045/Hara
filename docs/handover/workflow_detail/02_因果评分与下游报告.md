# 工作流详解（二）：因果资格、风险评分与下游报告

本章对应当前工作流的 `wf-09` 至 `wf-12`，按生产执行顺序展开。代码依据为 `d6a400e7010d62ff5dda56efd8215f23729bb3ec`；交接文档更新未改变本章引用的 `src`、方法资产和报告资产。结果、剩余问题及耗时分别按AVP、IPA-High、IPA-Main、RPA、rTPA五份输入的最新修订证据解释，不跨项目混用统计口径。总体证据与批准边界见 [验证结果与已知限制](../07_验证结果与已知限制.md)。

这四步的实际顺序是：**带来源的物理实例 → 因果资格判定 → 保留队列的缺失风险事实解释 → 同一危险分支评分及时间审计 → SG 汇总 → 发布门禁 → 报告投影与模板渲染**。FTTI 在物理响应校验、评分审计、SG 候选检查和报告投影中均可能被求值，各处调用同一个输入组装器和执行器；并不存在“先生成 SG 才开始计算 FTTI”的独立算法。

## wf-09 逐身份验证因果，并区分保留、排除与未决

### 因果验证的职责：判断当前失效是否形成危险

上一步解决的是“在这一组条件和假设下，车辆与对象会怎样运动”。本步接着问：“这样的运动与我们正在分析的功能失效之间，是否有说得通、能追溯的因果关系？”两者都需要，但回答的问题不同。

例如，某条轨迹计算得到自车与行人接触。接触可能是故障车辆加速造成的，也可能是行人原本就会走到静止车身上。后者至少不能仅凭“发生了接触”证明当前驱动故障导致危险。因此，程序不能把物理计算结果直接转换成一条有效 HARA 风险；还要核对功能当时是否在作用、故障是否改变了相关行为，以及危险是否由这个变化形成。

本步产出**逐条核验的因果交接记录**。满足交接条件后，才把该身份送去补评分事实、计算风险等级；不成立和没有判断清楚的身份也会留下记录。它们不会因为不进入主表就从审计中消失。

| 本步用语 | 通俗解释 | 为什么要单独记录 |
|---|---|---|
| 物理可行 | 这个对象关系和运动过程在当前模型内是否成立 | 不能分析一个与几何或物理输入矛盾的世界 |
| 功能相关 | 该功能在这个工况下是否参与车辆行为 | 功能没有参与时，不能只因失效名称像就认定有关 |
| 因果相关 | 功能失效是否确实把行为推向所述危险事件 | 有碰撞可能性，不等于当前失效对它有作用 |
| 危险事件 | 某种危险行为在具体运行工况下形成的事件 | 需要说明“谁、在什么条件下、与谁发生什么交互” |
| 保留 | 证据与契约满足后续评分资格 | 是进入评分的资格，不是工程师已批准最终结论 |
| 排除 | 已有有效依据说明这条因果链不成立 | 应能解释断在哪一环，不能用缺信息作为排除理由 |
| 未决 | 当前还没有足够的有效判断或交接尚未完成 | 必须与“安全”“无风险”和“已排除”区分 |

### 三跳因果的分析示例

以下只解释数据怎样流转，不是五份输入中新增加的分析记录，也不指定实际 S/E/C 等级。假设上游形成了这样的条件性工况：车辆正在低速泊入，驱动指令异常增大，前方有静止车辆；物理模型已经按所声明的初速、加速度和距离算出了接近轨迹。

1. **失效 → 行为变化（M→B）：** 驱动指令异常增大，是否会让当前车辆产生非预期加速？需要功能和控制关系证据，不能只复述失效标题。
2. **行为变化 → 运行后果（B→I）：** 这次加速在当前行程、方向和目标位置下，是否使自车接近前方车辆？需要当前物理实例，不能拿另一参数点的轨迹代替。
3. **运行后果 → 危险事件（I→H）：** 此接近关系是否形成所描述的碰撞危险？要核对真实对象、接触阶段和故障的作用，不能因为父场景写过“可能碰撞”就自动通过。

链条中的 M、B、I、H 分别是英文 Malfunction、Behavior、Impact、Hazard 的缩写，在代码里用于标识三条连接。这里的 I 指车辆行为造成的运行后果，不等同于已经确定的人员伤害。人员伤害说明在后面的 S 方法给出等级含义后再附加。

如果同一方案还取了另一个距离点，新点没有发生接触，程序需要重新判断该点的实际危险主张，不能沿用“已与前车碰撞”的句子。反过来，没有接触也不自动等于所有危险都不存在；保留、排除还是未决，仍按当前受支持的危险机制和证据判断。

### 进入本步的对象：已经实例化的世界，不是标题相似的场景

入口为 [assess_scenarios](../../../src/hara_agent/workflow/nodes/scenarios.py)。输入包括 `HARAState`、明确的 `MalfunctionCandidate` 列表、候选 `ScenarioCandidate`、活动 `MethodContract`、项目证据注册表，以及普通运行或已提交条件重验所提供的物理实例。实际核验单位是 `malfunction_id + scenario_id`。同一基础场景在不同失效、驾驶员配置、对象或轨迹下形成的子身份，必须分别交接；不能凭场景描述相似就共用结论。

候选中需要保留 `facts`、`fact_provenance`、`analysis_instance`、物理模型及 `motion_model_outcome`，请求还带当前失效的功能影响和车辆级危险主张。程序先建立项目证据目录，再构造带精确证据 ID 的因果视图。来源 ODD 只说明允许的条件；车位角度、道路类型、正常速度范围和模型取点不能互相替代。条件性物理方案已经通过实例化检查时，可以作为“这些假设成立时”的分析世界；它仍不等于 Item 原文事实或工程批准。

物理阶段已报 `PHYSICAL_PLAN_INVALID`、`PHYSICAL_INSTANTIATION_FAILED`、`MODEL_GEOMETRY_NOT_APPLICABLE` 或需要另建初始接触阶段时，本步将其保留为具体未决。因果 LLM 不能通过改写说明修好几何，也不能把未能计算当作安全排除。

### LLM 实际判断什么，明确不判断什么

[ScenarioFeasibilityAgent.assess / _parse](../../../src/hara_agent/services/semantic/scenario_agent.py) 按受控请求返回 `assessments`。每个请求身份必须恰好有一项，字段包括三个布尔资格、`breakpoint`、三跳 `causal_chain`、`hazardous_event`、`physical_interaction`、`risk_dimension_changes`、置信度及状态。当前语义阶段止于 **M→B→I→H**：失效、系统行为变化、运行后果、危险事件。伤害尾段在评分后按 S 的活动方法语义附加，因果模型不自由生成伤情或先选 S 等级。

每一跳都要有 `claim`、`basis_type`、`evidence_refs`。`DIRECT_FACT`、`DERIVED_PHYSICS`、`APPROVED_RULE` 必须引用对应类别的已注册证据；原始速度不能伪装成已经计算的接触结论。父级 `vehicle_level_hazard` 是待验证主张，不能独自证明 I→H。故障运动产生的未干预轨迹是本步对象，制动可用、他方可避让等处置能力不能被写成已经发生的动作，从而取消原危险链。

`physical_interaction` 还限定当前目标、方位、对象 ID，以及 `CURRENT_STATE` 或 `MODEL_TRAJECTORY` 阶段。前者表示当前状态，后者表示模型推导的后续轨迹；两者不能混写成同一时刻。无接触取点不能写成已经发生接触；另一个参数点、后车或坐标系也不能补足当前取点。若自车静止反事实仍接触同一目标，必须说明故障运动增加危险的环节，不能仅因“有接触”就肯定该失效具有增量因果性。这里的“反事实”只是用同一几何问一句“如果没有这次故障运动，会怎样”，不是另建一份项目事实。

### 三类去向由一个资格入口决定

权威判定是 [evaluate_risk_eligibility](../../../src/hara_agent/models/scenario.py)，其结构校验依赖 [ScenarioCausalAssessment](../../../src/hara_agent/contracts/scenario_causal_assessment.py)。`final_retain` 是判定的派生结果，不是可以单独改成 `true` 的批准按钮。

| 去向 | 必要判断 | 下游处理 |
|---|---|---|
| 保留并可进入评分 | 三个资格均真；M→B→I→H 路径完整；各跳证据绑定有效；无断点、无不支持环节；危险事件非空；已提交状态满足资格 | 按身份进入 `state.scenarios`，再补缺失事实和评分 |
| 因果排除 | 已完成有效判定，但存在不成立的因果环节或明确不适用 | 原 assessment、断点、证据和排除原因留存，不生成本次风险行 |
| 未决或尚未交接 | 缺断点、缺证据、资格未完成、物理实例无效，或运行中断尚未提交 | 保留审计与恢复位置，不冒充排除，也不先生成评级 |

三个历史布尔值全部为真，不能替代当前 typed 因果契约。另一方面，来源关联的失效分析前提可以在工程状态 `PENDING` 下合法进入条件计算：前提来源、三跳已验证证据及专门的资格条件必须成立。因果验证通过与车辆能力、失效定义获得批准是两条轴。评分后附加的条件性 H→Harm，也不能反过来撤销已经合法交接的 M→B→I→H 输入队列。

### 合批、结论复用和中断恢复的边界

`_scenario_batch_cache_key` 将方法执行身份、项目输入、提示与契约版本、Provider 配置和完整场景事实/来源纳入请求身份。`save_batch` 在失效组完成时写回 `scenario_assessment_batches`，通过 checkpoint 回调保存；最后再以资格结果构造保留队列和完整 `scenario_assessments`。因此原始响应存在、缓存可读、assessment 已提交是三个不同事实。

[scenario_equivalence](../../../src/hara_agent/services/analysis/scenario_equivalence.py) 的精确任务键可以复用相同任务，驾驶员家族复用另需证明非驾驶员事实和各跳依赖没有变化。两个驾驶员放进同一请求不等于可以复制结论。重绑定只改受控身份并再次走原解析器；请求规模过大、单项格式错误、覆盖缺项等使用原有拆分、挽救有效项和有界纠正，不能重置同一任务的失败额度反复收费。

出现“为什么没进评分”时，先看资格原因与原因果三跳，再看批次提交和断点；不要直接改后续 SG 或主表。回归入口可从 [因果契约测试](../../../tests/regression/scenario_causal/test_contract.py)、[因果 Agent 集成](../../../tests/unit/test_scenario_causal_agent_integration.py)、[批次单项挽救](../../../tests/unit/test_scenario_batch_item_salvage.py) 定位。

### 因果记录的核验顺序

先固定 `malfunction_id + scenario_id`，也就是“哪一个失效、哪一个具体场景身份”，再从记录读出当前对象、方向、参数点和驾驶员条件。不要先按 Excel 行号查：报告重新分组后行号可以变化，但这组分析外键仍用于关联数据。

接下来依次检查三跳主张及引用。每个引用都应该能回到项目事实、已计算轨迹或活动规则，而不是只回到一段模型自己的解释。最后检查判断是否已经提交到状态。这样可以区分三种看起来相似的问题：模型确实判定因果不成立；模型没有提供合格证据；模型已经返回，但任务中断导致结果还没有交给后续工作流。

如果需要重新分析，只处理输入或因果主张实际变化的身份。日志中的“合批”表示一次请求带了多个身份；“完整因果复用”表示另一身份在证明成立后没有再请求完整判断。它们的成本含义不同，应分别统计。



### 实现例 R01｜驾驶员因果复用必须经过子场景重验

**所在函数与调用关系：** `assess_scenarios → _assess_instantiated_scenarios`。此前已对家族代表 `parent` 得到 `assessed`，下面处理同家族的 `child`。输入是代表结论、父子候选和证据注册表；输出是可复用的子身份 assessment，或者进入 `pending` 的独立任务。

这里展示的是生产调度的分岔，不是复用率统计代码。`prebatched` 表示该子身份已经独立判断过，不能把合批误记为完整结论复用；其余成员必须先有 `proof["reusable"]`，还要经过 `revalidate` 将身份和证据绑定到当前子世界。

## wf-10 仅为保留场景补查真正缺失的风险事实

### 风险事实解释的职责：将已有依据绑定到评分需求

经过因果核验，程序已经知道“这一条值得继续分析”。但“值得分析”不代表评分需要的每个字段都已齐全。例如，某个方法可能需要确认对象属于行人还是车辆，或者需要知道现有证据中的速度究竟指自车初速还是目标速度。本步的职责是带着这些明确问题，回到可引用的证据里查找和解释。

`RiskFact` 可以理解成一张小型证据卡：上面不仅有“值”，还写着这个值属于哪个场景、哪个对象、哪个阶段、用什么单位、从哪里来。`RequiredFactSpec` 则是评分方法提出的取证要求，相当于“这次计算需要哪一种事实，允许哪些类别和单位”。两者对上以后，后续绑定器才知道能不能用于本次计算。

本步不能把“没有查到”变成“模型再猜一个”。动态距离、故障加速度、响应策略等分析假设应由前面的物理方案任务明确提出和标注；来源解释只负责原证据已经支持的内容。两个职责分开后，报告中的数值才能明确区分为材料给出的、规则指定的或分析方案提出的。

| 同一个字段可能来自哪里 | 例子（仅说明类别） | 程序应该怎样处理 |
|---|---|---|
| 项目原文 | 执行阶段的速度范围、遥控功能的使能条件 | 保留原句、限定条件和来源位置，按原作用域使用 |
| 活动方法 | 某类对象或运行条件的规则定义 | 从 `MethodContract` 使用，不让模型另写数值规则 |
| 分析假设 | 为一个代表工况提出目标距离或故障加速度 | 保留假设及适用条件，经物理实例化后进行条件计算 |
| 程序推导 | 当前轨迹的首次接触时间或碰撞速度 | 保留模型、输入、对象和阶段，不当成材料中的实测值 |
| 尚无依据 | 证据没有说明当前失效后的某条控制路径 | 明确缺什么；不能把空值、未知或未找到写成“不可用” |

例如，原文说“系统以 10 ms 周期执行任务”，不能据此得到“制动响应时间为 10 ms”。单位相同不代表物理含义相同。又如，原文只说有制动执行器，不能顺便推出驾驶员在车外仍能通过踏板控制它。本步和后续绑定检查的价值，正是避免这种表面有数字、实际接错含义的问题。

### 本步是来源解释，不再生成物理方案

本步仍在 `assess_scenarios` 的保留交接之后执行，由 [ScenarioRiskFactAgent.interpret](../../../src/hara_agent/services/semantic/scenario_risk_fact_agent.py) 负责。输入是已保留的 `(malfunction_id, scenario_id)`、对应候选、失效对象及活动方法编译出的 `RequiredFactSpec`。只挑选 `origin=SCENARIO_FACT` 的需求；项目事实和方法规则由各自权威入口提供，不在此重新解释一套。

输出是带精确上下文的 `RiskFact`，以及找到、未找到、解析失败和缓存命中的审计。请求中的场景名称、危险描述和分析理由能帮助限定查询，但不能冒充原文摘录。缺一个速度值不授权 LLM 选一个“合理速度”，缺避让能力也不能根据“支持泊车”自行推定。需要生成动态参数或控制响应时，应回到上游有界物理/控制任务，不把本步当成第二个物理生成器。

### 缺口选择、证据裁剪和返回字段

`_existing_input` 先检查当前世界是否已有可用输入，`_interpret_specs` 只对真正缺少的类型组请求。碰撞类型、道路参与者类别和速度语义之间有依赖，程序分组处理，避免先有一个任意速度再去寻找能解释它的对象。已有实例的取点、单位和批准来源继续保留；新查出的来源值与它冲突时，后续绑定器报告冲突，而不是悄悄覆盖。

LLM 任务名为 `interpret_scenario_risk_facts`，返回 `results`。每个请求必须回带 `malfunction_id`、`scenario_id`、`fact_type` 和 `FOUND/NOT_FOUND`，包括未找到也不能只写一个 status。`FOUND` 还须包含 `value`、精确 `unit`、一个或多个 `evidence_ids`；类别值必须落在当前编译契约允许的枚举中，数值必须是 JSON number，布尔值不能当数字。证据 ID 既要在目录中，也必须属于本失效/场景允许的证据集合。

程序 `_parse_results` 校验身份、重复项、单位、枚举和来源范围，然后构造 `RiskFact`。`fact_id` 根据身份、值、单位和物理语义稳定生成；`context` 保存 MF/SCN，`source_refs` 保存实际引用，`produced_by` 保存提示版本，另记录 `physical_semantics` 与 `normalization_evidence`。来源解释经过了格式和语义检查，不意味着由模型赋予工程批准；后续计算仍要读取实际 approval、来源性质和适用范围。

### FOUND、NOT_FOUND 和无效响应不能混成一个空值

`FOUND` 表示当前提供的摘录支持该值；是否足够用于具体评分，还要经过绑定、物理语义和适用性检查。`NOT_FOUND` 表示本次有界证据查询没有找到支持，不等于世界中不存在该能力或该事件不发生。重复身份、越界枚举、引用其他成员证据或错误单位属于无效返回，不得当成合法未找到；缺项只可使用已有的有限覆盖修复路径。

同一个来源集合、查询与物理世界下，已查明的 `ABSENT_IN_EVIDENCE` 可按 `_absence_key` 复用，避免每次恢复都重复购买相同的“未找到”。它不是全项目的永久否定：源文、世界或请求改变后不能沿用旧的缺失判断。普通响应批次另由 `_batch_cache_key`、`_load_batch_cache` 及 `scenario_risk_fact_batches` 保存，`on_batch` 完成即 checkpoint。没有需求、没有保留对象或需求全已满足时，本步可为零请求。

### 交接给评分时保留的三层信息

评分交接应同时检查：**原始值及单位**、**值的来源/范围/批准**、**当前计算是否可用**。例如已源连但未批准的手动制动假设，可以在适用的条件规则内形成条件 C；仅有制动执行器存在的原文，不证明驾驶员能触发它，更不证明当前失效后该路径仍存。与之类似，静止目标的来源类别可以确定，但当前轨迹是否纵向接触仍由现有物理计算决定。

普通入口随后把风险事实送入状态的 typed 风险事实集合，评分阶段由事实绑定和风险上下文服务消费，不让报告文本直接参与查表。修改本步时，优先检查“是否错误请求已有事实”“是否把 NOT_FOUND 扩大成事实”“是否跨身份复用来源”；相应回归见 [风险事实 Agent 测试](../../../tests/unit/test_scenario_risk_fact_agent.py) 与 [评分输入来源测试](../../../tests/unit/test_exposure_binding_audit.py)。不能为减少 Pending 直接补默认值，也不能仅删除缺口审计来获得表面完成度。

### 为什么本步有时没有 Provider 请求，有时仍然需要请求

如果上游已给出合格的对象类别、速度语义和其他必要事实，本步只核对已有内容，可能完全不调用模型。如果只有部分类型缺失，则仅为这些类型组织请求，而不是把整套物理方案再生成一次。已经按相同证据查过且得到“未找到”的问题，也可以在作用域不变时复用该查询结论。

因此，“风险事实阶段零请求”可以是正常的复用结果；“阶段有请求”也不等于场景生成失败。排查时应看每条请求的缺失类型和已有输入判断，而不是只看次数。若两次请求对应的原文、对象或阶段已改变，它们就不能因为字段名相同而被合并。



### 实现例 R02｜先扣掉已有合格输入，再按缺失类型安排事实请求

**所在函数与调用关系：** `assess_scenarios → ScenarioRiskFactAgent.interpret → _interpret_specs`。输入 `pair_material` 是保留场景的身份、候选和可引用证据；`specs` 是编译后的事实需求。下面先按每个身份真正缺失的类型分组，再按预期返回项数分批。返回合同是事实、批次审计和缓存命中数。

`_existing_input` 不只检查字典里有没有值：它检查活动允许值及当前 MF/SCN 的来源适用范围；`SPEED_UNSPECIFIED` 还需后续速度语义解释，不能只因已有一个速度数字就跳过。缓存中的“未找到”也有独立的 `source_absences` 作用域。

```python
def _interpret_specs(
    self,
    pair_material: Sequence[dict[str, Any]],
    specs: Sequence[RequiredFactSpec],
    *,
    batch_cache: dict[str, Any] | None,
    on_batch: Callable[[str, dict[str, Any]], None] | None,
) -> tuple[list[RiskFact], list[dict[str, Any]], int]:
    if not pair_material or not specs:
        return [], [], 0
    groups = {}
    for pair in pair_material:
        needed = tuple(spec for spec in specs if not self._existing_input(pair, spec))
        if needed:
            key = tuple(spec.fact_type for spec in needed)
            groups.setdefault(key, (needed, []))[1].append(pair)
    facts: list[RiskFact] = []
    audits: list[dict[str, Any]] = []
    cache_hits = 0
    scoped_cache = batch_cache if batch_cache is not None else {}
    absences = {key: value for entry in scoped_cache.values()
                if isinstance(entry, dict) and entry.get("cache_version") == SCENARIO_RISK_FACT_BATCH_CACHE_VERSION
                for key, value in entry.get("source_absences", {}).items()}
    batches = [(pairs[start:start + max(1, self.batch_max_results // len(needed))], needed)
               for needed, pairs in groups.values()
               for start in range(0, len(pairs), max(1, self.batch_max_results // len(needed)))]
```

**为什么这能减少重复请求：** 完全没有需求或候选时直接返回；某条候选的所有输入已满足时不会进入 `groups`。`batch_max_results // len(needed)` 按“每场景缺几项”限制一批容量，避免多类型查询意外生成超大返回。这个截段展示请求准备；真正命中缓存、解析和落盘在后续 `_interpret_cached_batch` 中，不能把 `groups` 数量直接当作付费请求数。

## wf-11 绑定评分输入，逐危险分支执行 S/E/C 与 ASIL

### 风险评分的职责：分别计算 S/E/C，再查询 ASIL 矩阵

到这里，工作流已经交来一个有因果依据的具体危险场景。评分不再让大模型写“我认为是 A 级”，而是把当前事实和物理计算结果交给活动方法。S、E、C 分别回答不同的问题；ASIL 是把这三个结果按当前方法矩阵组合后得到的等级。

| 名称 | 本项目里要回答的问题 | 不能与什么混淆 |
|---|---|---|
| S，Severity，严重度 | 按活动方法，这个具体危险后果对应怎样的伤害严重度？ | 不能只用正常功能限速代替当前碰撞量，也不能只因描述吓人就提高等级 |
| E，Exposure，运行工况暴露度 | 这种运行条件在当前方法中处于什么暴露等级？ | 不是故障发生概率，也不是碰撞概率；故障后速度上升不自动把停车场变成高速道路 |
| C，Controllability，可控性 | 在该交互和可用控制条件下，有关人员是否具备避免伤害的能力？ | 不是只有一段 TTC 就可查表；必须有适用的控制、人员和时间/空间条件 |
| ASIL，汽车安全完整性等级 | 当前 S/E/C 组合在活动矩阵中对应 QM 或 A—D 中哪一项？ | 不是对模型回答质量的打分，也不是把 A、B、C、D 平均分配给项目 |
| QM | 矩阵给出的质量管理分类 | 不等于“没有危险”，也不授权把未知 S/E/C 写成零等级 |

评分链的职责分工是：**物理计算给当前世界中的量，方法给量的意义和分档，矩阵给最终组合。** 报告只解释和展示这些结果。把错误修在报告文本里，不会修正真正的评分输入；把一个等级硬填进 Python，也会绕过方法来源。

### 从一条风险身份到多个危险分支，再回到主表

“一个场景身份”和“一个碰撞分支”不是完全相同的概念。同一场景可能涉及不同对象或不同接触阶段，每一条实际分支都需要自己的物理视图。例如，一条分支描述与前方车辆接触，另一条描述与侧向对象交互，就不能把前车的接触速度、侧向对象的暴露条件和另一驾驶员的避让能力拼成一套评级。

程序按以下四步处理：

1. 固定分支所描述的对象、轨迹和接触阶段，核对这条分支自己的输入。
2. 分别执行 S、E、C，并保留每项所用的规则、来源与条件。
3. 用这条分支自己的三个等级查询 ASIL；缺项按活动矩阵允许的规则处理，不能任意补齐。
4. 汇总时选出一条真实存在的最高已知 ASIL 分支，同时保留其他分支的结果和缺口。

文档和代码中的 `tuple` 是“元组”，这里就是把 `(S, E, C, ASIL)` 当作同一条分支的一组完整结果。假设分支甲的 S 更高、分支乙的 C 更高，汇总也不能逐列选最大值，拼出一条从未计算过的新组合。相反，最大 S 所在分支也未必拥有最高 ASIL，所以不能只比较 S。

这同样解释了为什么“还有未决分支”和“已有数值结果”可以同时存在。程序可以报告已知部分，但不能借已知部分声称全部分支都已完成。

### 调用链、输入资格和产物

[score_structured_scenarios](../../../src/hara_agent/workflow/nodes/scoring.py) 再次读取规范资格，不直接相信保留列表或旧布尔值。它按 MF/SCN 外键找候选，再找功能；外键缺失、重复身份和真实来源冲突不能靠数组顺序修补。中立事实由 `MethodRiskFactBindingService` 绑定，危险事件输入由 [HazardousEventRiskContextService](../../../src/hara_agent/services/analysis/hazardous_event_risk_context_service.py) 检查对象、物理量、阶段、来源范围和可用性，交给 [StructuredRiskScoringService.score](../../../src/hara_agent/services/analysis/structured_risk_scoring_service.py)。

本步不调用 LLM 选等级。S、E、C 执行器只消费编译好的 `MethodContract` 和当前计算事实；运行期不会重新打开 YAML。每项结果保存等级、`calculation_status`、`engineering_status`、`calculation_nature`、规则 ID/版本/原文位置、`inputs_used` 和缺口。随后构造 `RiskAssessment`，保存 `branch_evaluations`、`branch_summary`、伤害说明，并写 `risk_execution_trace.json`。评分审计同时调用 `RiskCalculationInputService.ftti`，最后进入 `SAFETY_GOALS`。

### S：先确认物理量的意义，再查活动速度分档

`SeverityDeltaVSemanticAuditService.input_authority` 先确认活动方法要求的速度语义和当前输入权威，`SeverityMethodExecutor.lookup` 再执行分档。正常限速、初始速度、故障后速度、碰撞速度和相对速度不是同一量；方法要求 Δv 时，也不能未经批准就用相对速度替代。已确认来源内部有语义冲突时，执行器不被调用，结果是 `PENDING_METHOD_SEMANTICS`；缺当前对象/阶段的物理输入则保留 `PENDING_INPUT`。

S 有值后，[PotentialHarmResolver.resolve](../../../src/hara_agent/services/analysis/potential_harm_resolver.py) 从当前方法的 S 等级语义生成 Potential Harm，再用 `with_harm` 追加 H→Harm。它不把低速碰撞自行解释成某种具体伤情，也不让新尾段批准上游失效前提。修改伤害展示，应先检查活动 S 语义和证据尾段，再检查中文映射；不能让报告层另选一个更重的 S。

### E：Atom、Z/F 域、耦合和覆盖信息各有职责

`ExposureMethodExecutor` 根据部件类别选择唯一的 Z/F 域，读取当前 `scenario_atom_ids` 对应的方法 Atom。当前 `fusa_v1` 还保留受治理的场景级域切换：请求域没有可用值时才查另一域，并在 `requested_domain`、`actual_domain`、`dimension_fallback` 中明确记录。它不是缺值时任意选较高 E。Atom 不存在、两域都无值或绑定来源不足仍然未决。

当前策略先处理全部最高等级、单个有效 Atom、特殊高等级组合和其他不等等级组合；仅当多个相同等级需要合成时才消费 `atoms_coupling`。例如本策略下多个 E2：`coupled` 保持 E2，`independent` 降一级且受方法下限约束；耦合未知时不猜。全部 E4 或特定 E3/E4 组合已在前序规则得到结果，不必为了填字段额外要求耦合。数值和优先级来自已编译策略，不能作为所有 HARA 方法的通用公式。

当前 [exposure_policy.yaml](../../../method_assets/fusa_baseline_v1/normalized/exposure_policy.yaml) 的 `mixed_high.match=EXACT_LEVEL_SET`：只有等级集合**恰好为 `{E3,E4}`**才走该特殊分支得到E3。`{E2,E3,E4}`和`{E1,E3,E4}`走其他异级组合取小，分别为E2和E1，不能因为同时含E3/E4而忽略更低值。没有该字段的旧契约保留历史`CONTAINS`语义，重导历史快照不得偷偷换成当前政策；本版说明不是再次修改规则。

[ExposureDimensionCoverageService](../../../src/hara_agent/services/analysis/exposure_dimension_coverage_service.py) 的覆盖审计与 E 输入完整性也要分开。当前 `fusa_v1` 的覆盖信息用于审核，不替代原 Atom 决策；其他编译策略可以要求明确维度覆盖。只因标题含“斜列”不能声明角度覆盖，换了碰撞对象也不能继承另一对象的 OBJECT Atom，除非有新的绑定或已证明的不变性。

### C：先验证干预路径，时间数字不自动获得适用资格

`StructuredControllabilityExecutor` 执行活动覆盖规则、未知条件策略和选定 profile。手动制动、远程接口、他方避让分别通过现有 `RiskCalculationInputService` 的适用性入口；执行器存在不证明人工命令路径存在，远程按钮也不恢复已失效执行器。他方避让需要同一目标的可计算避让及空间/时间条件，不能只读一句“可以避让”。`unknown` 不等于 `false`，也不能默认符合优先覆盖规则。

当前受治理的 [IAV profile](../../../method_assets/fusa_baseline_v1/raw/c_profiles/iav_avp.yaml) 在驾驶员在位、制动反应路径可用等条件下，用 `TTC≤3 s → C3`、`3<TTC≤4 s → C2`、`4<TTC≤5 s → C1`、`TTC>5 s → C0`。这是该 profile 的分档，不是 ISO 的通用秒数；清单中排除为数值权威的旧 `raw/controllability_rules.yaml` 不能重新启用。后方接近、横穿、曲率和静止本车不能只因有接触时间就套此表。

活动 [project_analysis_policy](../../../method_assets/fusa_baseline_v1/normalized/project_analysis_policy.yaml) 对部分横穿/曲率或转向场景提供明确的条件性参考迁移，仍需满足实际控制、人员、观测和适用性条件。真遮挡和发现延迟不能被“无遮挡”的另一分句抹掉；“仅作几何参照，不据此声明遮挡”也不能误读成已经遮挡。SIDE 是接触表面标签，不独自决定速度轴；程序只在现有模型及来源支持时重算纵向 DERIVED 视图，横向运动、曲率或真实横穿仍保持原几何，不能把 first contact 全部重命名为纵向 TTC。

### 同分支评级、部分结果和矩阵决定

`_score_collision_branches` 先检查分支集合来源、`branch_id`、`mechanism_id`、`impact_time_id` 和物理可行性；`branch_physics_view` 为每个实际对象/阶段建立评分视图。速度区间要在方法分档边界与各开放区间取点，不能仅算两个端点就证明非单调表内的不变性；S 区间分割也不证明整段轨迹的 C 已成立。

每个分支独立产生 `(S,E,C,ASIL)`，ASIL 只通过 [MethodContractASILService](../../../src/hara_agent/services/analysis/asil_service.py) 查活动矩阵。顶层“最高已知 ASIL”选择的是一条真实已算分支，不分别取最大 S、E、C 拼成从未出现的世界。有部分行但无完整 ASIL 时，保留稳定的真实 partial tuple 并标记 `partial_branch_id`；完全没有有效分支时，独立环境 E 可以保留，父级 S/C 不能冒充该对象的结果。未决分支仍在摘要中，最高已知值不证明全分支上界。

矩阵允许的零等级短路同样是查算证明：某一已成立 S0/E0/C0 只有在所有未知维度补全组合都导向同一个受治理结果时，才能得到 QM；未知项仍为空。QM 不等于把缺失 C 写成 C0，也不要求额外创造 SG。

| 可见现象 | 应保留的实际含义 |
|---|---|
| 等级非空，计算 `FINALIZED`，工程 `PENDING` | 规则已完成条件试算，输入/前提仍待批准 |
| 等级为空，`PENDING_INPUT` | 当前输入或路径没有建立；检查具体缺项和来源 |
| 等级为空，`PENDING_METHOD_SEMANTICS` | 活动方法不覆盖或语义未解决；不能补数字假装闭环 |
| 有最高已知 ASIL，分支摘要 `PENDING` | 已算成员有结果，其他分支仍未解决 |

### 数值结果与审核状态：计算完成不等于工程批准

表中的 S2、E3、C3 或 A 等字符只表示计算结果本身，不能单独说明结果是否已获工程确认。内部使用两类状态来表达这个区别：`calculation_status` 说明计算有没有完成，`engineering_status` 说明所依据的语义、能力或假设是否已得到确认；`calculation_nature` 进一步说明本次是否为条件性分析。

例如，模型提出一套明确的距离和故障加速度假设，程序检查相容后顺利算出碰撞速度，S/E/C 也都能查表。这里的算式可能完全正确，但距离和加速度仍是分析假设，并没有因此变成该车辆已测得的性能。报告应保留等级，并在独立说明中写清条件和待审状态。它不应把每个等级格都加上重复后缀，也不应为追求“全表已完成”自动批准假设。

相对地，“待评定”表示当前没有可用的等级值。造成它的原因至少应分开：事实未传到正确位置、物理输入冲突、控制适用性未成立、活动方法没有覆盖、或者因果交接尚未完成。前几类可能需要修程序或补已有证据；真正的方法范围缺口需要方法依据，不能一概归结为用户没有提供数字。

审核时应先看结果有没有值，再看值的性质，最后看具体理由。只统计 `PENDING` 这个单词，会把“已经完成条件试算”和“完全没有算出值”混在一起，导致进度判断失真。

### 时间审计：FTTI、TTC 与响应完成时间如何同时保留

[RiskCalculationInputService.ftti](../../../src/hara_agent/services/analysis/risk_calculation_input_service.py) 先保存接触时间类型、模型、对象、时间原点及逐分支 `branch_timings`，再调 [FTTIMethodExecutor.evaluate](../../../src/hara_agent/services/analysis/deterministic_risk_executor.py)。有分支时父场景时间不能顶替分支时间；当前多于一个接触分支尚需分别绑定响应轨迹，执行器保留未决，不先取最短接触时间冒充结果。ASIL 也不会被转换成默认秒数。执行前校验当前方案来源、所需/剩余/失效控制、驾驶员范围、响应模型、接触阶段、模型时域和停车保持条件。

静止目标的一类现有响应求的是最晚开始制动的 `τ`：

```text
故障继续行程 + 从响应起始速度制动的行程 = 当前可用行程
v0·τ + a·τ²/2 + (v0+a·τ)²/(2·b净) = d
t停止 = (v0+a·τ)/b净
t危险时限（故障时钟） = fault_to_model_start_s + τ
```

这里的 `b净` 是已声明且适用的净减速，不会自动叠加或扣除另一未经定义的加速度。对移动目标及静止有限接触包络的特定无接触情形，程序复用 [scenario_physics](../../../src/hara_agent/services/analysis/scenario_physics.py) 的同一目标轨迹、故障行驶—制动—停车保持分段检查，求从即时响应起连续有效的初始安全窗口。不能在停车瞬间结束检查，原轨迹无接触也不能跳过所选响应验证。响应导致接触、根不在声明时域、停车后运动未知，分别保留实际失败或未决。

说明例：`v0=1 m/s、a=0、d=4 m、b净=2 m/s²` 时，最晚制动起始为 `3.75 s`，之后停车耗时 `0.5 s`。它们不能相加成 `4.25 s` 的可用响应起始预算。检测、决策和命令建立延迟应与起始窗口比较；模型已有的完成耗时另列。该例只说明方程，未引用任何真实项目取值。故障到模型起点的 offset 和危险判据没有绑定时，即使算出模型相对窗口也不能宣称故障时钟 FTTI。

把这个教学例画成时间顺序，就是“故障轨迹持续一段时间 → 制动开始 → 继续走完制动距离 → 停住并按模型继续检查”。FTTI 相关求解关心的是前面还能允许多长等待，以及这个等待是否能绑定到明确的故障时钟；停车耗时是后面的运动过程。两者加错、把无干预接触时刻直接当成可用等待时间，都会高估响应余量。

对移动目标尤其要继续看“停车以后”。车辆在行人横穿路径上停下，并不自动消除了后续接触。现有执行器因此检查声明时域中的完整响应轨迹；它没有宣称模拟了车辆从此以后的所有行为。得到边界时也必须同时交代模型、对象、时域、响应能力和故障起点。

回归定位见 [结构化评分](../../../tests/unit/test_structured_risk_scoring.py)、[E 基线一致性](../../../tests/unit/test_fusa_v1_exposure_parity.py)、[C 路径适用性](../../../tests/unit/test_c_response_applicability.py)、[响应时间](../../../tests/unit/test_moving_response_timing.py) 和 [同作用域时间](../../../tests/unit/test_scoped_timing_and_avoidance.py)。调整规则须改方法来源并重新编译；调整物理来源/适用性须改现有输入或执行器入口；报告措辞不承担这两种修复。

## wf-12 关联安全意图，检查发布条件并生成报告

### SG、响应方案、Safe State 与 FTTI 的职责关系

这一阶段把前面的逐场景风险整理成工程师可以审阅和继续设计的内容。最容易产生误会的地方，是把“希望避免什么”“打算采取什么动作”“动作后要到达什么状态”“还有多少时间”写成同一段话。它们彼此关联，但不能互相代替。

| 内容 | 回答的问题 | 教学例：驱动异常后接近前方对象 |
|---|---|---|
| Safety Goal，SG，安全目标 | 为控制这类风险，需要避免什么不期望的行为或危险？ | 围绕防止非预期加速形成清晰安全意图；不把每个距离和参数点都写进目标正文 |
| 响应方案 | 准备用哪条实际可用的控制路径，怎样改变当前轨迹？ | 在适用控制条件成立时提出制动等响应，并声明依赖与参数假设 |
| Safe State，安全状态 | 执行响应后，要处于什么可保持、且与当前危险相容的状态？ | 若计算支持，可为停住并保持；若停住仍被移动对象撞到，该状态不能被当成已验证安全 |
| FTTI 相关时间结论 | 在所声明的故障时钟、危险判据和响应模型下，允许的时间边界是什么？ | 计算最晚响应起始边界，另列后续完成耗时；缺时钟绑定时只保留模型相对窗口 |

表中是概念说明，不是给项目新增控制措施或认可某条响应路径。实际报告必须使用当前来源、方法、已生成方案和计算证据。安全目标可以已经存在，而安全状态仍未确定；某个响应方案也可能已经完整建模，但结果是“即使立即响应仍不能避碰”。这两种情况都应如实显示，不能为了让 SG 页完整就填一个笼统的“安全停车”。

还要区分“工作做到了哪一步”和“谁批准了它”。SG 已生成并关联成员，只说明程序建立了可追溯的安全意图；Safe State 有候选，说明存在待评审的分析提案；求得条件性时间边界，说明该模型下已经完成一次计算。三者都不自动等于产品要求已经批准或车辆能力已经实测确认。

### SG 怎样生成：共享的是安全意图，参数留在成员关联里

评分后，[aggregate_safety_goals](../../../src/hara_agent/workflow/nodes/safety_goals.py) 调 [MethodSafetyGoalService.register_intent](../../../src/hara_agent/services/analysis/method_safety_goal_service.py)。键材料是去首尾空白并 `casefold` 的 `function_name + guideword + malfunction`，以换行分隔取 SHA-256 前十位，形成 `SG-METHOD-…`。场景参数、速度和驾驶员位置不进入共享意图键，而进入 `associations`、`associated_scenario_ids` 和候选范围。不要把显示句子的修改当成新 SG，也不要用 Excel 行号充当风险身份。

QM 成员跳过 SG 注册；非 QM 及 ASIL 尚未决成员保留意图关联。这样既不为明确 QM 造目标，也不让未算成员因没有 ASIL 消失。目录保存 `original_safety_goal`、意图正文、功能、最高已知 ASIL、方法来源和每条关联。重新聚合保留历史原文；既有安全状态只按旧关联范围保留，不因加入新成员而扩张适用范围。

SG 获得 `FINALIZED` 还需方法语义允许、无待审候选且关联风险已审核；条件性方案不会自行批准 SG。目录的 `NEEDS_REVIEW`、候选的 `PENDING/ANALYSIS_HYPOTHESIS` 和风险的条件性质继续留存。“最高 ASIL”只覆盖已计算成员，不是全 ODD 上界。

因此，SG 数量通常少于风险明细数量，这是预期的“多个具体工况关联同一安全意图”。但它不意味着程序可以任意把相近文字合成一个新目标。当前意图键的组成见上文；展示文字可以在已有意图和关联成员范围内整理得更自然，原始文字、目标 ID、方法来源及全部成员关系仍要保留。关联应支持从 SG 找回风险，也支持从风险找到相应 SG。明确 QM 成员没有 SG，是既有行为；它与“非 QM 成员意外丢失 SG 关联”不同。

### Safe State 从哪里来，为什么“已停车”仍可能不安全

当前候选来自已源连的 `(control_analysis or physical_analysis).hypothesis.safe_state_proposal`，包括 `description`、`required_controls`、`driver_positions`、`conditions` 和 `transition`，必要时还有 `required_command_path`。SG 汇总不临时调用 LLM 造一个状态，也不把“减速、报警、踩踏板”这类措施直接当最终状态。声明为 `REQUIRED_NOT_ESTABLISHED` 的独立系统命令路径是设计要求，不能在摘要里变成已存在的能力。

候选首先受当前驾驶员范围约束；不在驾驶位的成员不能借用驾驶员踏板。随后重用同一 FTTI 执行器检查所选响应是否能在同一目标、轨迹、包络和时域内避碰。即时制动都无余量，或制动/停车保持后仍接触目标时，SG 目录不保留其为可达安全状态，记录 `safe_state_gaps`，原方案仍保存在物理证据中。模型支持释放异常减速的响应时，期望状态也可能是保持当时速度继续运动，不能一律归纳成停车。

物理工作流的 [_retain_rejected_response](../../../src/hara_agent/workflow/physical_analysis.py) 保存已撤回提案、原输入快照、原方法 hash 和负面时间追溯。后续方法变化或重导不能直接继承旧负面，也不能复活提案。执行器只在快照精确匹配，或已有严格 DERIVED 轴向/TTC 更新证明成立时，在计算副本上按**当前**来源、控制、驾驶员和方法重验；窄范围更新还比较原冻结视图与当前视图的完整响应结果。真实对象、阶段、单位、轨迹、所用输入来源或适用控制改变仍使旧结论失效。

历史响应不安全，但当前所需自动命令已不在 `remaining_controls` 时，本轮只能判路径未建立，不能宣称负面重验通过。`missing_required_controls`、`failed_required_controls` 和 `driver_scope_mismatch` 分开记录，避免误归因驾驶员。历史证据保留在 `previous_timing_trace`，提案继续撤回。

### FTTI 的多次求值、状态分类和最小值语义

物理响应校验需要 FTTI 负面判断来发出有界纠正诊断；评分需要记录时间输入审计；SG 需要抑制实际失败候选；报告需要当前同范围的中文解释。这些入口均复用 `RiskCalculationInputService.ftti → FTTIMethodExecutor → scenario_physics`，不会让 SG 和报告各维护一个公式。报告显示使用当前 DERIVED 视图时，时间仍保持已冻结轨迹和撤回快照责任，不为统一显示随意改写历史快照。

| 时间追溯状态或缺口 | 报告应表达的结论 | 禁止的推断 |
|---|---|---|
| `CONDITIONAL_BOUNDARY` 且故障时钟/判据已绑定 | 已算条件性响应起始边界，仍待工程确认 | 当作实测端到端延迟或批准的时间预算 |
| `AVOIDABILITY_ALREADY_LOST` | 初始已无所选制动避碰余量 | 把内部零值/offset 格式化为可用正 FTTI |
| `NO_IMMEDIATE_SAFE_BRAKING_WINDOW` | 即时所选响应仍不能避碰，其他策略未建立 | 只写缺输入，或继续说停车即安全 |
| `FAULT_CLOCK_UNRESOLVED` | 响应轨迹已检查，但故障起点或危险判据未绑定 | 将模型相对窗口当故障时钟 FTTI |
| `NO_UNMITIGATED_CONTACT_BOUNDARY` 且响应也无接触 | 即时响应已检查，未建立延迟边界 | 给任意延迟安全保证、FTTI=0 或 C0 |
| 无适用控制、未建模响应、停车保持未知等 | 按实际缺口保留，能有接触证据也可无 FTTI | 把全部 Pending 都称为“用户未给参数” |

[EngineeringReportTextMapper.safety_goal_timing](../../../src/hara_agent/services/reporting/engineering_text_mapper.py) 按响应族、所需控制、驾驶员、时间原点、危险判据、命令路径实现状态、发起者和独立性要求分组，**每条路径内**对已算有效成员取最小值。摘要只预览有限条路径并给其余路径/缺口数；`detailed=True` 保存完整范围。最小值不覆盖负面或未决成员，也不是对未取样连续参数域的全局最小值。数值显示只进行受控舍入，原始 double 保留在时间追溯中。

这条“取最小值”规则可以这样读：同一条已说明的响应路径，如果甲成员可等 1 秒、乙成员可等 0.4 秒，就不能对这两个已算成员统一展示 1 秒而忽略乙。可这也不能推导出“所有成员都能等 0.4 秒”，因为组内还可能有尚未建模的丙，或立即响应也不安全的丁。不同驾驶员、不同命令路径或不同时间原点，首先要分清范围，不能只因单位都是秒就混在一起取值。以上数字仅为阅读示例。

### 投影如何分组：主表每行只有一组实际等级

“投影”在这里就是把已经保存的分析结果整理成表格可读结构，并不再生成新的风险事实。主表是审核入口，场景明细是完整成员清单，审计文件负责展示计算链。三者应描述同一批数据，只是阅读粒度不同。

可以用一个不涉及真实评级的教学例理解分组：同一失效有若干距离取点，取点的物理结果不同，但某些成员的完整评级、驾驶员条件、对象关系和审核状态都相同，程序可以让它们共享一行主表，参数差别放明细。若换成车外驾驶员、目标从前方改到后方，或者某成员的 C 尚无数值，就不能仅因失效标题相同把差别隐藏掉。具体能否同组，按下面的现有组键决定，不按人为目标行数决定。

[HARAReportProjectionService.project](../../../src/hara_agent/services/reporting/projection.py) 消费已提交状态、活动方法、风险/因果 trace、运行汇总和报告样式身份，生成 `HARAReportViewModel`。传入风险 trace 时，以 MF/SCN 建索引，缺少已提交风险、重复键或与评分记录不一致都会失败；不按两个列表的位置配对。`source_scenarios` 保留计算和生命周期语义，显示候选可使用受控的当前 DERIVED 视图。

`_member_display_tuple` 从同一实际分支取得展示 tuple。当前生成成员的 `group_key` 包含失效、物理机制、对象类别、伤害、审核条件签名、驾驶员身份、完整展示 tuple 和各维审核状态；方向、坡向、对象方位及接触表面等关键条件也参与区分。其他路径同样把展示 tuple 纳入键。因此一行 S/E/C/ASIL 只能是一组单元等级，不能出现“S2/S3”式混合评级，也不能把组内某条 QM 覆盖到未定级成员。

Atom 或参数变体可以作为同组明细，但“主表组数减少”不证明风险等价，更不证明覆盖完整。旧混合组的分布解释/共同字段处理只是历史诊断兼容，不是现行多值等级的正常输出。`grouping_map` 显式保留 `hara_id`、`review_group_id`、`assessment_ids`、`scenario_ids`、成员 SG、原 tuple 与分支；当前 `HARA_…` 编号按排序生成，重导版本间可变化，业务比较应使用稳定 MF/SCN/branch 外键。

### 报告核验路径：从主表成员追到计算证据

先在 `04_HARA` 选一行，读场景和危险事件，确认这行说的是谁在怎样的环境和运行阶段下受到什么影响；然后读同一行的 S/E/C/ASIL 及各自依据。等级格应是纯等级，是否条件性、哪里待确认应在独立说明中找到，不能靠猜测空白或后缀。

再按该行的 HARA-ID 到 `04A_Scenario Detail` 看所有成员。这里检查参数差异、对象、方向、驾驶员、物理结果和时间说明。若主表归了一组，明细应能解释组内包含哪些实际身份，而不是只重复主表的一句话。涉及多个危险分支时，再核对每个分支完整的 S/E/C/ASIL，确认摘要没有拼接不同分支。

随后沿 SG ID 到 `06_Safety Goal`，检查安全意图及成员关系，并把 Safe State 和 FTTI 的适用范围与刚才那条成员对上。最后，对争议数值进入 `05_Method Basis` 和 `99_Audit`，再按证据链接追到原始来源、物理输入及计算追踪。这条阅读顺序能把“输出看起来合理”变成“这一个结论的形成过程可以复核”。

如果要计算完整性，不应只数主表行数。应核对风险成员集合与 `grouping_map` 的映射，确认每个应展示成员都有去处、每个关联都能回到真实身份；排除和未决因果候选还应在各自审计中有解释。主表缩短可能只是展示归组，与减少模型请求或增加环境覆盖并不是同一件事。

[report_assets/hara_report_v1.yaml](../../../report_assets/hara_report_v1.yaml) 和 [ReportSchema](../../../src/hara_agent/services/reporting/report_schema.py) 管 canonical 字段、顺序、中文词表、显示策略及列资格；[EngineeringReportTextMapper](../../../src/hara_agent/services/reporting/engineering_text_mapper.py) 将方法标签、机制、原因和单位映成工程中文。等级栏只有纯等级或明确未决值，长理由进入解释栏；原始引用可以保留原语言，不把自由英文叙述直接塞进主表条件。

SG 展示以实际关联成员的对象/机制形成共同安全意图，不能把行人写成失效草稿里笼统的“障碍物”。倒车撞后方静止车的碰撞描述按当前条件表述，真实后车接近仍保留追尾含义。Safe State 的“已检查范围内避免接触”必须匹配同一成员、同一提案和实际时间 trace；只有响应模型或停车目标时，只述期望状态及待验证范围。

外文干预条件以受控说明引用原审计，保留 typed 控制，不伪造翻译。slash 检测仅用于该条件显示，普通来源中的 `camera/USSC/lidar/radar`、`100–500 m` 能见度限定及 MDC/IPB/EPB 缩写不能被隐藏。词表变更须核对主表、明细和 SG，不能替换原证据。

### 发布门禁、模板写入与零请求重导

[ReleaseGateValidator.evaluate](../../../src/hara_agent/services/validation/release_gate.py) 是只读检查：方法绑定、项目事实、风险因果契约、评级及批准、SG 关联及批准、待审项和工作流错误均进入 blockers。`pass_quality_gate` 只在通过时进入 `RENDER`。门禁不补评级，也不把 Pending 自动清空。应用层明确允许草稿时，可以输出带草稿范围的审核版；文件成功生成与 `ready_for_release=true` 必须分开记录。

报告经现有渲染入口交给 [HARAReportWorkbookRenderer.render](../../../src/hara_agent/services/reporting/canonical_renderer.py)：加载模板包、建立样式登记、依 canonical schema 写主表与支持表、原子保存，然后重新打开校验数量、字段和样式。静态字段只能按 canonical 身份受控合并，动态 S/E/C、ASIL、SG 和备注不合并；不能用合并单元格掩盖成员差异。核对单元格时应同时记录当前 schema 与工作簿版本，不能把本例行列当永久 API。

[OfflineReportRebuilder.rebuild](../../../src/hara_agent/services/reporting/offline_rebuild.py) 从已提交 checkpoint、实际方法 manifest、报告模板及对应 review root 读取；同样调用投影和 renderer，零 Provider。它产出 `p2-report-rebuild/report_projection_audit.json`、内容/伤害路径审计和模板/样式校验。投影审计中的 `ftti_timing_inputs`、`safety_goal_timing_evidence`、`safe_state_evidence` 和 `grouping_map` 能将单元格追到成员、分支、原始提案与时间状态，原始请求/响应再由 run/任务键和审计外链追查。

显示重导须保持评分 checkpoint 字节、身份/tuple、来源/批准不变，差异限定到语言单元格和报告 schema 身份。方法、控制或几何改变须走原评分/因果工作流及缓存/重绑定证明。付费恢复沿用同一持久账本，分别记缓存、原响应和真实请求；大 checkpoint 宜串行读取，重导无需 Provider。

定位回归可先跑 [成员范围](../../../tests/unit/test_report_member_scope.py)、[当前物理视图](../../../tests/unit/test_report_current_physics_view.py)、[共享主语](../../../tests/unit/test_report_shared_subject.py)、[响应证据复用](../../../tests/unit/test_response_evidence_reuse.py)、[撤回快照重验](../../../tests/unit/test_withdrawn_axis_cache_revalidation.py)、[报告 schema](../../../tests/unit/test_canonical_report_schema.py) 和 [模板渲染契约](../../../tests/unit/test_excel_renderer_contract.py)。正式验收仍需解决方法、控制实现和工程批准，表页或时间数值齐全不等于发布通过。

### 常见问题的责任层与定位顺序

| 看到的现象 | 先核对什么 | 应优先查的现有入口 |
|---|---|---|
| 候选在文件里存在，主表却找不到 | 因果是否保留、是否已提交、是否进入风险队列，而非先认定渲染漏行 | `evaluate_risk_eligibility` 与 `assess_scenarios` |
| S 依据用了与当前碰撞无关的速度 | 当前对象、阶段、速度语义及分支输入绑定 | 风险上下文与严重度语义审计，再查物理实例 |
| E 理由写的是旧动作或另一环境 | 当前 Atom 与物理条件是否一致、绑定是否已更新 | 场景条件绑定及 `ExposureMethodExecutor`，最后才查文字映射 |
| C 没有值 | 是输入未到位、控制不适用、交互模型不适用，还是活动方法确实不覆盖 | `RiskCalculationInputService` 与 `StructuredControllabilityExecutor` 的具体原因 |
| 已有等级，但审核状态仍未完成 | 是否使用了条件性假设或尚待确认的语义 | 评分 trace 的计算状态、工程状态及来源；不要批量改为已批准 |
| SG 存在，Safe State 却缺失 | 原方案未提出、驾驶员范围不适用、控制路径未建立，还是响应已被计算证明不安全 | `aggregate_safety_goals` 的 `safe_state_gaps` 与原物理方案 |
| FTTI 为待确定 | 时间起点缺失、响应未建模、控制不适用、所选响应失败等是哪一类 | 同一 `ftti` 入口的 `timing_trace`，不要直接用 TTC 填入 |
| 主表文字不自然或中英混杂，但数值和事实正确 | 映射是否遗漏了已有结构化含义 | `EngineeringReportTextMapper` 与报告 schema |
| 主表与明细、SG 对不上 | 真实身份、组映射及成员 SG 是否齐全 | `HARAReportProjectionService.project` 与 `grouping_map` |

定位以后还要按真实影响范围验证：只改语言，可以用同一 checkpoint 零请求重导并比较原数值与状态；改了对象、阶段或控制含义，就应重新评估相应依赖，不能仍称为“只改展示”。这种分层定位能减少无意义重跑，也能防止每次只把表格修好、生产输入仍然有问题。

### 实现例 R06｜报告分组键包含实际评级、驾驶员和交互条件

**所在函数与调用关系：** `HARAReportProjectionService.project` 被普通报告生成和 `OfflineReportRebuilder` 共同调用。输入是已提交风险、相应场景和风险 trace。下面先取同一真实分支的展示 tuple，再建立审核组键；这是展示归组，不是免除分析或风险等价证明。

[实际源码：src/hara_agent/services/reporting/projection.py 926—951行](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/src/hara_agent/services/reporting/projection.py#L926-L951)。以下为连续原码节选，依赖所在函数的上下文，不是可独立运行的新实现。

**为什么不会再把一行合成多个 S/E/C：** `display_tuple` 是组键的一部分，审核状态也在键内；驾驶员、目标方位、运动状态、坡向、坐标等差异由 `condition_key` 和驾驶员键保留。Atom/参数可以在相同展示组中保留为不同明细，不能据此断言已节省 Provider。普通非生成路径同样把 `display_tuple` 加入键。

**主表怎样追到全部成员：** 同文件 [1442—1454行](https://github.com/dmh045/Hara/blob/d6a400e7010d62ff5dda56efd8215f23729bb3ec/src/hara_agent/services/reporting/projection.py#L1442-L1454) 的 `grouping_map` 保存 HARA-ID、审核组 ID、每个成员 SG、完整 tuple 和分支、assessment IDs及scenario IDs。修改主表分组时必须同时检查这张映射，不应只比较主表行数。
