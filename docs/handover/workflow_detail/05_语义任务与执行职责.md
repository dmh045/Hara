# 当前语义任务与执行职责

## 模型解释与程序计算的职责边界

这个项目处理的不只是查表。输入可能是自然语言说明、带表格的 Word 或 PDF；同一句话中的“可以”“仅在”“故障后不可用”，会改变分析范围。大模型适合解释这类语义，并在原文未给出每个动态参数时，提出有边界、可追溯的分析假设。

但最终数值不能只靠模型文字。单位换算、轨迹求解、首次接触时间、方法表匹配、ASIL 矩阵和 Excel 关联，需要可重复执行、可检查的程序。本项目将这些职责分开：**模型提出结构化解释，程序检查和计算；审批状态由已有来源与治理记录决定。** 模型说“可以制动”不等于控制路径已经成立，更不等于正式批准。

文档中的 Agent 指“承担一个限定语义任务的模型调用组件”，不是一套独立运行的软件。它们都由同一个工作流调度，使用同一批类型契约、状态和已有方法。程序不会为每条报告行机械调用下表所有 Agent，也不会因为表格缺值就临时增加一条无界问答链。

## 同一份来源材料在不同任务中的用途

以下是流程示例，不是五份输入中的真实引文：假设资料写道，“泊车执行期间，驾驶员踩下制动踏板可退出功能”。

抽取任务要识别的是一个有来源、带阶段条件的功能行为：它适用于“执行期间”，操作是“踩下制动踏板”，效果是“退出功能”。它不能自行把这句话扩成“任何故障后都能在某个毫秒数内停车”。

物理任务关注的是另一件事：当前失效有没有破坏踏板通道或制动执行能力；当前人员位置是否允许踩踏板；如果只能条件性假设该通道可用，这个假设适用于哪个世界。Python 随后检查结构与依赖，再计算所提响应，而不是让模型直接报出 FTTI。

因果任务则核查“当前失效 → 车辆行为 → 对象交互 → 危险”的链是否成立。风险事实任务只补评分仍缺、且证据可以解释的输入。最后由同一个确定性评分入口计算 S/E/C 和 ASIL。这样，一段材料在不同任务中可以被使用，但其来源、限定和含义必须保持一致。

## 当前生产链中的模型任务

下表按职责区分请求，并关联相应实现。抽取按资料和缺口调度，失效分析按功能偏差调度，物理按可复用方案调度，因果按具体身份和依赖证明调度，风险事实按缺项调度。任务次数由实际输入、已有结果和缓存决定，不与主表行数一一对应。

| 职责与实现 | 这一环真正回答什么 | 允许形成的输出 | 不应越过的边界 |
|---|---|---|---|
| 核心资料与功能联合提取：[ItemArtifactExtractionAgent](../../../src/hara_agent/services/semantic/item_artifact_agent.py) | 文档描述了哪些功能、条件和明确事实 | 有来源的 Item 事实、功能及缺口 | 不能用模板例子填产品规格，也不能把标题直接当功能 |
| 有界资料补查：[ItemSupplementAgent](../../../src/hara_agent/services/semantic/item_supplement_agent.py) | 已发现的某类缺口，是否能在选定原文中补齐 | 对应事实类型的来源证据或未找到说明 | 不无界遍历，不建立第二套事实权威 |
| 方法所需项目事实定向提取：[TargetedProjectFactExtractionAgent](../../../src/hara_agent/services/semantic/targeted_project_fact_agent.py) | 当前方法要用的项目输入，原文是否明确给出 | 原文支持的具体事实与条件 | 不生成碰撞速度，不代替计算器给风险等级 |
| 引导词适用性：[GuidewordApplicabilityAgent](../../../src/hara_agent/services/semantic/guideword_agent.py) | “更多、更少、反向”等偏差是否适用于这个功能 | 下游候选／不适用／无可信危险三类去向及依据；待审核状态另行记录 | 不把所有功能与引导词的组合默认保留 |
| 失效及车辆危险行为：[MalfunctionHazardAgent](../../../src/hara_agent/services/semantic/malfunction_agent.py) | 功能这样失效后，车辆可能发生什么危险行为 | 准入后的功能偏差、车辆行为和危险主张 | 未经具体场景验证，不确定最终危险事件与风险 |
| 故障后物理方案：[PhysicalScenarioAgent](../../../src/hara_agent/services/semantic/physical_scenario_agent.py) | 在当前条件下怎样运动、与谁交互、剩余什么控制 | 现有模型选择、参数假设、对象、控制与响应提案 | 不生成最终 S/E/C/ASIL，不自行声明工程批准 |
| 具体场景因果：[ScenarioFeasibilityAgent](../../../src/hara_agent/services/semantic/scenario_agent.py) | 这里的失效是否确实通过当前行为与交互形成危险 | 具体因果链、结论及所依赖条件 | 不用一次父场景结论覆盖对象或轨迹已改变的所有子场景 |
| 风险事实解释：[ScenarioRiskFactAgent](../../../src/hara_agent/services/semantic/scenario_risk_fact_agent.py) | 评分缺的语义输入，能否由已有证据解释 | 有依据的输入，或明确未找到的结果 | 不用默认值替代未找到，不自行查表定级 |

生产调用可从 [HARAApplication](../../../src/hara_agent/application.py)、[场景节点](../../../src/hara_agent/workflow/nodes/scenarios.py)和[物理调度](../../../src/hara_agent/workflow/physical_analysis.py)进入。源代码中的职责比类名更重要：例如，一次控制补全仍由 `PhysicalScenarioAgent` 执行，但它不是重新构建整条运动轨迹。

## 模型不负责的下游内容，实际由谁完成

SG 是 Safety Goal，即安全目标；Safe State 是希望系统进入的安全状态；FTTI 在本项目的时间分析链中还需要明确故障时钟、响应和适用条件，不能直接把“到碰撞还有多久”当成已成立的故障处理时间要求。这些内容与模型的控制提案有关，却不是让模型自由补一句话就完成。

| 下游内容 | 程序负责检查或生成的内容 | 为什么不能只信模型一句结论 |
|---|---|---|
| 物理数值 | 同一输入视图下的运动、接触、相对速度和时间 | 公式必须符合当前坐标、阶段及模型范围 |
| S/E/C 与 ASIL | 通过活动 `MethodContract` 执行条件匹配和评级 | 等级来自当前方法，不能由模型偏好或参考输出反推 |
| SG 意图登记 | 按已有意图及成员关联保留目标和来源 | 语言简洁不等于可以新添控制措施或批准状态 |
| Safe State 响应检查 | 当前控制是否适用，响应轨迹能否达到所提状态 | “停车”并不总是安全，例如移动目标仍可能撞上已停车辆 |
| FTTI 时间求解 | 在明确的故障时钟、响应模型和条件下求时间边界 | 首次接触时间、可响应窗口和正式时间要求不是同一个量 |
| Excel 投影 | 将现有身份、结果、状态和关联写入模板 | 展示层不能通过改文字或填值改变风险结论 |

这些职责继续使用现有确定性或受方法约束的下游入口，不因某个单元格未完成就新增模型任务。详细数据路径在 wf-09—wf-12 中展开。

## 三种物理请求为何共用一个实现

物理分析最容易产生重复开销，因此先要问清“本次究竟缺哪一部分”。一条轨迹已经计算出来，只缺驾驶员手动制动是否受该故障影响时，再把完整对象目录、运动模型和全部参数重新发给模型，会增加成本，也增加模型改动原有效世界的机会。

当前代码通过既有 `task_scope` 决定请求范围。它不是三个独立 Agent，而是同一物理 Agent 在不同任务边界下工作。

| 本次任务 | 为什么需要它 | 发送的核心上下文 | 回来后必须保留什么 |
|---|---|---|---|
| 完整运动方案 | 当前事实尚不足以建立来源有效的轨迹 | 失效机制、对象和运行条件、适用模型目录、来源限制 | 有依据的原始条件；新假设要明确性质与作用域 |
| 控制补全 | 运动已可用，但当前人员或响应控制尚未评估 | 固定轨迹、相关人员条件、失效控制依赖、待补字段 | 原对象、原轨迹及原数值；不能顺手换成另一个世界 |
| 响应纠正 | 已返回的方案存在明确冲突、遗漏或不可达主张 | 当前方案、程序已算诊断、受影响分支和允许修改范围 | 首次返回和纠正历史；不能扩大能力或改距离制造成功 |

如果同一输入已经得到明确的“不适用”“符号条件”或“响应不能避碰”结果，恢复时不应仅因为它没有完整评级就再发同一个请求。是否继续请求要由实际缺项、当前作用域和校验版本决定。代码实例 P03 展示这个路由；P04 展示新假设如何避免混用旧值。

## 复用、合批、缓存，分别节省什么

这三个词都与效率有关，但含义不同。合批是把多个成员放进同一个请求中分别判断；复用是已有结果在证据允许的范围内用于另一个任务；缓存是同一有效请求或方案已保存，可直接读取。它们的统计必须分开，否则容易出现“一个请求返回两条判断”就被记作“完整因果复用”的误读。

| 方式 | 可以节省的工作 | 仍然必须保留的工作 |
|---|---|---|
| 精确输入去重 | 不再计算实际输入及有效来源完全相同的别名任务 | 原始身份与代表身份映射 |
| 物理方案复用 | 同一未缓解世界不重复生成模型和参数方案 | 各成员的合法实例化、控制差异与结果关联 |
| 共同证据共享 | 不重复组织、读取同一批资料 | 对不同世界分别作必要判断 |
| 有证明的因果复用 | 复用确实不依赖变化条件的因果部分或完整结论 | 依赖证明、身份重绑与正常解析校验 |
| 合批请求 | 共用一次请求的固定上下文 | 批内每个身份的独立结果，不能漏成员 |
| 有效缓存命中 | 不重复发送同一语义输入和配置的请求 | 缓存身份、版本、来源与恢复检查 |

人员位置可能影响启用或危险形成，因此不能因为两条分支算出相同速度就复制因果结论。反过来，精确任务和确定性物理输入已经一致时，也不需要等待一个覆盖全系统的抽象证明才允许复用。当前各入口只使用与本次职责对应的证明。代码实例 R01 对应驾驶员因果复用，O01 对应响应缓存，O02 对应请求账本。

## 为什么会有纠正和重试，排查时怎样分开

结构修复、语义纠正与网络重试处理的是不同问题。结构修复针对返回格式或契约不合法；语义纠正针对可解析方案中具体的物理或依赖问题；网络重试针对传输失败。它们都可能增加真实请求，但不能用一个“重试次数”掩盖原因。

例如，模型返回了合法 JSON，却把车头朝上坡时的纯重力运动写成向前，这属于语义或物理相容问题。返回内容缺少一个必需字段，则属于结构契约问题。请求超时又是第三类。定位优化时要看具体原因：减少重复上下文可能改善请求开销，却不会自动修复错误的坐标含义；扩大重试次数也不能替代生产输入传递修复。

现有有限纠正会保留首次原始响应、程序诊断和最终结果。已由计算器确定的接触或响应失败，应作为反馈交给模型判断是否存在合法的其他提案，不要求模型重新手算一遍，更不允许为了“成功”改掉原世界。

## 真实开销如何归属

模型调用的首次请求、结构修复、语义纠正和传输重试均计入适用的 Provider 账本；未记录 usage 的失败请求不能当成零 Token。输入 Token 包含 Provider 报告的缓存输入，输出 Token 包含推理 Token，二者的子项不能再次相加。文档整理、Codex 监控和离线评分没有计入 Provider 消耗。

耗时也有不同口径。单请求时间包括该请求从发出到返回的等待；多路并发时，这些时间相互重叠，因此请求耗时相加通常大于阶段墙钟时间。阶段墙钟时间还可能含检查点保存、恢复或等待。分析优化收益时，需要同时看请求量、单次输入、纠正原因、并发利用和真实阶段耗时，不能仅凭某个 Token 比例换算整轮会快多少。

最新五份结果来自此前全量加定向修订。当前定向账本不是五份项目从头运行的成本总和；文档更新也没有重新调用 Provider。准确数字、计数边界和未记录消耗的限制见“时间、Token 与复用”章节。
