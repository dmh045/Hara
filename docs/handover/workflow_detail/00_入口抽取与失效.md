# 工作流详解：入口、抽取、引导词、失效与来源基础场景

本篇对应原可视化报告的 **wf-00—wf-04**，保留原步骤编号。原报告以 `652f0774` 和 2026 年 10 月 v8 运行作为历史背景；下文以生产修复提交 `d6a400e` 的实际实现为准，交接文档起点为 `4429a2d`。历史“9 个功能、61 个失效、3 个基础场景”不是程序固定配置，也不是更换输入后的数量指标。“代码事实”说明当前实现；“解释例子”仅解释字段，不能视为新增项目事实或真实模型验收结果。

## wf-00 解析活动方法，建立运行身份和执行入口

### 真实调用链

CLI 的 `main()` 解析 `analyze` 后进入 [HARAApplication.run()](../../../src/hara_agent/application.py)。应用先执行 [RunConfig.validate()](../../../src/hara_agent/config/run_config.py)，再由 [MethodSourceResolver.resolve()](../../../src/hara_agent/method_sources/resolver.py) 解析方法。显式提供 `template_path` 时，模板经 `TemplateRoleCompiler.compile_method()` 形成方法与报告契约；没有显式模板时，先编译报告布局，再将 `report_contract` 传给 `YamlBaselineCompiler.compile()`。最终都进入同一个 `MethodContract` 和 [build_hara_agent_graph()](../../../src/hara_agent/workflow/semantic_graph.py)，不是 YAML 专用的第二套评分运行时。

### 字段如何产生和流转

应用对 Item 文件字节计算 SHA-256，将 `project_input_sha256` 注入本次方法元数据副本，不改写方法资产。状态中的 `method_contract` 保存 `template_hash`、契约／编译器版本、编译状态、`engineering_rules_compiled`、`source_kind`、`method_source_hash` 和 `report_template_hash`。随后装配语义任务、风险服务、检查点仓库、审核记录器及报告器。引导词以包含定义和来源的对象传递，不能只留下名称。`HARAState` 是节点共享状态；阶段名表示接下来要执行的节点，不表示同名业务已经完成。

### 输入／输出字段与来源

| 输入或产物 | 字段 | 含义 |
| --- | --- | --- |
| 项目与模式 | `item_path`、`operating_mode`，可选显式速度及来源 | 决定项目身份和分析范围，不从模板示例补事实 |
| 方法来源 | 显式模板或 `method_baseline_path` | 编译引导词、场景方法、S/E/C 与 ASIL 规则 |
| 报告布局 | `report_template_path`、`output_path` | 规定工作簿展示，YAML 模式下布局哈希与方法哈希独立 |
| 运行控制 | `run_id`、`resume`、`max_workers`、样本范围与预算 | 控制任务、留存和恢复，不改变方法数值 |
| 统一输出 | 方法引用、初始化状态、执行图与服务 | 供后续节点沿同一路径执行 |

### 精确分支／错误去向

缺文件、非法扩展名／Run ID、无效样本范围在配置阶段抛错。方法为 `NOT_READY` 或没有编译工程规则时，解析器拒绝并附阻断诊断，不交给模型补规则。新有界样本若检查点、账本、报告或审核目录已存在，也会拒绝以保护历史。首次有界运行会在 `MALFUNCTIONS` 之前停下生成 `bounded_sample_scope_preview`；这只是范围预检，不能宣称已经物理／因果验证。后续只有发布门禁因待审核中断且 `allow_draft=True` 时，应用才走草稿出口，保留待审核状态。

### 是否 LLM／请求粒度／上下文

本步骤的编译、哈希、校验和装配不请求 Provider。创建客户端也不等于已经发送请求。普通运行默认最多 8 个工作线程；有界样本受 `RunConfig` 约束使用 1 路。`provider_attempt_limit` 会使运行进入有界模式；普通 8 路全量 CLI 不会自动获得一个硬上限账本。其他硬预算执行方式通过既有客户端注入共享 `ProviderAttemptBudget`，不能将并发数当预算或在子运行中重置账本。

### 缓存恢复

恢复先载入检查点，再重读当前 Item 并重算来源选择指纹；非初始化阶段必须匹配保存的来源选择与输入身份。有界运行还检查 `sample_scope()` 和 `bounded_source_context`。模板绑定缺失或方法哈希不一致会拒绝恢复，不能改保存哈希强行跳过。[WorkflowGraph.run()](../../../src/hara_agent/workflow/graph.py) 在预算耗尽时恢复最后原子提交状态，记录额度与账本路径后停止。普通异常则记录失败并抛出，不伪装成运行完成。

### 具体示例

解释例子：同一输入使用 FUSA YAML 和布局甲导出，后来想改布局乙。方法规则与展示模板属于不同身份，不能混用哈希；应按既有离线报告重建工具的兼容条件处理，而不是修改旧检查点。另一个例子是“文件名仍为 Item.pdf，但正文已换成新项目”：字节哈希已经改变，旧工程决定与派生结论不能因名称相同继续沿用。

### 开发排查与现有测试

查 `RunConfig.validate()`、`MethodSourceResolver._ready()`、`HARAApplication.run()` 的恢复检查，核对 `method_contract_compiled`／`bounded_sample_configured`。相关测试：[有界入口](../../../tests/unit/test_bounded_production_run.py)、[项目输入复用](../../../tests/unit/test_project_input_reuse.py)、[YAML 编译](../../../tests/unit/test_yaml_baseline_compiler.py)、[模板角色](../../../tests/unit/test_template_role_contract.py)。`doctor` 是零 Provider 的编译／配置检查，不证明 API 余额、模型可用性或分析质量。

## wf-01 读取原文，联合抽取事实与功能，再按缺口补查

### 真实调用链

[build_semantic_frontend_graph()](../../../src/hara_agent/workflow/semantic_graph.py) 的 `INITIALIZE` 节点调用 [read_item_document()](../../../src/hara_agent/workflow/nodes/extraction.py)：`DocumentReader.read()` → `select_source_blocks()` → `EXTRACT`。随后 [extract_item_artifacts()](../../../src/hara_agent/workflow/nodes/item_artifacts.py) 调用 `ItemArtifactExtractionAgent.extract()`，按缺口调用 `ItemSupplementAgent`、`TargetedProjectFactExtractionAgent`，归一化来源作用域，写入 typed 事实与功能，再转入 `FUNCTIONS`。

### 字段如何产生和流转

[DocumentReader](../../../src/hara_agent/services/extraction/document_reader.py) 将 DOCX 按段落与表格行读取，保存 `block_id`、`kind`、`location`、`text`、`section_path`。PDF 读取层仍按有文本的页形成 `PAGE-xxxx` 块；后续证据路由在页内组织可追踪片段，没有通用 OCR。状态保留 `raw_blocks`、选中的 `blocks`、拼接 `text`、来源路径／ID、`item_sha256` 与 `source_selection`，所以“未送入分析”与“从未读取”能够区分。

主响应经 [normalize_core_item_artifacts()](../../../src/hara_agent/services/semantic/core_item_artifact_contract.py)、功能校验和来源对齐，生成 [ItemDefinitionFacts](../../../src/hara_agent/models/item_facts.py) 与 [FunctionDefinition](../../../src/hara_agent/models/item_definition.py)，分别序列化到 `item_definition['typed']` 和 `state.functions`；原文不被这些结构替代或删除。

### 输入／输出字段与来源

核心事实包括系统描述、边界、模式，以及地点／道路／天气／路面允许条件。速度进一步由 `speed_envelopes` 保存模式、范围、条件、单位和来源；`risk_facts` 保存方法所需的中性事实。功能包含 ID、名称、输出、描述、前提、触发、ODD 限定、回退、后果、来源、状态与置信信息。

`odd_scope_evidence` 表达某条件只适用于哪些功能／模式：全局列表是允许条件的并集，不是每个功能共同受限。[ItemDefinitionFacts.for_scope()](../../../src/hara_agent/models/item_facts.py) 后续按同一谓词过滤条件及证据，原 typed 对象不变，避免某子功能限制污染其他功能。

### 精确分支／错误去向

存在唯一明确的整车功能表／列表时，该清单决定功能成员，不可随意增删拆并；其他段落只补成员条件。没有明确清单时，才从全文抽取系统拥有的可观察输出，用户按键、标题、阶段或任务周期不直接作为功能。主契约最多 20 个功能。结构、输出语义、来源问题进入各自已有的有限修复；若限定为只修来源，修复却改变工程字段，会抛错。来源只能采用当前实现支持的有界格式／定位修复，不以模糊相似引用冒充来源。

核心缺项触发 `odd_repair` 局部检索，方法所需事实按类型和请求模式补查。未检索到证据时保留诊断，不用常识补值。核心仍缺失或合并有警告时保留 `PENDING` 和 `pending_reviews`；局部缺口不必立即停止所有节点，但后续边界和发布门禁继续检查。源码可把完整且来源有效的输入事实归一为 `FINALIZED`，这不批准故障假设、控制能力或安全目标。

### 是否 LLM／请求粒度／上下文

文档读取和路由是 Python。主请求 `extract_core_item_artifacts` 一次返回事实和功能，使用 `item-artifacts-v11-qualified-odd-scope`，不按每个功能重读全文。但补抽、事实批次和有限修复会增加实际 HTTP，不能把“联合一次”理解成全阶段固定一次请求。ODD 补任务最多按 2 路，定向事实最多按 3 路组织，同时受外部并发限制。输出预算取专用配置和客户端上限的较小值，真实 Token／重试以客户端账本为准。

### 缓存恢复

`ValidatedArtifactCache` 的有效缓存键包含原文、来源选择指纹／策略版本、主／补／定向提示版本、schema／路由版本、Provider 路由／模型／抽取思考配置、所需事实规格和请求模式。原始候选另存隔离区，可供当前校验重放，不能命中即认定有效。有效核心命中后仍校验功能清单和来源，失败按无有效缓存处理。补抽批次完成后保存；`extract_timing` 区分路由、补查、合并、缓存和 LLM 调用，便于判断网络与本地开销。

### 具体示例

解释例子：原文写“训练最高 15 km/h、执行最高 7 km/h、任务周期 10 ms”。速度要按阶段绑定；10 ms 不是制动响应延迟。只请求执行模式时，定向速度抽取优先该模式，不能将训练上界补到执行场景。若“垂直车位”只在 F5 条件下出现，就保留 F5 作用域，而不是扩大为所有功能限制；之后 Agent 提出的斜列几何仍是分析假设，不能提升为源文许可。

### 开发排查与现有测试

先查 `raw_blocks`／`blocks` 和排除原因，再看主响应、候选缓存、`function_source_guard`、`routing_diagnostics` 与补查结果，最后比较 typed 字段。相关测试：[来源选择](../../../tests/unit/test_document_source_selection.py)、[核心契约](../../../tests/unit/test_core_item_artifact_contract.py)、[来源锚定](../../../tests/unit/test_item_artifact_source_grounding.py)、[作用域](../../../tests/unit/test_qualified_odd_scope.py)、[定向事实](../../../tests/unit/test_targeted_project_fact_extraction.py)、[证据路由](../../../tests/unit/test_item_evidence_router.py)。当前不保证任意扫描 PDF 的表格自动恢复，也不能从未提供的外部引用规格提取已确认能力。

## wf-02 将每个功能与活动引导词逐项配对并保留三类去向

### 真实调用链

`FUNCTIONS` 节点先执行项目上下文预检，再进入 [assess_guidewords()](../../../src/hara_agent/workflow/nodes/hazop.py)。该节点按功能组织并行工作，每个未恢复的功能调用 [GuidewordApplicabilityAgent.assess()](../../../src/hara_agent/services/semantic/guideword_agent.py)，一次评估这个功能与所有活动引导词。结果合并到 `state.guideword_assessments`，转入 `HAZOP`。这里的阶段转换表示适用性分析已完成、下一步生成失效；不是程序再次运行一套独立 HAZOP 引擎。

### 字段如何产生和流转

功能来自上一步的 typed 对象，包含实际输出、输出组成、前提、触发、ODD 与回退。引导词来自活动 `MethodContract.guidewords`，其稳定 ID、名称、定义和来源不能互相替代。模型响应中的 `guideword` 字段必须填写稳定 ID，程序通过 `_bind_provider_identity()` 绑定回展示名称，形成 [GuidewordAssessment](../../../src/hara_agent/models/malfunction.py)：`function_id`、`guideword_id`、`guideword`、`applicable`、`rationale`、`disposition`、来源、状态与置信信息。最终按输入引导词顺序排序，不按模型返回顺序改变身份。

### 输入／输出字段与来源

| disposition | applicable | 后续用途 |
| --- | --- | --- |
| `DOWNSTREAM_CANDIDATE` | `true` | 语义适用且有可信车辆级危险潜力，满足完整性与状态要求后生成失效 |
| `NOT_APPLICABLE` | `false` | 偏差与该功能输出不匹配，保留具体理由，不生成对应失效 |
| `NO_CREDIBLE_HAZARD` | `true` | 偏差在语义上成立，但当前依据不足以构成可信车辆级危险；保留理由 |

`PENDING` 是审核／完整性状态，不是第四种 `disposition`。来源和状态由程序从功能证据传播，模型禁止自行返回 source／status。当前 `_parse()` 在理由、来源存在且功能为 `FINALIZED` 时传播 `FINALIZED`，否则为 `PENDING`。这是现有输入证据链的实现，不意味着后续具体故障、危险事件或 ASIL 已获工程批准。

### 精确分支／错误去向

输入引导词 ID／名称必须非空且唯一；返回必须每个 ID 恰好一次，不得缺项、重复或自增。布尔值与三类去向矛盾时，已有单项挽救请求只修该项一次；仍错则抛契约异常。缺理由可留下语义不完整的待审核记录；但 ID 或布尔类型错误不能伪造成有效组合。输出截断时，Agent 只在客户端允许更大上限时作一次有界重试；客户端上限不高于初次预算就直接抛错。

几乎所有引导词都适用时，提示在同一次回答内自检，节点另记 `guideword_blanket_applicability_observed` 或 `guideword_high_applicability_reviewed`，不会为了降低比例再增加付费审核。全局 `guideword_global_coverage_audited` 仅记录未匹配引导词，不强迫某功能匹配。节点把不完整和完整但待审核的结果分别加入 `pending_reviews`，保留负面判断，不用后续失效数组覆盖这些记录。

### 是否 LLM／请求粒度／上下文

LLM 判断适用性；Python 控制笛卡尔配对覆盖、身份、类型和去向一致性。当前版本为 `guideword-applicability-v12-repair-identity-shape-zh-v1`。输入只带当前功能上下文与活动引导词定义，不重新发送整份 Item，也不预先生成完整危险事件。复合输出必须逐一考虑 `canonical_output_components`，不能因为看见一个 HMI 提示就忽略同一功能的车辆控制输出。

例如 9 个功能 × 8 个引导词是 72 个语义判断；通常初始任务按功能组织为 9 项，而非 72 个 HTTP。截断、单项修复和网络重试另计实际请求，缓存／检查点恢复可能进一步减少本次请求。不能由矩阵格数推算 Token。

### 缓存恢复

本节点有明确的逐功能持久批次：`item_definition['guideword_assessment_batches']`。`_batch_key()` 包含功能完整结构、引导词对象、提示版本、Provider／模型和引导词思考配置。每个结果完成后通过 `save_batch()` 保存和检查点提交；中断恢复只调度未完成的功能。已提交批次若 key 不匹配，直接要求新 Run ID，不偷偷重用。阶段完成后汇总正式数组并移除临时批次。它与 HTTP 原始响应缓存职责不同：前者保存已解释的功能结果，不能作为所有阶段都存在同样恢复能力的证明。

### 具体示例

解释例子：“输出转向角”与 `More` 可以形成角度幅值过大候选；“用户确认按钮”的某个输出若没有可定义的反向量，`Reverse` 可能不适用，但须依据方法定义判断。若功能实际同时包含控制和提示，不能只凭“提示没有幅值”把整个 `More` 排除。即使所有八项都判适用，也不代表八个危险事件必然成立；后面还要生成具体失效、选择工况、验证故障到轨迹和危险事件的因果。

### 开发排查与现有测试

先核功能与引导词完整输入，再查 `assessments` 原始 ID、`disposition`、单项挽救记录、批次 key 和覆盖审计。相关测试：[引导词矩阵契约](../../../tests/unit/test_guideword_matrix_contract.py)、[逐功能中断恢复](../../../tests/unit/test_guideword_checkpoint_resume.py)、[项目上下文预检顺序](../../../tests/unit/test_project_context_preflight_order.py)。不要将 `NO_CREDIBLE_HAZARD` 与“没有方法规则”混为一谈，也不要把没有生成下游失效都归因为模型漏项。

## wf-03 从通过的功能偏差生成失效、功能影响与上游危险主张

### 真实调用链

`HAZOP` 节点调用 [derive_malfunctions()](../../../src/hara_agent/workflow/nodes/malfunctions.py)，按功能筛选对应的 `GuidewordAssessment`，再调用 [MalfunctionHazardAgent.generate()](../../../src/hara_agent/services/semantic/malfunction_agent.py)。Agent 生成与修复受约束候选，节点再次执行 `malfunction_guideword_gate`，确定性重编号，通过 `FailureModeSelectorResolver.resolve()` 解释方法分类，保存到 `state.malfunctions`，转入 `MALFUNCTIONS`。后者才是后续场景、物理、因果等复合节点的入口。

### 字段如何产生和流转

[MalfunctionCandidate](../../../src/hara_agent/models/malfunction.py) 保存 `malfunction_id`、`function_id`、`guideword_id`／名称、`description`、`functional_effect`、`vehicle_level_hazard`、至少两段 `causal_chain`、来源、状态、置信信息和分类。`derivation` 进一步保留 `function_refs`、逐字引用的功能主体 `subject`、单一偏差量 `quantity`、推导理由 `basis`、额外 `assumptions`。因此可以区分：功能是源事实，“该功能输出可能过大”是分析前提，“需要假设某实现细节”是尚待审查假设。

模型 ID 不作为最终权威 ID。节点按当前功能顺序生成 `MF-{function_id}-{序号:03d}`，原 ID 留在 `model_local_id`，并记录 `malfunction_identity_normalized` 映射。分类解析结果保存为 `selector_resolution`，不因为分类枚举里有“执行器”就证明项目实际采用某硬件。

### 输入／输出字段与来源

输入为当前功能上下文、已准入引导词及其适用理由，以及活动方法允许的部件／失效类型枚举。输出层级有严格区别：`description` 写故障偏差，`functional_effect` 写直接行为影响，`vehicle_level_hazard` 写车辆级危险状态；人员死亡、伤害等级、S/E/C/ASIL 和批准状态都不是该层应生成的内容。来源由 `resolve_malfunction_sources` 绑定功能依据，只证明推导起点可追溯，不证明 Item 原文已经声明这种故障会发生。

### 精确分支／错误去向

`generate()` 的准入条件同时要求 `applicable=True`、语义完整、`DOWNSTREAM_CANDIDATE`、状态为 `FINALIZED`。没有准入项就零请求返回空数组，并区分 `no_applicable_guidewords`、`no_complete_applicable_guidewords`、`no_credible_hazard_guidewords`。因此不能将“功能没有失效”统一解释为遗漏。

有准入项时先生成，再检查每个引导词至少有一条合法候选。缺项或被拒项先合并做一次覆盖修复，再对剩余引导词各做一次定向修复；不是无限循环。合法部分保留，重复描述和非法分类按现有校验过滤。仍缺覆盖则抛错，不用空字符串或其他引导词替代。节点还重验功能／引导词配对，防止替代 Agent 绕过解析器。所有新候选 `status` 必须是 `PENDING`，完整结构不意味着工程批准。

### 是否 LLM／请求粒度／上下文

当前提示版本 `malfunction-hazard-v9-explicit-candidate-fields`。初始请求按一个功能及其全部准入引导词组织，任务名 `derive_malfunctions_and_hazards`，携带该功能字段、适用理由和受治理分类，不携带整份文档或下游完整物理目录。一个引导词可以产多条不同偏差，但每条只针对可区分的单一量；不能用“转角或转向速率过大”合并两个量。泊入／泊出可共享一个失效定义，不机械展开操作阶段 × 偏差量；具体操作差异后续按真实工况判断。

### 缓存恢复

本节点使用图阶段检查点，但没有复制引导词节点的逐功能 `guideword_assessment_batches`。`derive_malfunctions()` 合并完整批次后才写正式数组；开发者不能假设中途每个功能结果都已独立提交。预算／异常恢复应先看最后实际提交阶段与审计，不能单凭终端某个“函数返回”就声称全部结果已保存。修复调用、请求 ID／usage、被拒项与缺项记录保存在 Agent 审计中；当前生产是否有外层原始响应留存，应以实际客户端和运行目录核对，不虚构通用缓存命中。

### 具体示例

解释例子：来源功能是“输出目标转向角”，`More` 可推导“目标转向角幅值高于需要”，但不能无依据升级成“EPS 电机硬件失控，且人工转向通道同时失效”。若后文真的有硬件及独立控制描述，可通过明确来源约束分析；没有则列为假设。车辆级危险可写偏离预期轨迹、侵入相邻区域，但是否在某距离、某对象下碰撞，必须到后续物理与因果步骤验证，不能本步直接断言严重伤亡。

### 开发排查与现有测试

核对上游三类去向和状态，再查 `derivation` 主体是否逐字引用、偏差量是否单一、因果链是否至少两段，最后检查枚举解析与重编号。审计包括 `malfunction_hazard_candidates_generated`、`malfunction_guideword_gate_validated`、`malfunction_derivation_summary`；日志区分初始有调用的功能数与含修复的实际调用数。相关测试：[准入边界](../../../tests/unit/test_malfunction_guideword_gate.py)、[覆盖修复](../../../tests/unit/test_malfunction_coverage_repair.py)、[来源作用域](../../../tests/unit/test_malfunction_source_scope.py)、[响应信封修复](../../../tests/unit/test_llm_malfunction_envelope_repair.py)。

## wf-04 按项目模式和 ODD 建立有来源的基础场景

### 真实调用链

`MALFUNCTIONS` 复合节点开始前，由应用注入的工厂调用 [HARAApplication.prepare_scenario_candidates()](../../../src/hara_agent/application.py)：恢复 typed `ItemDefinitionFacts` → `resolve_project_speed_context()` → [MethodScenarioCandidateService.generate()](../../../src/hara_agent/services/analysis/method_scenario_service.py)。[semantic_graph._scenario_candidates()](../../../src/hara_agent/workflow/semantic_graph.py) 接收候选和审计，写场景绑定缺口、候选记录与 `scenario_candidates_prepared`。这些基础候选随后交给失效条件化，不直接变成最终风险记录。

### 字段如何产生和流转

首先根据选定 `operating_mode` 取得对应速度上下文，并将项目事实投影到该模式。`generate()` 遍历活动方法的场景维度，`_project_values()` 选择该维度的项目允许值，`_text_binding()` 调用 Atom 解析器，以项目值、有效别名与方法目录形成绑定。每个绑定保留 `project_value`、`method_value`、`resolution_status`、`unresolved_reason`、候选 Atom、来源与 `filled_dimensions`。不能用一个展示字符串代替这些结构。

VDA Atom 目录模式下，`WHERE` 来自项目地点及明确的室内／室外环境限定，`ROAD` 来自路面条件；`EGO_ACTION` 使用当前模式，`EGO_DYNAMICS` 使用速度范围约束。明确的室内／室外替代条件可以细化通用停车场父标签，不能将所有通用地点直接改名为室外来制造覆盖。按失效的后续处理还会进一步投影功能作用域；本步按模式的投影不能被描述为已经完成所有功能适用性判断。

### 输入／输出字段与来源

输出是 [ScenarioCandidate](../../../src/hara_agent/models/scenario.py)，关键字段如下。

| 字段 | 产生方式与用途 |
| --- | --- |
| `scenario_id`、`semantic_fingerprint` | 方法哈希、场景契约版本与结构化绑定确定性生成，基础 ID 为 `SCN-METHOD-…` |
| `facts.method_scenario_dimensions` | 完整维度绑定，保留解析成功、歧义和缺口 |
| `facts.ego_speed_constraint` | 源模式速度范围，不等于故障后速度上限 |
| `facts.ego_speed_kph` | 仅显式项目点值路径直接绑定，不用范围上界伪装唯一实际速度 |
| `scenario_atom_ids`、`exposure_context` | 已解析 Atom 及方法 Z/F 依据；未解析项不能伪造为已选 Atom |
| `context_resolution` | 速度、维度、相容性、风险事实绑定与逐功能上下文 |
| `fact_provenance`、`sources`、`status` | 项目／方法／推导来源及审核性质，不靠自然语言相同推定等价 |

`_function_phase_bindings()` 保留功能前提、触发、ODD 谓词、输出、来源和速度约束。如果没有结构化阶段事实，会明确写 `PENDING_NO_STRUCTURED_PHASE_FACT`，不把功能名称自动当作已证实阶段。若有已批准的覆盖规则，才用其进行相应评价。

### 精确分支／错误去向

[ProjectFactResolver.resolve_speed_envelope()](../../../src/hara_agent/services/analysis/project_fact_resolver.py) 要求匹配明确模式，多个同模式范围有歧义时拒绝；不能用 `parking` 猜究竟是搜索还是控车。聚合范围仅在显式允许时使用，且不能把多个上下文范围压成一个。草稿路径只在没有任何来源速度范围时，允许返回 `NoSourceSpeedEnvelope` 和空约束，供后续假设分析；它不吞掉已有但不匹配、歧义或部分缺失的范围，也不自动补 7 km/h。

无项目值时生成 `NO_ITEM_FACT` 待解析绑定，不扩回整个方法目录。`_binding_sets()` 选择第一个具有多个来源值的维度为锚点，沿锚点形成候选；其他多值且未唯一绑定的维度保留 `AMBIGUOUS_BINDING`，不做全维笛卡尔积。有未解析维度时，相容性评价保持待定；已编译规则明确 `DROP` 的组合才排除，`KEEP_RARE` 保留，冲突与缺规则保留具体诊断。最终状态还结合速度审核性质和项目来源，不以“对象能创建”当作全场景已完成审核。

### 是否 LLM／请求粒度／上下文

本步不调用 LLM，不让模型自由生成基础 ODD。绑定、有限展开、约束和来源风险事实接线都由程序完成，所以生成若干基础候选不对应若干付费请求。后续物理 Agent 负责的是允许范围内的具体对象、轨迹和条件性参数假设，二者不能混为“全部场景都来自 LLM”。同样，基础允许列表有平行／斜列车位，只证明来源许可保存；它是否形成真实影响运动的几何、是否完成因果分析，需要后续独立证据，不能在此宣称覆盖已完成。

### 缓存恢复

基础生成是确定性过程，没有为它新建 Provider 缓存。其结构化绑定进入场景指纹，来源、方法或语义输入改变会影响下游任务身份。`prepare_scenario_candidates()` 将本次输入 SHA 继续绑定到候选服务的方法副本，项目专属决定按输入作用域匹配。普通入口保留完整父候选供后续代表焦点分配；样本父范围先记录允许 ID，再在既有条件化／归并后按 lineage 筛选，避免“抽样顺序改变同一候选的焦点”。这项调度见后续步骤，不代表本步额外增加场景维度。

### 具体示例

解释例子：项目允许室内、室外两类地点，路面又有干燥和湿滑。如果地点是多值锚点，本步可以形成两个有来源的地点上下文，而没有依据将路面任意两两配对时，路面保持待定；后续在既有有界代表组中处理必要差异。两个地点标签本身不证明两套危险机制都已算过。再如正常执行速度为 0—7 km/h，这里保存范围及来源，后续驱动异常可以用相容假设推导当前行程可达速度，既不能统一截为 7，也不能强迫全部故障速度超过 7。

### 开发排查与现有测试

按 `speed_resolution` → `dimension_bindings` → `scenario_binding_gaps` → `dimension_compatibility` → `fact_provenance` 排查。审计含 `combination_strategy='primary_dimension_anchor_with_pending_unbound_dimensions'`、未解析候选数、约束排除／罕见／冲突数、缺失或矛盾风险事实类型；要逐层统计，不用 Excel 主表行数代替覆盖或付费工作量。相关测试：[模式和速度接线](../../../tests/unit/test_application_project_context.py)、[来源锚定而非笛卡尔积](../../../tests/unit/test_scenario_ontology_binding.py)、[Atom 身份解析](../../../tests/unit/test_method_atom_resolver.py)、[来源范围与环境覆盖](../../../tests/unit/test_full_run_convergence.py)、[ODD 作用域](../../../tests/unit/test_qualified_odd_scope.py)。当前不保证基础生成已经穷尽任意项目所有风险条件；未形成的交互与几何必须在覆盖证据中单列，不能用允许列表长度充数。
