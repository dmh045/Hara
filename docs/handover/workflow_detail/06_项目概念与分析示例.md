# 项目概念、分析示例与文档使用

## start-purpose 项目定位与交付边界

一份自动泊车功能规格通常说明车辆能做哪些动作、在什么条件下工作，以及哪些条件下不能工作。安全分析还需要回答另一组问题：如果某个功能出了故障，车辆可能发生什么危险？什么环境下会发生？伤害可能有多严重？人还有没有机会避免伤害？最终需要提出什么安全目标？

这就是本项目组织的 HARA 分析。HARA 是 **Hazard Analysis and Risk Assessment，危害分析和风险评估**。这里的“危害”不是程序报错，而是车辆功能异常可能造成的人身伤害风险。程序报错、输入缺项和模型不适用是分析过程中的问题，需要记录；它们本身不是一条车辆危害。

本项目把产品文档、分析方法和报告模板连接起来，自动完成资料整理、候选场景构建、物理分析、因果判断、风险计算及报告输出。结果是可供工程师审核的 Excel 及其证据。它没有把工程审批自动化：一个字段有数值，只说明在当前条件和方法下得到了计算结果，还要看这些条件是什么、依据是否适用、审核是否完成。

### 交付材料的三个层次

**第一层是技术文档。** 即当前文档及其源章节，说明系统怎样工作、代码在哪、如何运行、如何排查和目前还缺什么。业务解释与实现细节分层组织，可以先理解分析流程，再按代码索引核对实现。

**第二层是可维护的工程实现。** 包括源码、治理后的方法资产、测试和报告模板。源码说明程序实际怎样执行，方法资产说明当前采用什么分析与评分规则。文档中的17段源码摘录带固定提交和行号，可以将文字解释对应到实际实现。

**第三层是运行证据。** 包括输入原文、模型原始返回、检查点、请求账本、计算追踪和 Excel。它们回答“某次运行到底发生了什么”。只把代码仓库交给下一位同事，不等于完成了运行证据移交。当前便携包包含五份最新 Excel 和证明文件；大型检查点及完整响应需按资产清单另行移交。

### 本文中的“当前结果”是什么意思

本文使用 AVP、IPA-High、IPA-Main、RPA、rTPA 五份输入截至2026-11-23的完整修订结果，文档核对日期为2026-11-24。五个标签用于区分实际输入及运行证据，不是程序根据名字选择的五套评分器。不同文件的功能、模式、限制及来源条件不同，因此各自的分析数量和缺口也不同。

后文出现的2389个活动风险，是五份结果的合计；并不是刚运行了一份包含2389条的新报告。文档这次扩写也没有重新调用模型、重新评分或增加工程批准。理解这个时间和范围边界后，再看结果表才不会把“新写的说明”当成“新完成的验证”。

## start-input 三类输入及权威来源

“产品文档”“评分方法”和“Excel模板”可能都包含速度、场景和表格，但用途不同。相同的文字或数字出现在不同来源里，并不具有相同的工程含义。

| 输入 | 用通俗的话解释 | 一个例子 | 不能拿它做什么 |
|---|---|---|---|
| 产品文档，常称 Item Definition 或 Item | 告诉程序这次分析的系统是什么、功能和边界是什么 | 某模式允许自动转向；某条件下需要驾驶员持续操作 | 不能因为原文没给碰撞距离，就假装原文已经证明了一个距离 |
| 方法来源 | 告诉程序怎样选条件、怎样计算、怎样从输入得到等级 | 某种碰撞构型使用哪个严重度分档；某个可控性规则适用于什么范围 | 不能把参考项目中的车辆能力自动变成本项目事实 |
| 报告模板 | 告诉程序结果写到哪里，怎样保留工作簿布局和关联 | 主表的场景、S/E/C、ASIL和明细区域怎样排列 | 改单元格位置或标题，不等于改变评分规则 |

方法可以来自显式方法模板，也可以来自受治理的 YAML 资产。YAML 是一种便于维护结构化规则的文本格式。两条来源最后都编译成同一种 `MethodContract`，即程序实际执行的方法契约。**“契约”在这里指双方约定好的数据结构和规则接口，不是额外一份人工合同。** 运行时执行这个契约，不由每个评分函数各自打开 YAML、各自解释规则。

报告布局则编译成 `ReportContract`。在 YAML 方法模式下，方法文件和报告工作簿有各自的内容哈希；换了展示模板，并不意味着应该悄悄换一套风险规则。`doctor` 命令用于预先检查这些输入能否被当前程序识别和编译，不能把“doctor通过”理解为已经完成车辆项目的 HARA。

程序对文件计算内容哈希，可以理解为按文件内容生成的指纹。文件名改了但内容没变，和同名文件内容被替换，是两种情况。保存内容身份是为了识别缓存、恢复和项目决定是否仍然适用，不能用文件名或“parking”这个词代替项目身份。

## start-language 业务与技术术语

下表按每个概念在分析中回答的问题组织。中文解释用于理解业务，英文名称用于对应数据结构和检索源码。

| 术语 | 它回答的问题 | 本文中的具体含义 |
|---|---|---|
| 功能 Function | 系统本来要完成什么？ | 有来源的职责、动作或输出；一个大标题不一定是一个功能 |
| 引导词 Guideword | 正常功能可能怎样偏离？ | 例如“没有”“过多”“反向”等偏差方向；先判断适用，再生成失效 |
| 失效模式 Malfunction | 哪个功能以什么方式出了问题？ | 例如驱动指令大于需求；不同控制层级不能只因文字相近而合并 |
| 危险行为 Hazardous behavior | 车辆因此出现什么危险表现？ | 例如非预期加速。它还不是完整的具体危险事件 |
| ODD／运行范围 | 系统在哪些条件下工作？ | 模式、场所、道路、天气和限制之间的关系；不是一串随意相乘的标签 |
| Atom／条件单元 | 程序怎样识别一个可用于方法计算的场景条件？ | 方法中的结构化条件身份，例如某类道路条件；不只是生成文字里的关键词 |
| 父场景 | 具体分析从哪个背景条件出发？ | 保存来源运行条件，后续可以形成不同对象、轨迹或驾驶员分支 |
| 候选场景 | 这个组合值得进一步分析吗？ | 待分析的工况；“候选”不代表已经证明会形成危险 |
| 物理方案 | 怎样把危险表现变成可计算的运动问题？ | 选择对象、模型、参数、坐标、阶段及剩余控制能力，明确假设和范围 |
| 参数取点 | 同一个范围选哪些代表值做计算？ | 比如一个加速度范围的有限取点；不是自动增加了同样数量的独立功能 |
| 因果判断 | 这个故障是否导致当前工况中的危险？ | 把故障、车辆行为、交互和危险事件连起来；算出会接触，并不自动证明故障导致了它 |
| 风险事实 RiskFacts | 计算还需要哪些中性的输入？ | 对象、条件、能力等事实或明确标识的假设；不是模型直接给出的S/E/C答案 |
| S／Severity | 可能造成多严重的伤害？ | 按活动方法和相应物理输入得到严重度等级 |
| E／Exposure | 车辆处于相关运行情境的暴露程度如何？ | 按已绑定条件及方法聚合；不是故障发生概率，也不是模型置信度 |
| C／Controllability | 有关人员在该工况下有多大机会避免伤害？ | 需要核对可用控制、人员、时间和适用方法，不能只凭一个TTC数值 |
| ASIL／QM | 该危险事件的风险分类是什么？ | 用同一分支的S/E/C查活动矩阵；QM也是一个分类结果，不表示“没有分析” |
| SG／Safety Goal | 为避免相关危险，应当达到什么安全意图？ | 与实际风险成员关联的安全目标，不是把整个场景原文再抄一遍 |
| Safe State／安全状态 | 系统希望最终处于什么安全状态？ | 还需要证明适用控制能够到达该状态；“停车”不自动等于所有对象都安全 |
| TTC／接触时间指标 | 按这条轨迹，什么时候首次接触？ | 依赖对象、坐标和时间起点；不等于驾驶员或系统还可等待同样久 |
| FTTI相关分析 | 在当前故障及响应条件下，时间约束是什么？ | 程序区分条件性响应启动边界、时钟映射和正式审核；不能把TTC直接改名 |
| Provider | 谁在实际执行模型请求？ | 应用连接的模型服务；费用与开发助手本身的消耗分开 |
| Checkpoint／检查点 | 中断以后从哪里恢复？ | 已保存的业务状态；还需要核对方法、输入和缓存身份 |
| Trace／计算追踪 | 这个结果如何产生？ | 保存输入、规则、推导、中间结果和原因，用于复核而不是只看最终等级 |

英文名称保留在代码索引和必要的数据结构说明里；面向工程阅读的描述优先使用中文。类名、枚举和字段的完整含义在对应步骤中展开。

## start-walkthrough 端到端分析示例

下面是**教学例子，不是五份项目新增的实测事实、真实模型返回或正式评级**。它故意不预先给出S/E/C字母，因为正式评级必须以当前项目的输入和方法计算为准。

### 第一步：先确定原文说了什么

假设产品说明中存在“在某泊车执行模式下输出驱动控制指令”的功能。程序保留该段的来源位置、适用模式和前提条件，再形成结构化功能。如果同一页另有训练模式的速度上限，那是另一阶段的事实，不能直接塞进执行模式。

这一步得到的是“系统本来要做什么”。它还没有说功能会以什么方式失败，也没有给出碰撞速度。

### 第二步：从功能偏差得到一个明确失效

对驱动指令使用适用的“过多”引导词，得到“驱动指令超过当前需求”这一类失效。接着描述车辆层面的危险表现，例如非预期加速。这里必须区分指令异常和执行器完全失效，因为故障后还能不能通过另一控制路径减速，会影响后面的分析。

这一步得到的是“故障可能怎样影响车辆”。同一个失效接下来可能遇到不同对象和条件，不必只生成一条场景，也不能无理由展开所有条件的笛卡尔积。

### 第三步：建立与该失效有关的代表工况

候选生成选择来源允许且与危险机制有关的条件，例如车辆沿车位通道运动，前方存在静止对象。如果另一候选是行人横穿，就必须保留它自己的对象运动和几何关系。不能为了套用同一个计算模型，把移动行人改成静止对象。

此时得到的是“在哪种世界里分析这个故障”。来源条件、方法条件和自行提出的分析假设要分开保存。

### 第四步：把工况补成可计算的物理问题

若已有来源或方法代表规则提供了足够的有效物理输入，程序沿用已有路径。若只缺控制或响应信息，就只补对应部分。只有现有输入不足时，才调度完整的自主物理任务。

假设为了说明计算过程，选定初速1 m/s、故障后恒加速度0.5 m/s²、静止目标距离3 m，且三者在同一方向和阶段。程序可以由运动方程求出2秒到达该位置、接触时速度2 m/s。**这只是数学示例：数值由本节为教学设置，不是生产默认距离、默认加速度或车辆能力上界。** 实际方案还需要检查所选模型是否适用，是否存在车身尺寸、目标运动或其他约束。

换成范围时，结果仍带范围或取点身份；换成显式符号时，不能悄悄从父场景补回一个旧数值。否则表面上“算出来了”，实际上已经换了问题。

### 第五步：判断这个接触是否由该故障造成

物理计算只说明“按这套轨迹会发生什么”。因果判断还需要确认：该功能失效是否确实会造成这套车辆行为；与目标的交互是否能导致所描述的危险；是否存在“没有故障也会发生相同接触”的情况。

因此，算出2秒接触，不等于自动接受一条危险事件。如果因果被明确排除，要保留排除理由；如果证据尚不足，也不能把未决判断伪装成排除。

### 第六步：用同一个场景计算风险

保留的具体场景进入风险事实绑定和评分。S使用适用的伤害相关输入，E使用真实相关的运行条件，C使用当前人员和控制能力及方法适用条件。最后从同一分支的完整S/E/C元组查ASIL矩阵。

假如同一风险下还分析了另一个对象或参数点，每个分支都保留自己的元组。程序不能拿第一个分支的S、第二个分支的E、第三个分支的C拼成一条不存在的“最坏场景”。

### 第七步：形成安全目标，并说明响应和时间条件

物理与评分阶段已经检查了控制、响应和时间条件。这一步将相应结果与安全目标关联，并再次核对成员的有效提案及时间证据，沿用同一套已有计算。需要区分“希望避免非预期加速带来的伤害”和“具体如何实现安全”：能否制动、制动路径是否受同一故障影响、停止后是否还会被移动目标撞上，分别依据前面的控制与响应分析。

FTTI相关输出还要区分：当前时刻距离接触有多久、某个响应最晚何时启动仍有效、这个时间是否已经正确映射到故障起点。即使教学例的接触时间为2秒，也不能直接把2秒填为正式FTTI。

### 第八步：输出可以回查的报告

工程师先看主表，知道功能失效、具体工况、完整评级、安全目标和主要限制；需要复核时沿成员映射进入场景明细、分支评级和计算追踪。程序可以把共同描述组织在一起，但不能因为把主表压缩了，就声称减少了同样数量的模型调用。

到这里，一条记录已经从“原文功能”走到了“有来源、有假设、有推导、有判断、有状态的报告”。问题定位也按这个顺序回查，通常比从Excel里的一个字母直接猜原因有效。

## start-result 计算结果与审核状态

第一个问题是**有没有算出数值**。第二个问题是**这个数值依据什么、是否已经获批**。这是两个维度，不能合成一个“成功／失败”标签。

例如某成员已有C2，但它依赖尚未审核的控制能力假设。这是“已有条件性数值、待审核”。另一个成员因为当前方法不支持该交互，没有C数值，这是“待评定”。两者后续工作不同：前者重点审查依据和适用性，后者先定位缺事实、缺绑定、缺模型还是缺方法。只统计 `PENDING` 的个数，无法知道是哪种问题。

同样，合法的“所选响应不能避碰”是一个计算结论，不一定是软件缺陷。要看轨迹、控制能力和计算是否一致；不能靠改距离或提高制动能力让它看起来成功。反过来，如果已有有效输入没有传到计算器，那就是程序接线问题，应当修复并重算受影响结果。

当前五份结果的缺口已经按实际原因区分。阅读统计时先看分母：是全部候选、保留的风险成员、报告审核组还是SG？它们之间有一对多和多对一关系，不应互相当作完成率分母。

## start-read 章节导航与使用方式

| 工作任务 | 相关内容 | 对应问题 |
|---|---|---|
| 项目整体评审 | 项目概念 → 主流程图 → 五份最新结果 → 当前限制 | 输入、输出、责任边界和当前完成程度是什么 |
| 审核一行HARA报告 | 工况与身份图 → wf-09至12 → 实际明细及trace | 该故障在什么世界里造成什么危险，评级和假设是否一致 |
| 部署与运行维护 | 项目概念 → 部署与恢复附录 → 资产清单 → 预算/缓存图 | 怎么准备环境、检查输入、恢复运行和定位证据 |
| 修改生产代码 | 对应步骤 → 代码实例 → 问题定位索引 → 开发测试附录 | 谁是权威实现、哪些调用者受影响、怎样验证没有破坏上下游 |
| 维护方法 | 输入权威图 → 方法与来源章节 → 编译与doctor → 固定总体回归 | 改的是规则还是接线，影响哪些工况，是否需要重新计算 |

各步骤先说明业务含义、输入、输出和边界，再给出源码及验证入口。工程评审可以沿前一层检查结论；开发维护可以从同一节进一步定位到精确源码，不需要在两套说明之间重新对应概念。

## start-firstday 运行与维护核对流程

1. **确认版本和资产。** 查看当前提交、文档基线以及五份输入对应的报告和证明文件。缺少大体积运行证据时，记录缺什么，不把“GitHub没有文件”判断为分析从未执行。
2. **先运行环境与方法预检。** 按部署附录安装依赖并运行doctor；这一步检查配置与方法编译，不产生一份新的车辆分析结论。
3. **选一个已有成员，从主表回到来源。** 找到其失效、场景身份、方案、因果、评分和SG关联。不要以Excel的当前行号代替稳定业务身份。
4. **理解重导、重评分和真实重验的区别。** 只调整中文或列布局，通常是报告投影；改变方法或输入绑定，可能需要重评分；改变对象、轨迹或因果主张，可能需要重新进行受影响的真实语义判断。三者不是同一种“再跑一次”。
5. **修改之前看已有测试。** 优先选择对应入口的回归和冻结响应，然后按仓库要求跑完整门禁。离线通过能证明程序行为，但不能写成新Provider或新输入已经全部真实验证。
6. **执行真实请求前核对授权和账本。** 有界样本的请求上限不等于所有普通CLI都自动装配同一预算守卫；要检查实际入口。历史剩余额度也不能被新运行ID自动重置成一份新预算。

具体命令、环境要求、检查点选择和已知平台限制集中在部署附录，避免在这里再维护一份可能过期的命令副本。运行与维护验收应能用一条真实身份解释从原文到报告的完整经过，并把每一种缺口定位到负责的实现层。
