# 02　输入抽取、数据契约与方法治理

> 基线 `d6a400e`，核对日期 2026-11-24。返回[交接总览](README.md)。本章说明“依据从哪里来、怎样进入计算”，不能用生成文字替代这些记录。

## 1. 先分清四种内容

| 内容 | 示例 | 能否直接当产品事实 |
|---|---|---|
| 原文项目事实 | 某执行模式的速度范围、允许车位类型、驾驶员操作前提 | 需保留准确来源、限定和审核状态 |
| 方法规则 | 评级边界、适用对象、暴露组合政策、ASIL 矩阵 | 是方法依据，不是车辆能力 |
| 分析假设 | 为代表工况选择的距离、故障后加速度、目标初始位置 | 不能；可作为明确标识的条件性输入 |
| 程序推导 | 由给定轨迹求出的接触速度、时间、响应是否避碰 | 继承输入适用范围，不会自动消除假设状态 |

例如：原文写“任务周期 10 ms”，不能抽成“制动响应 10 ms”；写“训练速度 15 km/h”，不能自动成为运行模式的碰撞初速；正常模式上限也不等于故障后可达速度上限。

## 2. 文档读取与可追溯片段

### 2.1 支持的输入

[`DocumentReader.read()`](../../src/hara_agent/services/extraction/document_reader.py)目前接受 `.docx` 和 `.pdf`，读取失败、没有文本块或不支持的扩展名会显式报错。

- DOCX 通过 `python-docx` 按正文 XML 顺序读取段落及表格行；表格单元格在行内以 ` | `连接。段落保留章节路径；标题识别优先使用实际样式，也有有界的结构判断。
- PDF 通过 `PyPDF2.PdfReader` 提取页文本，原始块以 `PAGE-0001`等标识。当前不是 OCR 系统，也没有保证恢复所有复杂跨页表格或图中关系。
- `DocumentArtifact`含原路径、来源标识和块列表；项目运行另存文件内容 SHA256，文件名不承担项目身份校验职责。

### 2.2 原始页与检索片段不是互相覆盖

[`retrieval_blocks()`](../../src/hara_agent/services/extraction/evidence_retrieval.py)对较长 PDF 页按原有行、项目符号和空白边界形成约 600 字符片段；短页在不需阶段切分时保持原样。片段保存 `parent_block_id`、`span_start`、`span_end`、`span_location`，不改写原文。

示例标识：`PAGE-0008-S0002`仍可追到 `page[8]`的原始字符区间。片段选择用于缩小检索上下文，不替代原始页审计。代码对明确训练标题保留 `source_phase`；这不是任意文档结构都已百分之百识别的保证。

### 2.3 来源选择与输入身份

[`read_item_document()`](../../src/hara_agent/workflow/nodes/extraction.py)保存：

| 字段 | 用途 |
|---|---|
| `raw_blocks` | 未丢失的原始可读取内容 |
| `blocks`、`text` | 受当前来源选择政策约束的提取视图 |
| `item_sha256` | 当前文件字节内容身份 |
| `source_selection` | 选中/排除块、原因、政策版本与指纹 |
| `source_path`、`source_id` | 定位文件及展示来源 |

[`select_source_blocks()`](../../src/hara_agent/services/extraction/source_selection.py)使用已编译项目政策中的章节角色，仅对符合配置的带速度内容区分性能期望/执行器能力与运行速度；原块不删除。它不是任意关键词全局过滤器。修改选取政策会改变指纹，恢复时不能继续使用失配的派生事实。

## 3. 功能抽取原则

生产提取由 [`ItemArtifactExtractionAgent`](../../src/hara_agent/services/semantic/item_artifact_agent.py)与[`extract_item_artifacts()`](../../src/hara_agent/workflow/nodes/item_artifacts.py)组织，`FunctionNormalizer`负责结构归一化，不是另一个独立付费功能 Agent。

1. 优先遵循原文明示的功能清单。
2. 没有明确清单时，从有来源的功能动作、输出与职责识别；不能把标题、每个操作步骤或每一个性能数字都扩成新功能。
3. 功能与输出分开：例如“纵向控制”是职责，“减速度控制指令”是输出；两列不应只是原样复制。
4. 触发条件、前提、运行范围和退出行为保存在对应字段，不应混进功能名称后全部当无条件适用。
5. 一个来源功能可涉及泊入/泊出等多个运行条件，后续分析按真实条件区分；不能只在报表中拆成两个名字就声称已经分别做过因果分析。

[`function_source_guard.py`](../../src/hara_agent/services/semantic/function_source_guard.py)检查可识别的显式表格/编号清单与提取结果的一致性；发现多个候选权威清单时会标识歧义，不偷偷任选一个强制通过。该检查不是对任意文档风格的完整语义理解替代品。

## 4. 定向事实检索如何工作

```text
MethodContract.required_fact_specs + 请求运行模式
    → RequiredProjectFactSpec（类型、术语、单位、上下文）
    → DeterministicEvidenceRetriever 排序
    → CoverageFirstContextAssembler 组装有界证据及邻域
    → 定向语义提取
    → 原文片段、数值用途、限定/否定校验
    → RiskFact / SpeedEnvelope + 绑定或缺口
```

主要实现：[`project_fact_specs.py`](../../src/hara_agent/services/extraction/project_fact_specs.py)、[`evidence_retrieval.py`](../../src/hara_agent/services/extraction/evidence_retrieval.py)、[`targeted_verification.py`](../../src/hara_agent/services/extraction/targeted_verification.py)、[`project_fact_normalization.py`](../../src/hara_agent/services/extraction/project_fact_normalization.py)。

`RequiredProjectFactSpec`声明要找的语义类型及约束，不能内置测试答案、预期值或指定正确段落位置。检索不是必须找到某个固定标题才允许召回；类型词、单位、上下文、结构信号共同参与排序。没有足够证据时记录覆盖诊断与缺口，不能把“没被当前短上下文选中”等同于“原文一定没有”。

默认检索组装预算与物理请求的来源片段预算由各自入口控制。不能把约几千字符的原文片段预算误认为整条 LLM 请求只有几千 Token：请求还包含方法、结构化工况、控制依赖和输出契约。

## 5. 核心模型字典

| 类型 / 源码 | 重要字段 | 为什么不能省略 |
|---|---|---|
| [`FunctionDefinition`](../../src/hara_agent/models/item_definition.py) | `function_id/name/output/description/preconditions/triggers/odd_constraints/fallback_behavior/sources/status` | 功能、输出和适用条件职责不同 |
| [`ItemDefinitionFacts`](../../src/hara_agent/models/item_facts.py) | 边界、模式、ODD、`speed_envelopes/risk_facts/method_risk_fact_bindings/odd_scope_evidence` | 防止不同功能允许范围被并集化后全局使用 |
| `SpeedEnvelope`（同上） | 模式、上下限、条件、单位、来源、provenance/status | 一个全局最大速度不能代表训练、搜索、执行各阶段 |
| [`RiskFact`](../../src/hara_agent/models/project_facts.py) | `fact_id/parameter/value/unit/context/source_refs/provenance/approval/physical_semantics` | 中性事实可重绑定到方法，不把规则写进抽取 |
| `MethodRiskFactBinding`（同上） | 原事实 ID、目标 fact type、方法哈希、来源、绑定方式与状态 | 相同事实换方法后，旧映射不能无条件沿用 |
| [`EvidenceValue`](../../src/hara_agent/models/common.py) | `value/status/sources/rule_version/review_reason` | 数值、依据和审批是独立维度 |
| [`EvidenceBinding`](../../src/hara_agent/contracts/evidence_binding.py) | 因果边 ID、证据引用、证据种类与来源 | 证据应支持具体因果关系，不只是挂在整个场景上 |
| [`PhysicalScenarioPlan`](../../src/hara_agent/contracts/physical_scenario_plan.py) | 方案、假设、对象、运动与控制约束 | LLM 提议不直接变成评分结果 |
| [`HARAState`](../../src/hara_agent/workflow/state.py) | 身份、阶段、事实、场景、评级、SG、追踪 | 恢复、重导和复核的共同载体 |

`RiskFact.physical_semantics`会区分 `time_role`、`object_id`、`trajectory_id`、`branch_id`、参考语义与模型有效时域等。字段同名不代表可继承：故障前加速度不能自动成为故障后加速度；本车参数不能直接借给目标车。

**注意同名类型：** [`models/common.py`](../../src/hara_agent/models/common.py)中的 `SourceRef`面向项目/证据，含来源类型、ID、位置、摘录；[`contracts/method_contract.py`](../../src/hara_agent/contracts/method_contract.py)也定义方法编译用 `SourceRef`，含方法来源身份与哈希。它们不是同一种序列化结构，维护时不能只按名字替换导入。

## 6. 来源、状态与批准

`FactProvenance`目前包括项目输入、方法契约、批准规则、程序推导、LLM 推断、人工确认和场景定义。`ReviewStatus`为 `FINALIZED/PENDING/REJECTED/NOT_APPLICABLE`。

这些枚举表达的是不同维度：

- `provenance`回答“这个值从哪里来”。
- `status/approval`回答“这个值当前处于什么审核状态”。
- `value`回答“现在是否有可计算值”。
- 作用域与物理语义回答“这个值对哪个对象、阶段和条件有效”。

因此 `value=C2,status=PENDING`不是“没有 C”；值为 `None`或空等级字符串表示尚无数值，不能仅用 `is None`统计缺项。还需分别检查计算状态和工程审核状态。`RiskFact`要求精确来源；仅有 LLM 推断不能直接标成 `FINALIZED`。`EvidenceValue`的已批准值也必须有来源或规则版本。

自动假设不要求逐条等待工程师填距离或加速度，但必须明确其条件性。对确实未说明的产品控制能力，不能通过把假设改成项目事实消除 Pending。

## 7. 运行范围与跨项目复用

[`ItemDefinitionFacts.for_scope()`与`scoped_odd_context()`](../../src/hara_agent/models/item_facts.py)按功能和运行模式过滤 `odd_scope_evidence`。某种车位只允许某功能使用时，不会因为它出现在项目总列表中，就自动成为所有功能的允许车位。旧记录无限定时保留历史全局语义；这也意味着历史记录的粗粒度不能凭空恢复成更精细的原文事实。

[`HARAApplication.run()`](../../src/hara_agent/application.py)将当前输入内容哈希加入编译方法的运行视图；项目专属政策应匹配已绑定输入和条件，不能用方法资产名字、文件名或 `parking`词语猜当前项目。

换输入时正确做法是新输入身份、新运行，继续使用通用方法与同一生产链。以下情况应独立分类：

| 情况 | 处理 |
|---|---|
| 原文明确但没有被抽出/传到下游 | 程序缺陷，修提取/绑定并验证完整链 |
| 原文只写低/中/高速度档而没有配置值 | 产品规格缺项；记录限制，不伪造已知速度 |
| 引用其他版本或 TPA 规格但未提供 | 引用资料未交付；保留引用，不假设已读 |
| 场景距离/故障动态没有逐项给出 | 可由物理 Agent 提合理假设并条件性计算 |
| 方法不支持对象、速度边界或响应类型 | 方法/模型范围缺口，与来源缺失分开 |

四份 PDF 比旧 AVP DOCX 的规格粒度不同，不能要求它们都自动得到完全相同的事实数量或 Pending 比例。可复用性验收是“差异被正确处理”，不是强行输出相同等级分布。

## 8. 方法编译与治理

### 8.1 显式模板路径

[`TemplateWorkbookScanner`](../../src/hara_agent/template/scanner.py)扫描结构；[`TemplateRoleResolver`](../../src/hara_agent/template/role_resolver.py)解析角色；[`TemplateRoleCompiler`](../../src/hara_agent/template/compiler.py)及 [`FullTemplateCompiler`](../../src/hara_agent/template/method_compiler.py)生成方法契约。

角色发现依赖内容与结构证据，不能用固定 sheet 名、固定坐标、文件哈希或 sheet 顺序认定方法角色。歧义需要绑定本模板哈希的角色确认；角色缓存保存的是识别结果，不是又一份手维护业务规则。

### 8.2 YAML 基线路径

当前入口为 [`manifest.yaml`](../../method_assets/fusa_baseline_v1/manifest.yaml)，经 [`YamlBaselineCompiler`](../../src/hara_agent/method_sources/yaml_baseline.py)和 [`yaml_validation.py`](../../src/hara_agent/method_sources/yaml_validation.py)校验/编译。只有方法编译层直接读取治理 YAML；运行评分器只消费契约。

| 资产角色 | 当前来源示例 |
|---|---|
| ASIL | `raw/iso26262_spec.yaml` |
| S | `raw/severity_table.yaml`与归一化严重度语义 |
| E | `raw/vda702_atoms.yaml`、域规则与`normalized/exposure_policy.yaml` |
| C | `raw/c_profiles/iav_avp.yaml`及适用条件/别名 |
| FTTI | `normalized/project_analysis_policy.yaml`的 `timing_analysis`提供当前显式响应/时钟方法；`raw/ftti_formulas.yaml`、`raw/ftti_budgets.yaml`保留来源追溯，旧 contact+stop 公式及默认预算不是当前默认执行方法 |
| 场景与 FM | 维度、Atom、FM 场景模板、选择映射、约束与覆盖配置 |
| 项目分析政策 | `normalized/project_analysis_policy.yaml` |
| 报告文字与展示 | [`report_assets/hara_report_v1.yaml`](../../report_assets/hara_report_v1.yaml)，不承担评分权威 |

当前 manifest 明确将 `raw/controllability_rules.yaml`和`raw/c_iso26262.yaml`列为**不作为数值评分权威**，部分域文件的 S/E/C 段也被排除。文件“存在”不等于当前执行；查 C 为什么没有使用某条参考，先查 manifest 和编译结果，不能直接让运行时多读一个 YAML。

### 8.3 哈希与编译状态

[`yaml_loader.py`](../../src/hara_agent/method_sources/yaml_loader.py)使用安全 YAML 加载、文件 SHA256及规范化组合哈希。Manifest 的 `asset_hashes`核验资产内容；bundle hash考虑实际资产与政策。模板模式与 YAML 模式都需要 `compile_status`和工程规则编译检查。

[`MethodContract`](../../src/hara_agent/contracts/method_contract.py)包含 workflow、guidewords、scenario_model、severity、exposure、controllability、asil、SG/安全状态方法、report_contract、required_fact_specs、diagnostics，以及结构化评分/场景选择契约。`audit_snapshot()`提供分区哈希和数量，便于证明修改影响哪些部分。

## 9. 修改输入、规则或提示的影响

| 改动 | 不能忽略的后果 | 验证办法 |
|---|---|---|
| 只改展示用语 | 不应改风险值、来源、审批和身份 | 原 checkpoint 重导、字段对照 |
| 修改事实抽取/阶段判断 | 上游事实可能改变后续世界 | 原文正反例、跨输入固定样本、受影响因果重验 |
| 修改物理假设或对象方向 | 轨迹、因果和评级可能一起变化 | 重算依赖、因果身份失效、全分支核对 |
| 修改 C 适用边界 | 业务方法变化，不是“仅接线” | 可追溯方法依据、边界值测试、旧/新输入回归 |
| 修改提示或任务裁剪 | 模型解释和缓存语义可能改变 | 版本/请求身份、冻结响应与必要真实样本 |
| 修改报告模板 | 布局哈希变化，不一定方法变化 | 独立布局编译、样式/关联/原子输出核验 |

不要通过删除历史事实、给所有场景固定 7 km/h 或统一 C3 消除不确定性。新规则应进入受治理方法源，经编译进入同一个评分链。

## 10. 接手时最小可检查证据

对一个存在疑问的字段，至少能回答：

1. 它在哪份输入、哪一页/段/表行出现？原文有没有否定、前提或阶段限定？
2. 它是事实、方法值、假设还是派生量？来源与审批字段是什么？
3. 它对应哪个功能、运行模式、对象和轨迹？
4. 绑定的是哪个方法哈希、哪条规则？
5. 如果改变它，哪些缓存、因果结论和计算必须失效？
6. Excel 中的说明能否追回上述记录，而非只看到最后一段自然语言？

这套追踪关系是项目跨输入复用的基础。后续开发操作见[06](06_开发测试与维护.md)，现有数据交接见[08](08_资产移交与接手清单.md)。
