程序架构、状态与职责边界

系统解决什么问题

HARA Agent 把产品定义中的功能、运行范围和约束，与经过治理的 HARA 方法结合，形成可追溯的危险分析、风险评级、安全目标和 Excel 审核材料。它既不是让 LLM 直接填写整张 HARA 表，也不是只把一个参考项目的数值复制到新项目。

整个系统有三种职责：

职责 实际内容 主要实现
语义理解 提取功能和来源事实，判断引导词适用性，提出故障与危险行为、物理假设和因果解释 services/semantic/
工程计算 检查输入相容性，计算运动、接触与响应，执行活动方法中的 S/E/C 和 ASIL services/analysis/、编译后的 MethodContract
编排与交付 选择任务、限制预算、复用结果、保存状态、记录证据、投影与生成 Excel application.py、workflow/、infrastructure/llm/、services/reporting/

有数值不等于完成工程批准。系统允许对清楚标识的假设进行条件性计算；PENDING 可以是“已有数值但待审核”，也可以是“缺少计算条件而没有数值”。两者在数据和报告中都需要分开。

运行、缓存、复用和恢复是四件事

  1. Checkpoint保存流程已经提交到哪里和业务状态。CheckpointRepository.save()采用临时文件、flush、fsync、原子替换；不是只靠终端日志恢复。
  2. 提取产物缓存保存通过来源与结构检查的内容寻址产物。原始候选隔离在 candidates/，不能直接当成已验证事实使用。
  3. Provider 响应缓存保存对应请求的返回，降低恢复时重复网络调用。请求语义、模型或推理模式变化必须由相应身份区分。
  4. 分析复用决定不同原始身份能否共享物理方案、证据或完整因果结论。缓存命中不等于证明跨场景因果等价。

真实调用链

CLI 的 main() 解析 analyze 后进入 HARAApplication.run()。应用先执行 RunConfig.validate()，再由 MethodSourceResolver.resolve() 解析方法。显式提供 template_path 时，模板经 TemplateRoleCompiler.compile_method() 形成方法与报告契约；没有显式模板时，先编译报告布局，再将 report_contract 传给 YamlBaselineCompiler.compile()。最终都进入同一个 MethodContract 和 build_hara_agent_graph()，不是 YAML 专用的第二套评分运行时。

字段如何产生和流转

应用对 Item 文件字节计算 SHA-256，将 project_input_sha256 注入本次方法元数据副本，不改写方法资产。状态中的 method_contract 保存 template_hash、契约／编译器版本、编译状态、engineering_rules_compiled、source_kind、method_source_hash 和 report_template_hash。随后装配语义任务、风险服务、检查点仓库、审核记录器及报告器。引导词以包含定义和来源的对象传递，不能只留下名称。HARAState 是节点共享状态；阶段名表示接下来要执行的节点，不表示同名业务已经完成。

精确分支／错误去向

缺文件、非法扩展名／Run ID、无效样本范围在配置阶段抛错。方法为 NOT_READY 或没有编译工程规则时，解析器拒绝并附阻断诊断，不交给模型补规则。新有界样本若检查点、账本、报告或审核目录已存在，也会拒绝以保护历史。首次有界运行会在 MALFUNCTIONS 之前停下生成 bounded_sample_scope_preview；这只是范围预检，不能宣称已经物理／因果验证。后续只有发布门禁因待审核中断且 allow_draft=True 时，应用才走草稿出口，保留待审核状态。

是否 LLM／请求粒度／上下文

本步骤的编译、哈希、校验和装配不请求 Provider。创建客户端也不等于已经发送请求。普通运行默认最多 8 个工作线程；有界样本受 RunConfig 约束使用 1 路。provider_attempt_limit 会使运行进入有界模式；普通 8 路全量 CLI 不会自动获得一个硬上限账本。其他硬预算执行方式通过既有客户端注入共享 ProviderAttemptBudget，不能将并发数当预算或在子运行中重置账本。

缓存恢复

恢复先载入检查点，再重读当前 Item 并重算来源选择指纹；非初始化阶段必须匹配保存的来源选择与输入身份。有界运行还检查 sample_scope() 和 bounded_source_context。模板绑定缺失或方法哈希不一致会拒绝恢复，不能改保存哈希强行跳过。WorkflowGraph.run() 在预算耗尽时恢复最后原子提交状态，记录额度与账本路径后停止。普通异常则记录失败并抛出，不伪装成运行完成。

    resolution = MethodSourceResolver().resolve(
        template_path=self.config.template_path,
        baseline_manifest_path=self.config.method_baseline_path,
        report_template_path=(
            self.config.template_path
            if self.config.template_path is not None
            else self.config.report_template_path
        ),
    )
    method = resolution.method
    # One input identity for ordinary and bounded runs. Keep the compiled

result = dict(context)
records = context.get("odd_scope_evidence", [])
def applies(record):
    return ((not record.get("function_ids") or function_id in record["function_ids"])
            and (not record.get("operating_modes") or operating_mode in record["operating_modes"]))

applicable_records = [record for record in records if applies(record)]
for name in ("odd_locations", "odd_road_types", "odd_weather_conditions", "odd_road_surfaces"):
    scoped = [r for r in records if r.get("field") == name
              and (r.get("function_ids") or r.get("operating_modes"))]
    if not scoped:
        continue
    qualified = {v for r in scoped for v in r.get("values", [])}
    applicable = {v for r in applicable_records if r.get("field") == name
                  for v in r.get("values", [])}
    result[name] = [v for v in context.get(name, []) if v not in qualified or v in applicable]
if "odd_scope_evidence" in context:
    result["odd_scope_evidence"] = applicable_records
return result

真实调用链

MALFUNCTIONS 复合节点开始前，由应用注入的工厂调用 HARAApplication.prepare_scenario_candidates()：恢复 typed ItemDefinitionFacts → resolve_project_speed_context() → MethodScenarioCandidateService.generate()。semantic_graph._scenario_candidates() 接收候选和审计，写场景绑定缺口、候选记录与 scenario_candidates_prepared。这些基础候选随后交给失效条件化，不直接变成最终风险记录。

字段如何产生和流转

首先根据选定 operating_mode 取得对应速度上下文，并将项目事实投影到该模式。generate() 遍历活动方法的场景维度，_project_values() 选择该维度的项目允许值，_text_binding() 调用 Atom 解析器，以项目值、有效别名与方法目录形成绑定。每个绑定保留 project_value、method_value、resolution_status、unresolved_reason、候选 Atom、来源与 filled_dimensions。不能用一个展示字符串代替这些结构。

VDA Atom 目录模式下，WHERE 来自项目地点及明确的室内／室外环境限定，ROAD 来自路面条件；EGO_ACTION 使用当前模式，EGO_DYNAMICS 使用速度范围约束。明确的室内／室外替代条件可以细化通用停车场父标签，不能将所有通用地点直接改名为室外来制造覆盖。按失效的后续处理还会进一步投影功能作用域；本步按模式的投影不能被描述为已经完成所有功能适用性判断。

精确分支／错误去向

ProjectFactResolver.resolve_speed_envelope() 要求匹配明确模式，多个同模式范围有歧义时拒绝；不能用 parking 猜究竟是搜索还是控车。聚合范围仅在显式允许时使用，且不能把多个上下文范围压成一个。草稿路径只在没有任何来源速度范围时，允许返回 NoSourceSpeedEnvelope 和空约束，供后续假设分析；它不吞掉已有但不匹配、歧义或部分缺失的范围，也不自动补 7 km/h。

无项目值时生成 NO_ITEM_FACT 待解析绑定，不扩回整个方法目录。_binding_sets() 选择第一个具有多个来源值的维度为锚点，沿锚点形成候选；其他多值且未唯一绑定的维度保留 AMBIGUOUS_BINDING，不做全维笛卡尔积。有未解析维度时，相容性评价保持待定；已编译规则明确 DROP 的组合才排除，KEEP_RARE 保留，冲突与缺规则保留具体诊断。最终状态还结合速度审核性质和项目来源，不以“对象能创建”当作全场景已完成审核。

是否 LLM／请求粒度／上下文

本步不调用 LLM，不让模型自由生成基础 ODD。绑定、有限展开、约束和来源风险事实接线都由程序完成，所以生成若干基础候选不对应若干付费请求。后续物理 Agent 负责的是允许范围内的具体对象、轨迹和条件性参数假设，二者不能混为“全部场景都来自 LLM”。同样，基础允许列表有平行／斜列车位，只证明来源许可保存；它是否形成真实影响运动的几何、是否完成因果分析，需要后续独立证据，不能在此宣称覆盖已完成。

缓存恢复

基础生成是确定性过程，没有为它新建 Provider 缓存。其结构化绑定进入场景指纹，来源、方法或语义输入改变会影响下游任务身份。prepare_scenario_candidates() 将本次输入 SHA 继续绑定到候选服务的方法副本，项目专属决定按输入作用域匹配。普通入口保留完整父候选供后续代表焦点分配；样本父范围先记录允许 ID，再在既有条件化／归并后按 lineage 筛选，避免“抽样顺序改变同一候选的焦点”。这项调度见后续步骤，不代表本步额外增加场景维度。

具体示例

解释例子：项目允许室内、室外两类地点，路面又有干燥和湿滑。如果地点是多值锚点，本步可以形成两个有来源的地点上下文，而没有依据将路面任意两两配对时，路面保持待定；后续在既有有界代表组中处理必要差异。两个地点标签本身不证明两套危险机制都已算过。再如正常执行速度为 0—7 km/h，这里保存范围及来源，后续驱动异常可以用相容假设推导当前行程可达速度，既不能统一截为 7，也不能强迫全部故障速度超过 7。

开发排查与现有测试

按 speed_resolution → dimension_bindings → scenario_binding_gaps → dimension_compatibility → fact_provenance 排查。审计含 combination_strategy='primary_dimension_anchor_with_pending_unbound_dimensions'、未解析候选数、约束排除／罕见／冲突数、缺失或矛盾风险事实类型；要逐层统计，不用 Excel 主表行数代替覆盖或付费工作量。相关测试：模式和速度接线、来源锚定而非笛卡尔积、Atom 身份解析、来源范围与环境覆盖、ODD 作用域。当前不保证基础生成已经穷尽任意项目所有风险条件；未形成的交互与几何必须在覆盖证据中单列，不能用允许列表长度充数。

实现例 E04｜保留来源差异，同时避免无依据的全组合

筛选顺序与保守放行的准确含义

第一层是 MalfunctionSituationSelectionService.select。它由有来源的功能输出、功能运行作用域和规范化故障类型匹配情境规则，对每个父场景产生 INCLUDE/EXCLUDE/UNRESOLVED。没有正向规则不等于排除：缺输出证据、没有目录或竞争规则时，记录 UNRESOLVED 并继续后续因果判断。真正 EXCLUDE 要有可执行排除权限、批准项目约束、当前项目／功能／MF／场景范围精确匹配的直接证据；不能因“没命中参考场景”删除父场景。入口见 malfunction_situation_selection.py：select，审计保留 records/exclusion_evidence/unresolved_passthrough_count。

第二层才是 match_fm_template。一般路径按关键词／治理别名、组件类别、失效类型发现候选，再由 _qualify_matches 判断强、弱或歧义；原始首项优先序只记录，不作为歧义时偷选第一条的依据。另有已绑定项目且字段精确匹配的治理工程决定路径，也要核对批准模板及完整 option 身份。只有 FMTemplateMatchResult.injectable，即 STRONG_MATCH 且存在模板时，才执行父场景×模板选项；否则 selection_mode=BASE_CANDIDATES_ONLY，保留来源父场景。入口见 scenario_method_service.py：match_fm_template/_qualify_matches/instantiate_analytical_candidates。

一般资格判断的真实先后是：唯一“组件＋失效”交集先得强匹配，多个交集为歧义；无此唯一交集时，结构化组件／失效支持相互冲突则拒绝挑选；没有组件命中而有唯一“失效＋来源机制关键词”时可强匹配；唯一被规范目录支持的组件模板也可强匹配。只有失效类型或只有关键词通常仍是弱匹配，不据此注入。这样既不会让一个碰巧出现的词覆盖结构化冲突，也不会因多一个关键词别名降掉本已唯一的结构证据。具体层次及审计 qualification_tier 仍以 _qualify_matches 为准。

第三层逐 option 检查对象／方位、数值类型与非负范围、方法词汇映射，以及与父事实是否相容。INVALID_TEMPLATE_OPTION 或明确冲突的 option 不注入，并保留 validation_status=INVALID/CONFLICT；未映射词汇记 UNMAPPED_METHOD_VALUE，不伪造规范对象类型。合法 option 的距离、目标速度等写作 SCENARIO_DEFINED、approval=PENDING 的分析条件，原父对象不原地改写。一个父场景可以产生多个相互隔离候选。强匹配后若全部 option 无效／冲突，该方法返回空实例列表，不再悄悄退回父场景；这与未强匹配时保留父候选不同。 要查 options/conflict_count/instance_count 解释数量变化，不能自行补一个“最危险”对象或把未生成当成因果已否定。实现见 instantiate_analytical_candidates。

组合不是七维全集，也不是按评级选工况

wf-05 产生的每个物理 option 进入 ConstrainedScenarioSynthesisService.generate_candidates。实际调用为 generate_for_malfunction → generate_candidates → _generate_context_candidates → build_input → logical_selection_assignments → validate_provider_payload → materialize；验证方法名称虽然带 provider，普通确定性组合仍复用它来校验本地产生的选择，不表示这一层必须联网。当前基线的七维是 WHERE/ROAD/EGO_ACTION/EGO_X_ROAD/TRAFFIC_PATTERN/EGO_DYNAMICS/OBJECT，维度定义和适用性由已编译 scenario_model 提供。入口见 scenario_synthesis_service.py。

build_input 从 MF、功能输出、父条件、FM 模板证据与已按函数／模式收窄的项目上下文构建语义查询，再由 candidate_sets 分别形成候选池。硬约束包括速度交集、坡度、天气、来源地点、全局复合 Atom 相容性和可执行方法约束；排序使用机制与条件语义，不把 E 等级作为选取“更危险场景”的依据。已确认、不可修改的父绑定不能被覆盖；可细化的分析选择则保留父 Atom、子 Atom、来源与细化理由。必需、可选、不适用三类维度分别处理，不能为了凑齐七格把不适用项硬填成任意 Atom。入口见 candidate_sets/hard_filter_decision/global_compound_legality、ScenarioConstraintExecutor。

覆盖选择、来源边界与失败去向

逻辑组合先满足 coverage_plan 中的主要变化维度及复合填充关系。一个复合 Atom 可填多个维度，但不能被再次选择、与另一个 Atom 冲突占用同一维度。来源坡度边界通过独立 context 表达，而非把所有坡度、车位、天气与对象求笛卡尔积；include_source_boundaries 控制每个物理 option 的来源锚点，明确边界优先解析，再让普通来源场景代表其他环境。没有合法 assignment 返回 NO_VALID_COVERAGE_ASSIGNMENT；多来源边界 context 无解时可保留 SCN-SOURCE-… 的 PENDING 缺口候选，上层某 option 未产生组合时保留该 option 供后续审查，而不是扩回整个目录。入口见 generate_candidates/_generate_context_candidates、generate_for_malfunction。

def expand(
    self, scenario: ScenarioCandidate, risk_facts: Iterable[dict[str, Any]],
) -> tuple[ScenarioCandidate, ...]:
    if not self.policy_id:
        return (scenario,)
    if scenario.analysis_instance.get("driver_configuration_branch"):
        return (scenario,)
    by_position: dict[str, list[tuple[str, SourceRef]]] = {}
    for fact in risk_facts:
        if not isinstance(fact, dict):
            continue
        if str(fact.get("parameter", "")).upper() != "DRIVER_IN_VEHICLE":
            continue
        if str(fact.get("approval", "")).upper() != "FINALIZED":
            continue
        position, context = self.allowed_position(fact)
        if not position or not self._scope_matches(context, scenario):
            continue
        for source in self._source_refs(fact):
            by_position.setdefault(position, []).append((
                str(fact.get("fact_id", "")), source,
            ))
    if not by_position:
        return (scenario,)

FINALIZED 在这里修饰来源位置事实，不是把后续整个场景批准。_scope_matches 继续匹配当前模式和条件，_source_refs 保留来源。通过这段后，后续代码才核对父位置、建立新身份并应用有项目绑定的约定；“不在驾驶位”仍不能据此推出“人在车外”。

模型方程、坐标与适用条件

所有方程先把 km/h 除以3.6转为 m/s；距离 m、时间 s、加速度 m/s²。BODY_FORWARD_POSITIVE 为初始车体 x前、y左，目标中心偏移带符号；方向角从+x朝+y计，是固定速度方向，不是车轮角。有限接触 contact_half_length_m/contact_half_width_m 是双方投影半尺寸之和，不能替换成缺乏来源的默认车长／车宽。静止沿程模型的 relative_distance_m 是至首次表面接触的剩余行程，不是中心距。权威单位与模型范围见 MODEL_CATALOG/PARAMETER_UNITS。

模型 程序关系 使用前提与拒绝边界
CONSTANT_ACCELERATION_TO_IMPACT_DISTANCE d=v0*t+a*t²/2、v_contact²=v0²+2*a*d，稳定根求首次接触 静止目标在运动路径上；停止后不隐式反向。显式剩余独立限速可形成加速／限速分段，正常运行上限不是故障限速
GRADE_ROLLAWAY_TO_IMPACT_DISTANCE a=max(0,g*sin(atan(p/100))-r) 后使用沿程方程 从静止开始，坡度p为百分比，r为残余阻力；须明确重力与车头／下坡坐标。阻力足够时不启动，目标不在下坡路径不能强行接触
CONSTANT_LATERAL_ACCELERATION_TO_CONTACT w=vy0*t+ay*t²/2，x恒速，接触合速度按 x/y 分量求范数 明确独立惯性横移／侧滑与延展静止侧边界；不是恒速转弯，不能把正常转弯法向加速度当漂移；不派生纵向TTC
CONSTANT_SPEED_CURVATURE_TO_CONTACT theta=v*t/R、y=R*(1-cos(theta))，a_normal=v²/R 恒速无侧滑圆弧，只到显式时域或首个四分之一圆；方向、半径、目标侧须相容。半径为假设不等于车辆能力上界
RECTILINEAR_MOVING_TARGET_CONTACT r(t)=offset+u_hat*s_target(t)-v_hat*s_ego(t)；分段 s=v0*dt+a*dt²/2；首次同时 abs(x)<=hx、abs(y)<=hy 固定方向／固定投影有限包络，自车恒加速度；目标恒速或显式反应后制动至停，停止保持不反向。不模拟时变转向或旋转包络

求解权威集中在 scenario_physics.py：constant_acceleration_contact/constant_speed_curved_contact/rectilinear_moving_contact/derive_scenario_physics。圆弧还可成对提供 object_offset_x_m/contact_half_length_m，只核对固定有效纵向区间是否覆盖计算接触点；缺区间时只能依赖延展边界假设，区间外返回几何不适用，不能说别处也不会撞。直线移动模型可用 grade_frame 从静止推导坡度运动，并用 post_stop_motion=HOLD_POSITION 检查本车停住后目标是否继续进入包络。治理规则生成的 CONSTANT_SPEED_REPRESENTATIVE 则是已有确定性输入路径，不是 Agent 可任选的第六模型。相关入口为 AnalyticalPhysicsInstantiationService.produce_inputs。

def task_scope(self, candidate, malfunction_id):
    """Retain solved motion; assess its controls and response once."""
    scope = dict(malfunction_id=malfunction_id, scenario_id=candidate.scenario_id)
    for key in ("control_analysis", "physical_analysis"):
        if candidate.facts.get(key) and source_is_accepted_for(candidate.fact_provenance.get(key, {}), **scope):
            h = candidate.facts[key].get("hypothesis", {})
            if ("driver_in_vehicle" in self.intervention_inputs
                    and candidate.facts.get("driver_in_vehicle") is None
                    and not self.driver_position(candidate) and len(h.get("driver_positions", [])) != 1
                    and "driver_in_vehicle" not in h.get("unresolved_controls", {})):
                return "CONTROL_INPUTS_ONLY"  # Legacy omission; retain motion, assess the missing condition once.
            contact = candidate.facts.get("motion_model_outcome", {}).get("status") == "CONTACT" or bool(candidate.facts.get("collision_branches"))
            if contact and self.manual_path_gap(candidate, h, malfunction_id):
                return "CONTROL_INPUTS_ONLY"
            return ""  # An assessed limitation is not another request on resume.
    # A validated symbolic/no-contact world may intentionally have no
    # collision branches. Reuse its assessment rather than proposing the
    # same world again just to manufacture a numeric contact.
    if not (candidate.facts.get("collision_branches") and
            source_is_accepted_for(candidate.fact_provenance.get("collision_branches", {}), **scope)):
        return "MOTION_AND_CONTROLS"
    if self.method.metadata.get("project_analysis_policy", {}).get("timing_analysis"):
        # C readiness does not establish a reachable safe state or a timed
        # response. Existing source/method motion needs the same assessment
        # already requested by the autonomous motion path.
        return "CONTROL_INPUTS_ONLY"

LLM 实际判断什么，明确不判断什么

ScenarioFeasibilityAgent.assess / _parse 按受控请求返回 assessments。每个请求身份必须恰好有一项，字段包括三个布尔资格、breakpoint、三跳 causal_chain、hazardous_event、physical_interaction、risk_dimension_changes、置信度及状态。当前语义阶段止于 M→B→I→H：失效、系统行为变化、运行后果、危险事件。伤害尾段在评分后按 S 的活动方法语义附加，因果模型不自由生成伤情或先选 S 等级。

每一跳都要有 claim、basis_type、evidence_refs。DIRECT_FACT、DERIVED_PHYSICS、APPROVED_RULE 必须引用对应类别的已注册证据；原始速度不能伪装成已经计算的接触结论。父级 vehicle_level_hazard 是待验证主张，不能独自证明 I→H。故障运动产生的未干预轨迹是本步对象，制动可用、他方可避让等处置能力不能被写成已经发生的动作，从而取消原危险链。

physical_interaction 还限定当前目标、方位、对象 ID，以及 CURRENT_STATE 或 MODEL_TRAJECTORY 阶段。无接触取点不能写成已经发生接触；另一个参数点、后车或坐标系也不能补足当前取点。若自车静止反事实仍接触同一目标，必须说明故障运动增加危险的环节，不能仅因“有接触”就肯定该失效具有增量因果性。

时间审计：FTTI、TTC 与响应完成时间如何同时保留

RiskCalculationInputService.ftti 先保存接触时间类型、模型、对象、时间原点及逐分支 branch_timings，再调 FTTIMethodExecutor.evaluate。有分支时父场景时间不能顶替分支时间；当前多于一个接触分支尚需分别绑定响应轨迹，执行器保留未决，不先取最短接触时间冒充结果。ASIL 也不会被转换成默认秒数。执行前校验当前方案来源、所需/剩余/失效控制、驾驶员范围、响应模型、接触阶段、模型时域和停车保持条件。

静止目标的一类现有响应求的是最晚开始制动的 τ：

故障继续行程 + 从响应起始速度制动的行程 = 当前可用行程
v0·τ + a·τ²/2 + (v0+a·τ)²/(2·b净) = d
t停止 = (v0+a·τ)/b净
t危险时限（故障时钟） = fault_to_model_start_s + τ

这里的 b净 是已声明且适用的净减速，不会自动叠加或扣除另一未经定义的加速度。对移动目标及静止有限接触包络的特定无接触情形，程序复用 scenario_physics 的同一目标轨迹、故障行驶—制动—停车保持分段检查，求从即时响应起连续有效的初始安全窗口。不能在停车瞬间结束检查，原轨迹无接触也不能跳过所选响应验证。响应导致接触、根不在声明时域、停车后运动未知，分别保留实际失败或未决。

说明例：v0=1 m/s、a=0、d=4 m、b净=2 m/s² 时，最晚制动起始为 3.75 s，之后停车耗时 0.5 s。它们不能相加成 4.25 s 的可用响应起始预算。检测、决策和命令建立延迟应与起始窗口比较；模型已有的完成耗时另列。该例只说明方程，未引用任何真实项目取值。故障到模型起点的 offset 和危险判据没有绑定时，即使算出模型相对窗口也不能宣称故障时钟 FTTI。

回归定位见 结构化评分、E 基线一致性、C 路径适用性、响应时间 和 同作用域时间。调整规则须改方法来源并重新编译；调整物理来源/适用性须改现有输入或执行器入口；报告措辞不承担这两种修复。

上述统计分别由 MethodScenarioCandidateService、construct_physical_scenarios、assess_scenarios 和 ReviewArtifactWriter 记录。评估成本还要区分方案请求、响应缓存命中、确定性求解点和因果请求。不能用 Excel 行数代替场景覆盖，也不能把同一个共享方案算成所有成员都完成了独立因果评估。

因果资格：运动算得出，不代表故障导致该运动

因果链为 M（故障）→B（功能／车辆行为）→I（物理交互）→H（危险结果）。每一跳须引用当前来源或派生证据。已有接触解最多支持交互／危险阶段，不能倒推故障必然产生所列加速度或 t0 即固定曲率。当前因果 Agent 明确按未施加避险响应的世界评估；remaining_controls 或 Safe-State 提案不证明已检测、已请求、必触发，不能据此否定危险。若原轨迹本来已经包含制动、保持或目标反应，则必须保留该真实阶段，不能删掉它来制造接触。入口见 ScenarioFeasibilityAgent.SYSTEM_PROMPT、scenario_batching.py，回归见 test_unmitigated_causal_boundary.py。

只有 evaluate_risk_eligibility_payload 与有效 ScenarioCausalAssessment 共同满足资格的关联进入评分。否定、引用错误、断点未决分别保存，不能只看“有一个 assessment”或 final_retain 字面字段。因果契约的 FINALIZED 与场景假设的 PENDING 可以同时存在。需要有界纠正时复用 Agent 的 _repair_single_item_contract 及既有错误类型，不新增无限重试或把希望的 true/评级写入反馈。代码见 models/scenario.py、scenario_causal_assessment.py、scenario_agent.py。

业务复用与缓存：复用什么，失效什么

物理层先用 _physical_families 按任务类型和规范化物理条件归组，已知驾驶员配置可共享同一未缓解运动方案，但成员控制、因果和风险仍各自求值。plan_key 的输入包括条件、MF／功能、作用域项目上下文、方法／策略、模型目录身份、生产契约版本、提示版本和模型路由。相同文字 ID 不等于相同条件；也不能只因项目名相同便共享计划。入口见 construct_physical_scenarios、PhysicalHypothesisInstantiationService.physical_conditions。

保存的 physical_analysis_plans 包含 context、原计划／响应、校验版本、实例化和有界纠正记录。响应校验版本变化可先重验旧响应；合法旧方案不必重新付费。提示语义、目录或请求输入确有改变时，要通过实际身份隔离，不能伪造旧 key。当前版本常量位于 PhysicalScenarioAgent：运动 v61、控制 v40、因果 v34 位于 ScenarioFeasibilityAgent；计划契约仍是 PHYSICAL_PLAN_VERSION 的 v6，恢复行为应看版本和保存内容共同验证，不能只比版本号。

因果 exact_task_key 包含当前结构条件、来源、方法、提示／契约和项目证据。普通 key、请求序列化和解析均使用同一 scenario_with_current_physics 视图：当前只对保存的直线移动接触计算缓存作窄范围刷新；无变化返回原候选，直接事实冲突报错，同值直接来源仍保留原权威。不能让 key 看新 TTC、请求正文却引用旧布尔量，也不能把所有旧 DERIVED 都无条件当成可覆盖缓存。入口见 scenario_equivalence.py、HazardousEventRiskContextService._scenario_with_derived_physics、scenario_batching._scenario_json。

驾驶员间复用因果不是复制批准：driver_reuse_proof 检查真实依赖、人员差异及引用，rebind_assessment_payload 只重绑身份，再由正常 parser 校验。模型实际写了“纵向接触=false”等已改变事实时，应失效相应任务并重新判断，不能因为接触数值没变就免费重绑字面相反的结论。历史记录保留，最新合格结果按过程替代，不能按评级高低挑选。代码见 scenario_equivalence.py、workflow/nodes/scenarios.py，缓存回归见 test_scenario_incremental_checkpoint.py、test_scenario_checkpoint_contract.py。

来源、状态与批准

FactProvenance目前包括项目输入、方法契约、批准规则、程序推导、LLM 推断、人工确认和场景定义。ReviewStatus为 FINALIZED/PENDING/REJECTED/NOT_APPLICABLE。

这些枚举表达的是不同维度：

  • provenance回答“这个值从哪里来”。
  • status/approval回答“这个值当前处于什么审核状态”。
  • value回答“现在是否有可计算值”。
  • 作用域与物理语义回答“这个值对哪个对象、阶段和条件有效”。

因此 value=C2,status=PENDING不是“没有 C”；值为 None或空等级字符串表示尚无数值，不能仅用 is None统计缺项。还需分别检查计算状态和工程审核状态。RiskFact要求精确来源；仅有 LLM 推断不能直接标成 FINALIZED。EvidenceValue的已批准值也必须有来源或规则版本。

自动假设不要求逐条等待工程师填距离或加速度，但必须明确其条件性。对确实未说明的产品控制能力，不能通过把假设改成项目事实消除 Pending。

运行范围与跨项目复用

ItemDefinitionFacts.for_scope()与scoped_odd_context()按功能和运行模式过滤 odd_scope_evidence。某种车位只允许某功能使用时，不会因为它出现在项目总列表中，就自动成为所有功能的允许车位。旧记录无限定时保留历史全局语义；这也意味着历史记录的粗粒度不能凭空恢复成更精细的原文事实。

HARAApplication.run()将当前输入内容哈希加入编译方法的运行视图；项目专属政策应匹配已绑定输入和条件，不能用方法资产名字、文件名或 parking词语猜当前项目。

换输入时正确做法是新输入身份、新运行，继续使用通用方法与同一生产链。以下情况应独立分类：

情况 处理
原文明确但没有被抽出/传到下游 程序缺陷，修提取/绑定并验证完整链
原文只写低/中/高速度档而没有配置值 产品规格缺项；记录限制，不伪造已知速度

四份 PDF 比旧 AVP DOCX 的规格粒度不同，不能要求它们都自动得到完全相同的事实数量或 Pending 比例。可复用性验收是“差异被正确处理”，不是强行输出相同等级分布。

S/E/C、分支ASIL及控制通道

S/E/C 与分支 ASIL 的实际边界

7.1 同一个危险事件风险上下文

score_structured_scenarios 先绑定方法与项目事实、产生或核验中立物理量，再由 HazardousEventRiskContextService.build 形成同一 MF／场景／危险事件的上下文。RiskCalculationInputService 把上下文转换为 S、E、C、FTTI 输入；它不持有等级表。直接调用 StructuredRiskScoringService.score 也要经过当前物理视图和控制适用性检查，离线重放不能借旧 true 绕过。入口见 workflow/nodes/scoring.py、risk_calculation_input_service.py。

7.2 S：先选合法速度语义，再查表

S 的数字输入可能是相对速度、Δv、冲击速度或本车速度，但只能使用活动方法确认的语义。当前 manifest 声明相对速度主方法和交通域后备政策；后备尚未编译为可执行契约，编译诊断为 SEVERITY_FALLBACK_UNCOMPILED，缺相对速度时不能切到本车速度或交通域补 S。SeverityDeltaVSemanticAuditService.input_authority 检查来源、派生授权和语义冲突，SeverityMethodExecutor 按道路使用者组、碰撞类型及边界查表。若活动方法要求 Δv，没有批准转换时，已有相对速度也不能冒充 Δv。入口见 severity_delta_v_semantic_audit_service.py、deterministic_risk_executor.py、yaml_baseline.py，数值源见 severity_table.yaml 与 severity_semantics.yaml。

7.3 E：项目／场景语义绑定与组合策略

E 使用编译的 Atom、功能／组件适用域和组合关系，不是 LLM 对“常见程度”的自由打分。ExposureDimensionCoverageService.decide 给出维度覆盖诊断；ExposureInputReadinessService.assess 检查绑定可用性；ExposureMethodExecutor 与 ExposureCombinationExecutor 执行当前策略。默认 fusa_v1 的覆盖诊断并非额外强加的新评分门，实际结果仍按其编译语义决定。全高、混高、异级、同级依赖等分支的数值以治理策略为准，不能在修诊断时另造一套 E 算法。入口见 exposure_dimension_coverage_service.py、exposure_input_readiness_service.py、exposure_policy.yaml。

7.4 C：能力、适用范围和查表是三道检查

当前 C 先由活动方法执行 override／三态条件判断与 profile 查算，再核对有来源的条件性参考规则和运动适用性。TTC 有数值并不绕过这些条件。横穿、曲率、后方接近、停住后被目标撞上、全轨迹静止等世界，各自可能没有适用的制动时窗规则；应保留接触结果及具体 Pending 原因。参考规则来自 method.metadata.project_analysis_policy.controllability.conditional_reference_rules，包括必需控制、速度严格上界、函数输出和遮挡／迟发现排除条件；不修改数值精度来跨过方法边界。入口见 StructuredRiskScoringService._score／_conditional_reference_control、StructuredControllabilityExecutor、iav_avp.yaml。

排除条件的正则由治理 YAML 提供，执行器仅在当前有效假设的 conditions 和 operating_condition.physical_effect 中检查局部语句。否定、未覆盖范围、转折后的实际遮挡不能混为一谈。例如“不据此声明遮挡”不是当前已遮挡，而“道路无遮挡，但停放车辆遮挡行人”仍存在实际遮挡。改这里应同时保留正／反／混合句回归，不按项目 ID 或固定报告句子做白名单。来源见 project_analysis_policy.yaml，执行与回归见 structured_risk_scoring_service.py、test_c_response_applicability.py。

7.5 分支必须使用各自完整元组

collision_branches 是有对象、机制和接触时点的有限物理成员。branch_physics_view 在对象、方向、几何、速度、来源或阶段变化后失效父派生量；None 可显式清除分支输入。分支换对象时也不能借用父 OBJECT 的 E 绑定。相对速度范围的 S 表分区不证明 C 对整个区间不变。每条分支先算自己的 S/E/C，再经当前矩阵得 ASIL；不能拼接某分支最大 S 与另一分支最好 C。入口见 scenario_physics.branch_physics_view、StructuredRiskScoringService._score_collision_branches。

6.1 当前8路+硬预算的真实边界

HARAApplication.from_env 只有 bounded_sample=true 才自动建预算账本：

  • 普通非样本 analyze --max-workers 8 会调用模型，但默认没有逐HTTP硬预算账本。
  • --provider-attempt-limit N --max-workers 8 不会变成“有预算全量”；它触发样本校验并拒绝8路/缺失样本limits。
  • 8路全范围且统一记录/限额，使用已有client/budget依赖注入；不是新运行时或新CLI。

下面是受控调用骨架，只有替换占位并获得对应授权后执行：

7. 日志、账本与缓存

OpenAICompatibleClient 在stderr记录任务、尝试、字符、上限、思考选项和usage；WorkflowGraph.run 记录阶段。-u和 2>&1 | tee 同时显示终端及文件；已有后台运行可在另一个终端 tail -F 已确认的日志路径。后台在跑不等于IDE当前终端会自动显示。

产物 位置 意义
checkpoint <run-dir>/<run-id>.checkpoint.json 最后原子提交状态，不是最后HTTP返回

8. 中断恢复

CheckpointRepository 用临时文件、flush/fsync和原子替换；WorkflowGraph.run 在耗尽预算时回到最后提交状态并保存原因。HTTP返回已存而阶段未提交是可能的，恢复应命中响应缓存。

恢复前确认：原输入字节、来源选择策略、方法资产和模板不变；保留Run ID/run-dir/review-root/缓存/账本；样本所有limit、IDs、pair limit和预算与原scope一致；模型路由/思考配置等与绑定context一致；有当前有效授权与余量。然后原命令增加 --resume。注入budget的全量继续同一受控入口，设置 resume=True并复用原账本。

校验见 HARAApplication.run/bounded_source_context。Bounded sample inputs, method, or Provider configuration changed 应查真实差异，不删guard/改旧哈希。换Item内容、对象、方向或阶段应新建运行或走差异验证；不能用恢复继承旧结论。

HARAState.read_committed/from_dict 有不同语义：前者只读已提交状态，适合离线投影；后者用于恢复，Scenario/因果契约不兼容时保留上游、失效场景/风险/SG并回到MALFUNCTIONS。旧文件可读不代表旧结论可继续，恢复可能需要新请求和预算。

响应键包括提示、schema、有效路由/模型，物理独立推理策略也参与；凭据不参与。语义变化后不命中通常正确。旧格式兼容不能把旧返回冒称新提示真实验证。不要清空历史来“修缓存”。

5. 修改方法YAML

入口是 manifest.yaml、validate_manifest、YamlBaselineCompiler。执行器只接收编译后的 MethodContract，不直接打开YAML。

推荐步骤：

  1. 查canonical role、normalized source和profile，确认是数值权威、条件约束还是仅参考。
  2. 说明依据、适用范围、对象/阶段/控制及优先级，不按参考表ASIL分布倒推规则。
  3. 业务规则放受治理资产，不在Python写C等级或备用ASIL矩阵。
  4. 对已审资产按原字节重算asset_hashes，再编译。哈希只证明完整性，不是工程批准，不能用更新哈希掩盖未审方法变化。
  5. 跑编译、边界、parity与同输入冻结响应对比，记录允许变化和不应变化的结果。

只读计算单文件哈希可用：

.venv/bin/python -c 'import hashlib,pathlib; p=pathlib.Path("method_assets/fusa_baseline_v1/normalized/project_analysis_policy.yaml"); print(hashlib.sha256(p.read_bytes()).hexdigest())'

它不会更新manifest，也不授权变更政策。

三个常见误区：

  • 文件存在不代表执行。 当前manifest排除了raw/controllability_rules.yaml、raw/c_iso26262.yaml作为数值权威，不能只改这些文件就称C已接通。
  • 方法不是项目事实。 项目决定应绑定输入内容和适用条件，不通过方法资产中的项目名识别新Item；scoped_odd_context/ItemDefinitionFacts.for_scope 保留局部/全局证据。
  • 允许范围不是当前工况。 允许室内/外、上下坡、多车位不代表每个候选同时具备全部条件；17种请求焦点也不等于17种真实几何覆盖。

实现例 O01｜相同并发请求为什么只发送一次

生产调用中，语义 Agent 通过 ResponseCheckpoint.complete() 取得保存响应或发送请求。输入包括完整 LLMRequest、客户端有效配置以及是否只读缓存；输出是一个响应或缓存未命中时的 None。下面只摘录身份生成与加锁部分，缓存读取、校验及落盘继续在 _complete_locked() 中执行。

def complete(self, client, request, *, cache_only=False):
    config = getattr(client, "config", None)
    # Full prompt/schema identity includes source facts, method and scenario
    # IDs. Credentials are neither part of the key nor written to disk.
    effective_request = asdict(request)
    # Batch position and retry permission do not change the model input.
    # An exact successful response stays usable with stricter retry policy.
    effective_request["metadata"] = {key: value for key, value in effective_request["metadata"].items()
        if key not in {"parent_batch", "split_path", "split_depth", "strict_no_format_retry"}}
    material = {"request": effective_request, "route": {
        key: getattr(config, key, "") for key in ("provider", "base_url", "model", "scenario_thinking")
    }}
    if request.task == "construct_post_fault_physical_scenario":
        material["route"].update(physical_reasoning_identity(config))
    key = hashlib.sha256(json.dumps(material, ensure_ascii=False, sort_keys=True,
                                   separators=(",", ":"), default=str).encode()).hexdigest()
    path = self.directory / f"{key}.json"
    # Same in-flight request in concurrent workers must not pay twice on a
    # cache miss. Atomic rename below still protects interrupted writes.
    with _request_lock(path):
        if cache_only and not path.is_file():
            return None
        return self._complete_locked(client, request, path, key)

effective_request 保留实际提示、Schema 和元数据，仅去掉代码列出的批次位置／重试许可字段。物理任务另外纳入有效思考配置，防止 low、disabled 等配置串用缓存。相同路径由同一进程内的锁串行进入缓存检查，因此并发首次未命中也不会同时发送四遍；不能把这里的线程锁描述成跨主机分布式锁。

具体例子： 四个线程提交相同请求，第一次实际调用客户端，其余三个读取已保存响应。读取返回的本次 usage 为零；历史付费消耗仍由原账本保留，不能据此抹掉之前的成本。请求内容或有效物理推理配置改变时，不能期待仍然命中。

            if attempt == 4:
                raise
            time.sleep(0.05 * (attempt + 1))

具体例子： 写临时文件时中断，原 checkpoint 仍是上一版；写完后通过同目录 os.replace() 替换。遇到 PermissionError 时仅有限重试文件替换，不重新调用 Provider。原子替换并不提供多写入者业务合并，因此并发任务结果仍需由 workflow 的收集和保存流程统一提交。

源码与验证： CheckpointRepository.save/load、WorkflowGraph 保存入口；因果批次中断后复用、某并行任务失败后仍保存已完成任务、预算停止返回最后已提交状态。这些测试验证相关流程的保存/恢复行为，不等于对所有操作系统做过断电故障测试。
